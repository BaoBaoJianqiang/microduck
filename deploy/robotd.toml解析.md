# 解析：`robotd.toml`

## 这是什么

**每台机器人各自的参数模板**（403 行，绝大多数值以注释形式给出内置默认）。安装到 `/etc/robot/robotd.toml`，由 `robotd` 在启动时读一次（不热加载，改任何值都要 `systemctl restart robotd`，热加载推迟到 robotd-design.md §4.2）。

文件头注释交代了三个设计决定：

1. **它放在 `deploy/` 而不是发布版目录里**：这是每机的配置而非随版本出厂的默认值，必须幸存于更新*和*回滚（architecture.md §3），安装器永不覆盖它。
2. **下面每个值都是内置默认**：整个文件删掉也能跑——未初始化的板子按同样的数字起来，而不是拒绝启动；远程诊断"守着默认值的守护进程"远比"不肯启动的守护进程"容易。
3. **保持注释状态，除非这台机器真的需要不同值**：`install.sh` 只复制一次这个文件、永不覆盖，所以一旦取消注释，这个值就永远冻在这块板上，而发布版的默认还在前进——某支舰队就是这样站在这份文件的 kP 120 上、而发布默认已是 160 的。

## 逐节解析

### `[bus]`

| 配置 | 值 | 说明 |
|---|---|---|
| `port` | `/dev/ttyS2` | 15 个舵机与 imu_to_dxl 板共享的串口。`/dev/ttyS2` 是 Radxa Zero 3W 的接线；接法不同的板子也可用 `robotd --port` 按次覆盖（dev 逃生门，不是让人改这里） |

### `[control]`

| 配置 | 值 | 说明 |
|---|---|---|
| `hz` | `50` | 控制环频率（Hz）。50 继承自原型机在树莓派 Zero 2W 上的选择，从未在 Radxa 上重新推导过——相信它之前先测量：`microduck_runtime` 里的 `bench_dynamixel_bus` 报告给定频率下的实际速率、抖动、总线占用与错误计数，控制环自己的五分钟摘要也从 robotd 内部报告同样的东西 |
| `cmd_alpha` | （注释，0.2） | 对收到的命令做每 tick 的 EMA 平滑：`cmd += alpha * (target - cmd)`，摇杆的突变变成步态跟得上的斜坡；1.0 为直通。`cmd_alpha` 管速度扭量，`head_alpha` 管头部目标与身体姿态 |
| `head_alpha` | （注释，0.2） | 同上 |

### `[update_gate]` —— 决定"健康"从而决定回滚

这一节是守护进程现有形态的全部意义：更新器的自动回滚只有当判定是真实测量时才有意义。**60% 目标速率的环是活的、每问必答、但坏透了**——三个阈值就是用来区分它与正常机器人的。叫 `update_gate` 而不叫 `health`，是因为 `robot.health` 报告的多得多（电池、电机温度、环与总线计数器），而这些都不能参与判定——发布版绝不能因为它落在的板子状态而被回滚。

| 配置 | 默认 | 说明 |
|---|---|---|
| `min_achieved_hz` | （注释，45.0） | 实际速率下限（50 Hz 的 90%）：松到一个慢 tick 不触发，紧到每十拍丢一拍的环不算健康。随 `control.hz` 同步调整 |
| `stall_periods` | （注释，25） | 多少个周期完全没有 tick 判为 WEDGED（500 ms）——检测死环而非慢环。原值 3（50 Hz 下 60 ms）会被忙碌板子上的普通调度抖动轻易超过，抖动触发的健康检查会回滚好发布 |
| `max_consecutive_errors` | （注释，10） | 容忍的连续总线读失败。一次掉事务在串口总线上很普通；连续一串意味着总线没了，读不到自己关节的机器人无论环转多快都不健康 |

### `[policy]` —— 策略加载与调参

| 配置 | 值 | 说明 |
|---|---|---|
| `enabled` | `true` | 是否加载策略。`false` = 照常跑环、保持初始姿态、且保持健康——台架上反复 install/rollback/断电时最安全的配置，与"想要但加载失败"（报不健康、触发回滚）刻意区分。命令行等价 `robotd --no-policy` |
| `mode` | `"walk"` | 驱动模式：`walk`（腿，默认）或 `roller`（轮）。模式决定加载哪些策略**以及下面所有未设值的按模式解析**——切轮式 = 改这一行 + 重启。roller 预设来自原型发射器：`roller.onnx` 为运动策略、A 键触发下蹲拾取（3.0 s, 0.8）、`action_scale` 0.8，其余与步行一致；唯独站立网络不进轮式（轮上跳过站立过渡） |
| 策略文件 | （注释，walk/stand/sitstand/ground_pick/kick_left/kick_right/roulade 七个默认路径） | 未设 = 发布目录内该模式的默认，普通更新会带着与二进制一同训练的策略。指向自己的 `.onnx` 可以不切版本试构建。字面量 `"none"` 显式关闭可选槽位 |
| 维度约束 | —— | 全部必须是 **61 输入、14 输出**：每个 alpha 策略是 obs[1,61] → actions[1,14]，robotd 在加载时检查（另有 51 维遗留家族，加载即拒："observation width is 51, expected 61"） |
| ONNX Runtime | —— | 需要 dlopen（非链接），缺库是启动失败而非构建失败，经 `robot.health` 报告并保持姿态；`ORT_DYLIB_PATH` 可覆盖查找路径 |

调参项（全部注释、按模式解析默认值）：

| 配置 | walk / roller 默认 | 说明 |
|---|---|---|
| `action_scale` | 0.9 / 0.8 | 策略原始输出 → 关节偏移的缩放 |
| `standing_action_scale` | 1.0 | 站立策略按整体应用训练 |
| `standing_gain_ratio` | 0.8 | 站立以 `gain` 的这个比例更柔地运行 |
| `gain` | 200 | 位置 P 增益 |
| `head_lowpass` / `legs_lowpass` | 0.5 / 0.7 | 头/腿关节目标的一阶低通——这是 alpha 策略**训练时**的值（mjlab ACTION_LOW_PASS_*），必须与训练一致否则迁移劣化；两种模式都保留（roller 预设同样继承） |
| `ground_pick_period` / `_action_scale` / `_gain_ratio` | 4.0/1.0/1.0（roller 蹲 3.0/0.8） | A 键地面拾取：一个周期秒数（70% 处收手）、缩放、增益倍率 |
| `kick_duration` | 0.5 | 踢腿窗口持续秒数 |
| `roulade_duration` / `_action_scale` / `_gain_ratio` | 1.0/1.0/1.0 | 一次前滚秒数（按住 X 链式翻滚，滚动中的必然完成）；滚动态的缩放与增益倍率 |
| `voltage_adapt` / `nominal_voltage` | false / 7.4 | 按电池电压缩放动作：有效 scale = action_scale × (标称/实测 EMA，钳位 6.0~9.5 V)。舵机有效 kP 随供电走，这个让压降时响应保持稳定；默认关，同原型 |

### `[safety]` —— 跌倒判定与软着陆

核心思路：**跌倒是一个报告**（`robotctl monitor` 与状态流可见），它什么都不拒绝——跌倒的机器人照样可以 enable、init、驾驶、放技能，因为倒地恰恰是最需要做这些事的时候。守护进程对跌倒*做*的事是 `limp_fall`，它有自己独立的探测器。

| 配置 | 默认 | 说明 |
|---|---|---|
| `fall_gravity_z` / `fall_debounce_ms` | （注释，-0.5 / 200） | 投影重力在躯干系上的跌倒判定（直立 z ≈ -1.0，侧躺近 0）；去抖，否则一次扎实的落脚冲量会被读成跌倒 |
| `deadman_ms` | （注释，500） | 多久没有速度意图就停机。**是停、不是瘫**：与客户端失联应留下一个站着的双足（站立是它的安全态），失稳是另一件事、由 limp_fall 应答 |
| `gain_limp` | （注释，50） | limp-fall 让出的增益——低到让路而非跟地板较劲 |
| `limp_fall` | （注释，**true**） | 软着陆：看到要倒的瞬间（落地前）增益降到 `gain_limp`、关节随推随动，落地后经 `limp_fall_pose_ms` 斜坡回站立姿态再交还站立策略——交给它的是"已知姿态的静止机器人"，恰好是它擅长的情况。关掉则跌倒不改变任何行为（原型行为）。**已在真机上验证后默认开启**：全舰队软着陆是目的，每块板单独选入的模式等于没人选 |
| `limp_fall_tilt_z` / `_predict_z` / `_lookahead_ms` / `_debounce_ms` | （注释，-0.90 / -0.5 / 300 / 60） | **跌倒算"开始"的判定——整个特性的关键**。不用位置（重力到 -0.5 时已在地板上），用投影：投影重力随躯干旋转，其变化率正是同一 12 字节 IMU 块里陀螺的 `-(w × g)`，外推可知 `lookahead` 之后的重力。已倾斜超过 `tilt_z`（约 26°，正常走路到不了，落脚与推搡因此被排除）、仍在倾而非恢复、外推越过 `predict_z` 才触发。去抖三 tick |
| `limp_fall_still_rate` / `_still_ms` / `_max_ms` | （注释，1.0 / 200 / 1500） | 着陆与之后：limp 在机器人静止（读陀螺不靠计时——绊一下与摔下桌子时长完全不同）时结束，或至多 `max_ms`，免得被抱在手里的机器人一直瘫着 |
| `limp_fall_pose_ms` / `_pose_gain` | （注释，600 / 160） | 姿态斜坡回到站立的时长与增益（160 是软化后的站立增益；0.6 s 在真机上敲定——1 s 大多是站立前的死时间，0.3 也可行，留了余量） |
| `battery_empty_shutdown` | （注释，true） | 电池 EMA 到空电下限（6.6 V，即电量 0% 的同一值）时优雅坐下并关机。EMA 走约 10 s，负载压降不会误触发；到 6.6 只能是电池真的耗尽 |

### `[audio]` —— 声音与耳朵

| 配置 | 默认 | 说明 |
|---|---|---|
| `enabled` | （注释，true） | 机器人嗓子（`/var/lib/robot/sounds` 下的种子合成音库——发布版 postinstall 的 `sounds ensure-bank` 渲染）与耳朵（板载麦克风上的撸鹅分类器）。全是可选设备：没编解码器的板子走路一样、保持安静，本节任何东西都到不了健康判定 |
| `device` | （注释，`plughw:aic3104`） | ALSA 播放设备——`setup-board.sh` 带起来的 TLV320AIC3104 编解码器；麦克风 worker 从 `"<device>,0"` 采集 |
| `bank` | （注释，`/var/lib/robot/sounds`） | 音库位置 |
| `greet` | （注释，true） | 控制环起来时嘎一声——无头板子上那声嘎就是"robotd 在跑"的听觉确认；频繁重启守护进程嫌烦可单关它（保留触发器与麦克风） |
| `pet_detect` | （注释，true） | 监听撸鹅并咕咕。未设=关（常开版太吵），选入制；模型随发布版携带（`models/pet_detect.onnx`），阈值是分类器滞回（进高于、出低于） |
| `pet_enter_threshold` / `pet_exit_threshold` | （注释，0.95 / 0.85） | 同上 |

### `[theremin]` —— ToF 特雷门琴

| 配置 | 默认 | 说明 |
|---|---|---|
| `enabled` | （注释，true） | 开关只决定它**能不能**被启用（`robotctl theremin` / `robot.theremin`），ToF 已知损坏的鸭子可以 outright 拒绝。需要 `[audio]` 开——没有嗓子的特雷门是一张无缘无故张开的嘴 |
| `socket` | （注释，`/run/tofd/tof.sock`） | tofd 的深度流 |
| `near_m` / `far_m` | （注释，0.10 / 0.70） | 可演奏频带（米）。低于 near 是传感器盖玻片串扰发明的短回波；超过 far 是噪声回波，而那偏偏会是低音区 |
| `min_zones` | （注释，2） | 凑成一只手的最少区域数。取 2：频带远端的手只占几个区域，且其中只有部分携带可用状态 |
| `statuses` | （注释，`[4,5,6,9,10,12,13]`） | **决定乐器音域的字段**。ST 把 5、9 记为"range valid"，只信它们的构建在约 30 cm 处就看不到手——再远，移动的手返回 4 或 13（一致性失败、sigma 过高），携带的距离对音高完全够用；6、10、12 是另外实际可用的码（12 = 被锐利边缘模糊，手沿正是如此）；255 = 看了但没东西，永不入列。音域短加码、空气里出鬼音减码；`robotctl theremin` 最后一列的逐码计数带 `*` 标出本列表相信的码——调它就用那个 |
| `hold_ms` | （注释，250） | 传感器掉线时音符保持的毫秒数——让"可用/不可用"间闪烁的区域不把音符剁成碎渣；太长则收回的手还在响 |

### `[detect]` —— 摄像头找鸭子（由 mediad 读取）

| 配置 | 默认 | 说明 |
|---|---|---|
| `enabled` | （注释，true，**默认关**） | 开关住在这里是因为这是 `robotctl configure` 编辑的文件、机器人只有一个设置的地方；帧在 mediad 的管线上、感知该挨着传感器，所以由 mediad 读取。没被要求找鸭子的机器人不该每半秒白付约 60 ms |
| `model` | （注释，示例路径） | 未设则试发布版自带的，NPU 优先（`models/duck_detect.rknn`），NPU 被设备树关掉时（Armbian 出厂即如此）落到 CPU（`.onnx`）。`sudo sh /opt/robot/daemon/current/scripts/setup-npu.sh` 打开 NPU，需重启 |
| `hz` | （注释，2.0） | 每秒看几次。**2 是热限不是偏好**：全速在 Radxa Zero 3 上到 95 °C、CPU 降频到 408 MHz——那是"为了看清楚而走不好路"的机器人 |
| `threshold` | （注释，0.35） | 本模型自有刻度上的置信度。随附模型量化为 INT8、分数不是概率——每个真实检测约 1.3，其余什么都不读（输出张量与框坐标共享一个量化 scale），所以这是有/无阈值而非旋钮 |

### `[chorale]` —— 多鸭合唱

`accept`（注释，false，**默认关，且这一节就这一个键**）：几只鸭子经蓝牙合唱一首四声部，无共享时钟——指挥鸭的节拍计数器就是时基，声部按各自音域推算；`robotctl chorale` 启动寻伴。默认关的原因：合唱不只是声音——它动嘴也动头。一台因为别的机器人走进房间就开始动画的机器人，是在别人客厅里做没人要求的动作；咖啡馆里两个人的鸭子没道理配对。关还意味着*不可见*而非礼貌拒绝：没选入的鸭子根本不向空中放任何东西。需要 `[audio]` 开。

### `[media]` —— 摄像头与推流（由 mediad 读取，改动需重启 mediad 而非 robotd）

这节曾是 `mediad.service` ExecStart 行上的 flag（发布版安装器会重写该行），唯一支持的改法是 systemd drop-in——而没人会为了"为什么视频发虚"去碰 drop-in，所以搬进配置文件。

| 配置 | 默认 | 说明 |
|---|---|---|
| `camera` | （注释，true） | 关掉改为推测试图案——没摄像头的板子要的就是这个：流水线照样起、WebRTC *控制*通道仍然存在（它与视频轨道捆绑，流水线起不来两者全丢） |
| `quality` | （注释，`"720p30"`） | 单键设定帧尺寸与速率：`1080p30`/`720p30`/`720p15`/`360p30`。一个键而非宽、高、fps 三个，因为它们不独立变化——采集路径给不出的档位等于 mediad 起不来；全部 16:9，"更小"永不意味着"裁切"。720p30 是 mediad 所有测量所在的档位（ISP 主路径 29.3 fps，采集格式与缓冲深度找了三轮台架）；传感器钉在 1920×1080@30 上由 ISP 缩小输出，故 1080p30 不需缩放——未测的是 2.25 倍像素下采集与编码是否仍守 30 fps。守不住的档位是变慢而非失败 |
| `bitrate` | （注释，2000000） | 起始视频码率（比特/秒）。未设跟随质量：1080p30→4 Mb/s、720p30→2 Mb/s、720p15→1 Mb/s、360p30→800 kb/s。webrtcsink 的拥塞控制从这里出发，它是起点不是天花板。单位是比特：2 Mb/s 写 2000000，低于 100000 会被当作把千比特当比特写的人而拒绝 |
| `congestion_control` | （注释，`"gcc"`） | 发送速率是否随链路自适应、以什么方式：gcc / homegrown / disabled。**既是网络设置更是 CPU 设置**：带宽估计器是 mediad 中最大的单一消耗者——一个对端时 `rtpgccbwe` 占 7.6% 核对 v4l2src 的 0.3%（它逐包工作，采集逐 DMABuf 句柄工作），`disabled` 删掉那个线程。代价是自适应性且不小：让码率随链路变化正是 webrtcsink 收原始视频而非预编码 H.264 的全部理由——链路一直好（同 LAN 一跳）时估计器花 CPU 探一个永远碰不到的天花板；链路劣化时它是"还有画面"与"卡死"的区别。`disabled` 也让上面的 `bitrate` 回归字面义：没人动它，它是速率本身而非起点。`homegrown` 是 webrtcsink 自带的发送端启发式——比 gcc 便宜、也比它钝。gcc 是 webrtcsink 默认，这行写出来只为可发现 |

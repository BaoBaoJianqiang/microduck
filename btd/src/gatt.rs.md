# `gatt.rs` 文件解析 —— GATT 线路契约：UUID

## 1. 文件定位

- 路径：`src/gatt.rs`
- 角色：定义客户端必须知道的两个 UUID（服务、RPC 特征值）。刻意做成**平台无关**。
- 为什么不放 `bluez.rs`：它们是线路契约的一部分，与 `duck-ipc-proto` 里的方法名地位相同——机器人提供它们，每个客户端都要按它们查找；无法为 Linux 编译的客户端（笔记本上的 `duckctl`）同样需要。

## 2. UUID 的选取原则

- 使用随机 v4 UUID，而非任何派生值；它们归本项目所有；
- 一旦 App 依据它们发布，就**绝不能再改**；
- 完整写出字面量，方便直接 grep 某个 UUID 值时定位到本注释。

## 3. 公共常量

### 3.1 `SERVICE_UUID`

```rust
pub const SERVICE_UUID: uuid::Uuid =
    uuid::uuid!("6f5d2a10-3b47-4c8e-9a1f-2d7e8c4b6019");
```

机器人的服务，客户端扫描时寻找的目标。

### 3.2 `RPC_UUID`

```rust
pub const RPC_UUID: uuid::Uuid =
    uuid::uuid!("6f5d2a11-3b47-4c8e-9a1f-2d7e8c4b6019");
```

RPC 管道特征值，用法有三种：

1. **read（读）一次**：获取 API 版本（`API_VERSION`）；
2. **write（写）**：写入 NDJSON 请求字节；
3. **subscribe（订阅）**：接收答案通知。

双向都做分片，以 NDJSON 消息间已有的换行分隔，具体机制见 `framing`（机器人与 `duckctl` 共用同一模块）。

读取操作是契约的一部分，而非可有可无的点缀：

- 它要求经过认证的加密链路，因此是迫使中心设备**在写入之前先配对**的机关；
- 订阅不需要加密，所以若没有这个读操作，客户端会先订阅、第一次写被静默拒绝，而在 macOS 上既看不到配对提示也看不到错误；
- 读回的 `API_VERSION` 让版本不匹配的客户端在发送任何请求之前就能说明问题。

## 4. 关键设计：一个特征值承载双向

客户端向 `RPC_UUID` **写请求**，并**订阅同一个特征值**收响应。

- "两个特征值（一个写、一个通知）"是更常见的形态，最初也是那样写的；
- 但在本场景更差：BlueZ 把写和订阅报告为两个独立事件，使用两个特征值时，机器人不得不靠设备地址把"某特征值的写"与"另一特征值的订阅"猜测式地配对；
- 合成一个特征值后，两个事件按构造就从属于同一条连接，是真正的双工流；
- 同一特征值同时具备 `write` 和 `notify` 在 BLE 中很普通。代价只是在 nRF Connect 之类的通用浏览器里同一行既是写又是通知，看起来略怪。

## 5. 单元测试

- `the_uuids_are_distinct`：断言 `SERVICE_UUID != RPC_UUID`。二者在 App 发布后都被冻结，必须互不相同。

## 6. 本文件要点小结

1. 全文件只有两个随机 v4 UUID 常量 + 一个不相等测试；
2. 平台无关，作为机器人与所有客户端共享的线路契约；
3. 一个服务、一个特征值；该特征值集"读版本/写请求/订阅响应"于一体；
4. 读操作承担"强制先配对"和"版本握手"双重职责；
5. 单特征值双向设计避免了跨特征值按地址猜测配对事件。

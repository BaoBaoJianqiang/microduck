## 从 runtime 移植（审计 §03）

一个 16 状态机——Chill、LookAround、Wander、TurnInPlace、Zoomies、Startle、Stretch、Ruffle、Preen、Sneeze、Dance、GroundPick、Nap、BallPlay、Petted、Held——构建于：

- 驱动状态选择的**能量/情绪模型**
- 用于 Wander 的**新奇度网格探索记忆**
- 带新鲜度门控的 **ToF 避障**
- 基于对比度的**惊吓（startle）**；带自音频/自运动门控的**声音反应**（噪音 vs 人声）
- **玩球**（接近/对准/踢）、**小睡周期**、**抚摸反应**
- 进行中的手柄↔自主切换（DpadRight 2 s）、`--autonomous-max-speed`

它的输入现在都已存在于 daemon 中：环境声音事件（步骤 2——已记录，无消费者）、深度帧（步骤 3）、分类后的躯干帧障碍点（步骤 5），以及语音标签（步骤 2，"已就绪，等待大脑步骤"）。`Held` 依赖于拾取检测，该检测已废弃——决定是恢复它还是丢弃该状态。

## 大脑免费获得的新输入（2026-08 工作）

theremin/chorale 步骤构建的、runtime 的大脑从未有过的东西：

- **按稳定 id 识别附近的鸭子**——chorale 信标（`ChoraleBeacon`），能在 BLE 地址轮换中存活（见 `docs/../memory`：永远不要以地址为键）
- 无需时钟同步的**共享节拍**（`sounds::chorale::beat`）——鸭子间 ±20 ms
- **每个广播包的 RSSI**——免费的粗略距离（近/远/接近中）
- 扩展广播负载中约 **245 字节空闲**
- **实时合成语音**（`sounds::Stream`）：运行时的音高/音量/元音，而不仅仅是音频库 wav
- **来自 ToF 的手距离**（`kinematics::hand::Tracker`）

## 行为想法，大致按每行魅力值排序

**社交（BLE 存在——新领域）：**

- **识别与问候**——保存一份已遇到的鸭子 id 的持久化列表；对陌生人 `greet`，对朋友发出更温暖的声音，当朋友的信标变陈旧时 `peck`/叹息。友谊作为一个见面次数计数器，随时间改变问候方式。读起来像*记忆*；无需同步。
- **孤独/满足**——独处的鸭子偶尔叫唤；有伴的鸭子不会。是情绪模型的输入，而非一个状态。
- **接近时的兴奋**——已知 id 的 RSSI 上升→可见的期待表现。
- **马可波罗**——一只鸭子藏起来，另一只通过 RSSI 增长时叫得更快来引导你。
- **跟随领头者**——RSSI 保持间距，ToF 处理正前方的鸭子。
- **喝彩/社交反馈**——一只鸭子做一个滚音（roulade），附近的鸭子做出反应。
- **传电话**——一条消息通过空闲负载在鸭子间跳跃传递，并发生变异。
- **投票**——信标负载中的偏好；多数决定群体的下一个行为。

**节拍同步运动（在能体现的地方兑现同步工作的成果——不涉及扬声器）：**

- **群体点头/摇摆**——所有鸭子在共享节拍上同相；视觉同步可容忍约 50 ms，而音频需要 20 ms。小节强拍时的群体姿势。康加舞队列。
- **Dance**（已是 runtime 状态）在有同伴时变成*同步*舞蹈。

**音乐，超越 chorale：**

- **呼唤与应答**——对唱乐句；乐句之间的间隙掩盖了同步误差，因此比 chorale*更容易*且更像鸭子。
- **轮唱**——相同旋律，刻意的多小节偏移；偏移吸收了误差。
- **每只一个角色**——持续低音 + 节奏啄击 + 旋律。小扬声器做织体比做和声更好。

## 鸭子检测器（摄像头 + NPU）——需要，等待 mediad

一个针对*我们自己的鸭子*的微型单类检测器：用于注视和跟随的精确**方位角**，这是 ToF 和 BLE 都给不了的。RK3566 有一个 0.8 TOPS INT8 NPU（`rknpu2` / `rknn-toolkit2`）；320 输入的 YOLOv8n/11n 级模型应能在约 20–40 ms 内运行→15–30 Hz，不占用 CPU。距离计算：IMX219 约 62° 水平视场角，25 cm 的鸭子在 3 m 处约 25 px——房间尺度，即交互范围。

- **先查门控：**板上有 NPU 驱动吗？（`dmesg | grep -i rknpu`）——厂商内核 `rknpu2`，不是主线。以及 `/dev/rga` 用于免费 NV12 缩放。让 mediad 从 ISP 主路径 tee 原始 NV12；检测器绝不能解码流式 MJPEG。
- **数据才是项目，不是模型。** 鸭子视角素材（机器人高度、机器人摄像头）由大型开放词汇模型自动标注，蒸馏到微型模型；用 Open Duck CAD 的合成渲染补充尾部；困难负样本（橡皮鸭、白色印花）。
- **融合：**视觉无法区分相同的鸭子——摄像头=方向，ToF=距离，BLE 信标=身份+存在。跟随领头者三者都用；"做事时互相看着对方"=信标说*何时*，检测器说*何地*，`robot.look` 完成其余部分。
- 与 `tofd`/`pet-detect` 相同的架构：`robotd` 之外的感知 worker，可安全杀死。在 mediad 移植期间修复占位的 IMX219 内参（审计 §04 TODO）。

## 移植的形态注意事项

- 存在、情绪和共享节拍是**一个大脑的输入**，而非它旁边的模式——chorale/theremin 之所以成长为显式模式，是因为没有大脑可以挂载它们；当大脑落地时将它们折叠为状态/输入（"Petted" 之于 pet-detect，正如 "Sing" 之于听到的信标）。
- **chorale 最终成为自发事件，而非命令。** `robotctl chorale` 是实验台脚手架：一旦鸭子自主运行，一群在一起的鸭子应该*有时*自发开始唱歌——一个低随机概率，以有同伴在场为门控（可能还以情绪/能量为门控），就像 Zoomies 或 Dance 触发那样，而不是用户启动的东西。刻意稀有：意外的二重唱是惊喜，点唱机不是。机制几乎不变——一只空闲信标的鸭子已经知道谁在附近，所以"决定唱歌"只是多一个转换；`[chorale] accept` 保留为同意门控，决定一只鸭子是否可以加入。
- chorale 的同意规则可以推广：**任何社交功能都是 opt-in，关闭=不可见**（今天是 `[chorale] accept`；明天可能是一个 `[social]` 开关）。
- 识别/问候是正确的*第一个*行为：每行魅力值最高，无需同步，而且它锻炼了 BLE 发现层——这部分仍在硬件怀疑之下。

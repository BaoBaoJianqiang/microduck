# 重启顺序

什么重启，何时重启，以及以什么顺序。

本页面拥有在每次更新时移动 `current` 符号链接的每条路径，以及启动的权威序列。[`updater-design.md`](updater-design.md) 拥有存储、健康门和启动计数器；[`boot-recovery-net.md`](boot-recovery-net.md) 拥有当启动的版本无法启动守护进程时会发生什么。

## 守护进程集

七个守护进程，加上一个不是其中之一的启动检查：

| 守护进程 | 角色 | 在更新时重启？ |
|---|---|---|
| `robotd` | 电机控制 + 机器人 API | 是 |
| `mediad` | 摄像头 + 音频 + WebRTC | 是 |
| `btd` | BLE 网关 | **否**（延迟重启） |
| `configd` | 配置 + wifi + 电源 | 是 |
| `padd` | 板载音频守护进程 | 是 |
| `updaterd` | 更新守护进程 | **否**（延迟重启） |
| `robot-boot-check.service` | 启动恢复检查 | 不适用（一次性） |

`updaterd` 和 `btd` 永不 mid-update 重启。原因：

- **`updaterd`** 是执行更新的进程。在更新期间重启它会杀死更新本身。它在更新完成后五秒延迟重启（见下文）。
- **`btd`** 是手机与机器人通信的通道。在更新期间重启它会断开手机连接，而此时手机正在显示更新进度。它也延迟重启。

### 延迟重启

`updaterd` 和 `btd` 在更新回复后五秒重启。这给了手机时间来接收"更新完成"消息并断开连接，然后 `btd` 才会消失。五秒是猜测的——足够长以让 BLE 通知清空，足够短以让用户不会注意到。

实现方式：`on_apply` 钩子向 `updaterd` 和 `btd` 发送 `systemctl restart --no-block`，延迟五秒。`--no-block` 意味着 systemd 不等待重启完成——它只是排队，然后钩子返回。五秒后，systemd 执行重启。

## `units_to_restart` 从发布中派生

重启的单元集不是硬编码的。它从发布的 `systemd/*.service` 文件派生，跳过任何没有 `[Install]` 段的单元。

规则：

1. 读取发布中的 `systemd/` 目录
2. 对于每个 `.service` 文件，检查它是否有 `[Install]` 段
3. 如果有，将其添加到 `units_to_restart`
4. 始终排除 `updaterd.service` 和 `btd.service`（它们延迟重启）

这意味着一个添加了新守护进程的发布会自动重启它——无需维护名称列表。一个没有 `[Install]` 段的单元（如一次性服务或模板）不会被重启，因为它不应该持续运行。

`mediad` 就是这样获得其条目的：`mediad.service` 有 `[Install]` 段，因此它在派生集中。一个从未运行过 `mediad` 的机器人会在下次安装时启用它——规则是单元文件，而不是任何人维护的名称。

## `apply` 的 18 步序列

更新应用程序按此顺序执行 18 个步骤。每一步都是原子的——如果任何一步失败，更新会回滚到之前的版本。

```
1.  preflight 检查（磁盘空间、签名、兼容性）
2.  下载 artifact
3.  验证签名 + hash
4.  解压到 staging 目录
5.  运行 pre-install 钩子（最长 10 分钟）
6.  原子 symlink swap：current → 新版本
7.  运行 post-install 钩子（最长 2 分钟）
8.  启用新单元（systemctl enable）
9.  重启 units_to_restart 中的单元
10. 延迟重启 updaterd + btd（5秒后）
11. 健康门：等待健康探测通过（最长 30 秒）
12. 如果健康失败 → 回滚到 previous
13. 如果健康通过 → 提交更新
14. 记录更新日志
15. 修剪旧版本（保留 keep_previous 个）
16. 刷新 golden 符号链接
17. 清除启动计数器面包屑
18. 完成
```

### 为什么是这个顺序

- **pre-install 在 swap 之前**：旧版本仍在运行，因此长时间的 pre-install 是缓慢的更新，而不是处于不明状态的机器人。
- **swap 在 post-install 之前**：post-install 钩子可能需要新版本的文件。
- **单元重启在健康门之前**：健康门检查的是新版本的守护进程是否健康，因此它们必须先重启。
- **updaterd/btd 延迟重启**：它们在更新回复后重启，因此手机有时间断开连接。
- **健康门在提交之前**：如果新版本不健康，回滚是自动的。
- **修剪在提交之后**：只有在更新成功后才删除旧版本。

## 启动时协调

当 `updaterd` 启动时，它会检查运行中的单元是否与 `current` 指向的版本匹配。如果不匹配，它会协调它们。

### `reconcile_running_units`

在启动时运行：

1. 读取 `current` 符号链接 → 已安装的版本
2. 读取 `units_to_restart`（从该版本的 `systemd/` 派生）
3. 对于每个单元：
   - 如果它正在运行旧版本 → 重启它
   - 如果它应该运行但没有运行 → 启动它
   - 如果它不应该运行但正在运行 → 停止它
4. 对于 `updaterd` 和 `btd`：检查它们是否需要延迟重启（如果上次更新设置了面包屑但还没有重启）

这处理了更新被中断的情况——例如，如果电源在 symlink swap 之后但在单元重启之前断电。当板重新启动时，`current` 指向新版本，但守护进程仍在运行旧版本（或根本没有运行）。协调修复了这个问题。

### 被操作员停止的单元保持停止

如果操作员用 `systemctl stop robotd` 停止了一个单元，协调不会重新启动它。它检查单元的 `ActiveState`：如果是 `inactive` 且没有 `NRestarts`，它假定是操作员故意停止的，并置之不理。

这与启动恢复网络做出的判断相同——一个被停止的单元不是一个失败的版本，回退它会比什么都不做更糟。

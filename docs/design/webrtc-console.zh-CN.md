# WebRTC 控制台

从一个测试页面到一个机器人控制台。

本页面拥有 `mediad` 如何提供页面、`duckctl` 如何定位机器人、以及控制台本身如何从一个能查看视频的页面演变为一个能驾驶机器人的页面。[`remote-webrtc.md`](remote-webrtc.md) 拥有会话、信令和控制通道；[`app-path-design.md`](app-path-design.md) 拥有手机应用路径。

## 页面由 `mediad` 提供

页面是一个单文件 HTML，嵌入在二进制文件中，由 `mediad` 在其现有的 axum 服务器上提供。没有安装步骤，没有资产目录，没有 `npm build`。

```
GET /            → 页面（HTML，内联 CSS/JS）
GET /ws          → 信令 WebSocket
```

两个端口，因为它们有不同的用途：

| 端口 | 用途 | 谁访问 |
|---|---|---|
| 8080 | 页面 + 静态资源 | 浏览器，通过 LAN |
| 8443 | 信令 WebSocket | 页面自身，通过 LAN |

分开是因为页面可以从任何地方加载（本地文件、CDN、其他主机），而信令必须到达机器人。将它们放在同一个端口上会迫使页面和信令共享一个来源，这在开发期间是一个障碍——当你在笔记本电脑上编辑 HTML 时，你不想每次都重新打包 `mediad`。

### 嵌入而非安装

`include_str!("console.html")` 在编译时将文件读入二进制文件。这与 `updaterd` 将其单元文件嵌入二进制文件是相同的决定，出于相同的原因：一个通过 `current` 读取的资产会被它存在要幸存的 exactly 那些版本破坏，而一个安装到 `/usr/share` 的资产会在更新时被清理或不被清理。

代价是页面更改需要重新编译 `mediad`。对于 v1 来说这是可以接受的——页面很小，而且 `mediad` 无论如何都在同一个发布中。如果页面变得更大或更频繁地更改，它可以成为自己的组件，由 `updaterd` 作为静态资产发布，并由 `mediad` 从磁盘提供。

## `duckctl`：从广告中定位机器人

控制台需要知道机器人的 IP 地址。有三种方法，按便利性排序：

1. **`duckctl ip`** — 从 BLE 广告中读取 IPv4 地址。无需连接，无需 PIN，无需 wifi 凭据。机器人在其广告数据中广播其 LAN IP；`duckctl` 扫描并打印它。
2. **`duckctl open`** — 与 `ip` 相同，但随后在浏览器中打开 `http://<ip>:8080`。一行命令即可到达控制台。
3. **手动** — 在路由器的 DHCP 租约中查找机器人，或使用 `avahi-browse` 查找 mDNS 名称。

`duckctl ip` 存在是因为前两种方法在没有 BLE 的情况下都不可靠：mDNS 在某些网络上被过滤，DHCP 租约需要访问路由器，而主机名解析在 Windows 上一直很脆弱。BLE 广告是机器人已经在做的事情（`btd` 每 100–150ms 广播一次），因此添加一个 IPv4 字段是免费的，并且它在手机无法加入机器人 wifi 的情况下也能工作——你只需要在 BLE 范围内。

### `duck-btctl` 重命名为 `duckctl`

该工具最初称为 `duck-btctl`，因为它只做 BLE 事情。当它获得 `ip` 和 `open` 时，名称变得不准确——这些不是 BLE 控制命令，它们是定位命令。重命名为 `duckctl` 使其成为通用的机器人 CLI，与 `robotctl`（在机器人本身上运行）分开。

`duckctl` 是一个独立的 crate，不在 `board` 构建中。它在开发机器上运行，交叉编译到 macOS/Windows/Linux，并且不依赖于机器人的 Rust 工具链。

## 控制台：从查看器到控制器

页面演变为三个阶段：

### 阶段 1：视频查看器（已构建）

- 连接到信令 WebSocket
- 协商 WebRTC 会话
- 显示视频 + 音频
- 无控制

这是 [`remote-webrtc.md`](remote-webrtc.md) 中描述的最小会话。它证明了管道工作：摄像头 → GStreamer → webrtcsink → 浏览器。

### 阶段 2：遥测 + 控制台（进行中）

添加两个数据通道：

- **telemetry** — 从 `robotd` 读取：关节角度、IMU、电池、温度、电机电流。单向，机器人→浏览器。
- **console** — 一个 REPL：向 `robotd` 发送命令并查看回复。双向。

控制台是现有 API 的管道——与 `robotctl` 在串行端口上执行的操作相同，但通过 WebRTC 数据通道。没有新的命令，没有新的权限模型。如果 `robotctl` 能做到，控制台就能做到。

### 阶段 3：驾驶 + 姿势（计划中）

添加：

- **drive** — 虚拟摇杆或 WASD，发送 `teleop` 命令。需要序列号（SCTP `maxRetransmits=0` 会重排，因此接收者必须按顺序重新排序）。
- **posture** — 预设姿势按钮：站立、蹲下、躺下、回家。发送 `do posture <name>`。
- **do** — 一个动作库：挥手、点头、旋转。发送 `do <action>`。
- **sound** — 播放内置声音或通过 `mediad` 的音频输入播放 TTS。

这些都不是新的 API——它们是 `robotd` 已经通过其串行端口支持的命令的 UI。控制台是一个前端，而不是一个后端。

## 生产者元数据从 `configd` 填充

控制台需要知道机器人的名称、型号、软件版本和功能。这些都在 `configd` 中：

- `system.name` — 机器人名称
- `system.model` — 硬件型号
- `system.version` — 软件版本
- `system.features` — 支持的功能列表（摄像头、麦克风、NPU 等）

`mediad` 在页面加载时通过其现有的 IPC 从 `configd` 读取这些，并将它们作为 JSON 嵌入到 HTML 中。没有额外的 API 调用，没有额外的往返。

这与 `btd` 在广告中放置名称和版本是相同的模式——消费者不应该为了显示"你正在连接到 X"而连接到 X。

## 安全

控制台在 LAN 上运行，没有认证。这对于 v1 是可以接受的，因为：

- 机器人在家庭/实验室网络上，而不是在公共互联网上
- 控制命令通过 WebRTC 数据通道，而不是通过开放的 HTTP API
- `mediad` 只监听 LAN 接口，不监听 0.0.0.0

如果机器人需要在不可信网络上可访问，控制台将需要：

- 令牌认证（与 `configd` 的 `--allow-user` 相同的模式）
- TLS（信令 WebSocket 上的 wss://）
- 可能通过 `btd` 的 BLE 进行配对，以在首次连接时建立信任

这些都不在 v1 中。

## 什么未被测试

- 控制台在真实浏览器中与真实机器人的端到端测试——目前只在开发机器上用假的 `mediad` 测试过
- 驾驶模式的延迟和抖动——`teleop` 命令需要亚 100ms 的延迟，而 WebRTC 数据通道在 LAN 上应该能做到，但尚未测量
- 多个同时连接——`mediad` 目前一次只支持一个 WebRTC 会话；第二个连接会发生什么未定义

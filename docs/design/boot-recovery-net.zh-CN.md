# 启动恢复网络

当机器人启动的版本无法启动其守护进程时，是什么将其恢复到已知良好的版本。

本页面拥有启动截止时间及其谓词、它监视的单元的成员资格规则、`robot-rescue`、`golden` 符号链接和循环守卫。[`restart-order.md`](restart-order.md) 拥有它所处的序列——包括 `updaterd` 在启动时在哪里读取面包屑——而 [`updater-design.md`](updater-design.md) 拥有存储、健康门和启动计数器。

## 它填补的空白

`updaterd` 在更新期间从不重启自身，因为它是执行更新的进程。三层缩小了这一代价，且三层都在完全启动的板上运行：

- `self_test_updaterd` 在提交之前运行版本自己的 `updaterd --self-test`，因此错误架构的二进制文件、缺失的库或被拒绝的 `updater.toml` 会在旧版本仍在运行时使更新失败；
- 延迟重启将 `updaterd` 和 `btd` 在更新回复后五秒放到新二进制文件上；
- 启动协调检查从继任者的一侧验证这些重启确实发生了。

一个在运行中的板上能启动的二进制文件仍可能在**启动**时失败，此时网络未启动、外设未枚举、单元顺序不同。而且协调检查在*`updaterd` 启动时*运行，因此它预设了一个能启动的 `updaterd`。

最后一点就是这一切存在的全部原因。`BootCounter::record_boot` 从 `Engine::recover_on_start` 内部运行，在 `updaterd` 内部，计数的是 `updaterd` **启动次数**而非字面意义的启动次数——因此一个不启动的 `updaterd` 不被计数，永不砖机保证通过可能成为受害者的那个进程关闭。留在那里，板上磁盘上有一个好版本，有一个武装好的回退试验，但没有任何运行中的东西能对两者采取行动。

启动计数器处理的是*不同的*故障：一个启动并运行但从不报告健康的版本。这个处理的是守护进程根本不起来的版本。

## 组成部分

| | |
|---|---|
| `robot-boot-check.timer` | 在每次启动后 180 秒触发 |
| `robot-boot-check.service` | 一次性服务：询问版本是否起来了，如果没有则移交 |
| `scripts/robot-boot-check` | 谓词。安装在 `/usr/local/sbin/robot-boot-check` |
| `scripts/robot-rescue` | 将 `current` 交换到 golden，记录，重启。`/usr/local/sbin/robot-rescue` |
| `<install_dir>/golden` | 指向具有持续保证的版本的符号链接，由 `updaterd` 发布 |
| `<state_dir>/rescued` | 面包屑：最后一次尝试，以及循环守卫 |

两个脚本都是 `/bin/sh`，并且都由 `scripts/install.sh` 和 `hooks/postinstall` **复制**到 `/usr/local/sbin`——与那些复制而非通过 `current` 读取的单元文件是相同的决定，出于相同的原因。一个作为发布负载中的二进制文件发布的救援工具会被它存在要幸存的 exactly 那些版本破坏：错误架构、缺失共享库、启动时 panic。一个通过 `current` 读取的救援工具会将恢复路由通过正在被恢复的东西。

## 触发器：截止时间，而非 `OnFailure=`

`OnFailure=` 看起来是自然的选择——systemd 在单元耗尽重启并进入 `failed` 时精确触发它，无需轮询无需常驻看门狗。它不适合*这些*单元，这些单元被配置为不会到达该状态：

| 单元 | 策略 | `RestartSec` |
|---|---|---|
| `btd` | `Restart=always` | 5 秒 |
| `padd` | `Restart=always` | 5 秒 |
| `configd` | `Restart=always` | 2 秒 |
| `robotd` | `Restart=always` | 2 秒 |
| `updaterd` | `Restart=on-failure` | — |

`Restart=always` 在每种情况下都是故意的，并在单元文件中有论证。没有单元覆盖 `StartLimitIntervalSec`/`StartLimitBurst`，因此 systemd 默认的十秒内五次启动适用——而一个每 5 秒重启的 `btd` 永远接近不了它。它无限崩溃循环而从不进入 `failed`，而那正是 `OnFailure=` 等待的状态。让 `OnFailure=` 触发意味着重新调整这些单元使守护进程*放弃*：为了启用救援情况而降级正常情况。

截止时间反转了问题，不需要单元更改，并且能捕获永远重启者。`OnBootSec=180` 因为板比看起来慢——`hci0` 在通电后大约 73 秒才存在，其中 `bluetooth.service` 有 26 秒被阻塞在 `dbus` 后面——而守护进程等待它们的硬件而非退出，因此慢启动不是失败的启动。

### 谓词

两个条件，都是 systemd 试图运行守护进程但无法保持其运行的正面证据。任一成员上的任一条件：

- `ActiveState` 是 `failed`；
- `NRestarts` 是 3 或更多。

其他一切都被置之不理，而不对称性正是要点。一个被操作员停止的单元是 `inactive` 且没有重启，绝不能让板失去它的版本——与启动协调在让停止的单元保持停止时做出的相同判断。一个版本早于该单元的单元未被加载且不回答任何东西，读取方式相同。一个仍在等待硬件的守护进程是 `active`。而一次崩溃后恢复留下一两次重启，不是三次。**假阴性让操作员付出一次诊断的代价；假阳性让一个好版本付出代价。**

三次重启而非一次，因为 `Restart=always` 配合 2–5 秒的 `RestartSec` 意味着真正的循环在截止时间内轻松通过三次，而一个在瞬态上死过一次的守护进程不会。

### 它拒绝触发的三种方式

- 一次性服务上的 **`Conflicts=shutdown.target`**。一个在关机途中被杀死的守护进程可能被记录为 `failed`；没有这个，在错误时刻的 `systemctl poweroff` 最终会将机器人重启到 golden。
- **正常运行时间守卫**。超过十分钟，说明是计时器以外的东西启动了它，答案是这个问题不是这个脚本的事。
- 一次性服务上**没有 `[Install]` 段**，两个安装程序都将其读取为"不要启用这个"。没有它，`hooks/postinstall` 对它刚写入的单元运行 `enable --now` 会在安装它的更新中途运行一次回退检查——此时守护进程正当地处于重启中，而这正是回退检查读取为版本无法启动的情况。计时器被启用但从不启动，原因相同：一个 `OnBootSec=` 计时器在超过其截止时间后启动会立即触发。

## 成员资格规则

对"任何守护进程失败→回退"的反对意见是，守护进程可能因回退无法修复的原因而失败——缺失的无线电、未通电的电机总线——而因硬件故障回退一个好版本比什么都不做更糟。

这解决为一个接纳单元进入集合的规则：**一个单元只有在它等待其硬件（缺失或行为异常）而非退出时才可加入。** 那么一个失败的成员意味着*二进制文件*损坏——错误架构、缺失库、启动时 panic、它拒绝的配置——而这正是回退修复的。

| 守护进程 | 在集合中 | 当其依赖缺失时 |
|---|---|---|
| `robotd` | 是 | 等待电机总线，"等待，不指挥任何东西" |
| `updaterd` | 是 | 无论如何服务；它是恢复路径，在东西损坏时必须可达 |
| `btd` | 是 | 每 5 秒重试一次适配器，如果一个出现然后停止回答则重新运行整个启动 |
| `configd` | 是 | 服务 `system.*` 和 `pad.*`，并报告 `net.state=unavailable` |
| `padd` | 否 | 在没有 robotd socket 时干净退出，设计如此 |

`btd` 凭功绩而非对称性赢得其位置：没有网络时，BLE 是唯一的入口，因此一个启动时没有 `btd` 且没有已知 wifi 的机器人根本无法到达。`configd` 以同样方式赢得其位置——`system.pin` 是 `btd` 获取手机认证用的 PIN 的地方，因此一个宕机的 `configd` 会带走手机路径。

如果未来的守护进程在缺失硬件时退出，要么修复守护进程，要么将其排除在集合之外。不要削弱规则。

## 救援

`robot-rescue` 读取两个符号链接且不解析任何东西。

这不是节省。它最可能救援的是一个其 `updaterd` 拒绝板的 `updater.toml` 的版本——操作员的文件，在安装间保留，而版本可以自由改变它期望的东西。一个解析同一个文件的救援工具会死于它正在治疗的疾病。

Golden 是该文件中的一个版本（`ComponentConfig::golden`），因此 `Engine::refresh_golden_links` 在每次 `updaterd` 启动时将其发布为 `current` 旁边的一个 `golden` 符号链接：一次 `readlink`，没有东西可拒绝。它是一个缓存而非第二个真相来源，并且它安全失败——如果 `updaterd` 停止启动，链接仍然命名它上次写入时是 golden 的版本，而那是一个已知良好的版本。一个配置了但*未安装*的 golden 根本不发布链接，因为一个悬空链接会告诉救援它有一个目标而实际上没有。

**Golden，而非 previous：** 当损坏的是恢复路径本身时，previous 可能也损坏了。Golden 是唯一具有持续保证的版本，而 `prune` 从不删除它。

当没有 golden 链接、当 golden 命名一个未安装的版本、以及当 `current` 已经是 golden 时，它拒绝并说明是哪一种。最后一种最重要：此时守护进程在携带持续保证的版本上失败，因此这不是版本故障，交换除了增加一次重启外什么都不会改变——而这正是硬件故障变成重启循环的方式。

交换通过 `rename(2)` 将一个临时符号链接重命名到 `current` 上，与 `Store::link_to` 匹配，因为 `ln -sfn` 会取消链接并重新创建，留下一个守护进程无法 exec 的窗口。`rename(2)` 不跟随符号链接，但 `mv` 的路径解析会，因此普通的 `mv tmp current` 会将链接*移动到* `releases/<version>` 内部并让 `current` 原封不动；GNU 用 `-T` 拼写修复，BSD 用 `-h`。

`--reboot` 是可选的。每个单元通过 `current` exec，因此交换在它们重启之前什么都不做，而一个在其守护进程死亡时正站着的机器人是一个会摔倒的机器人——谁拿着它谁决定。启动检查传递该标志；在控制台上的人得到打印的命令。

## 循环守卫，以及什么打开它

两个独立的东西阻止"交换并重启"自行发生两次：

1. 当 `current` 已经是 golden 时的拒绝，这覆盖了普通情况，因为一次成功的救援恰好留下那个状态；
2. 面包屑，覆盖第一种遗漏的情况——一次更新将 `current` 移离 golden 并再次失败。

`Engine::record_rescue` 在下次 `updaterd` 启动时清除面包屑，在将其复制到更新日志之后。因此守卫恰好在板证明它能再次运行其更新守护进程时打开，并在它不能时保持关闭：一个坐着不动且日志清晰的机器人胜过一个永远重启的机器人。`robot-rescue --force` 是手动越过它的方式。

该清除在**启动计数器之前**运行，而顺序是承重的。一个武装好的试验会回退到 `previous`；救援已经走得更远，到了 golden。如果保持武装，`record_boot` 会推进试验并最终将 `current` 移*离*救援选择的版本——恢复网络和永不砖机保证相互撤销，相隔一次启动。

面包屑是 `key=value` 而非 JSON，尽管 `updaterd` 解析它：

```text
at=1786453421
install_dir=/opt/robot/daemon
from=1.2.0
to=1.0.0
because=boot check: robotd.service (failed, 7 restarts)
```

写入者是一个在已经出问题的板上运行的 shell 脚本，而在 `sh` 中正确引用 JSON 是一种产生没有东西能读取的记录的方式。`journal::Breadcrumb` 出于同样原因是宽松的——每个字段都是可选的——因为一个无法解析的面包屑是一个永远不会打开的守卫。`install_dir` 是条目如何归因于一个组件而无需第二个必须就名称 `daemon` 与 `updater.toml` 达成一致的地方。

## 证据

一次静默回退是一天如何变成"它在我的板上工作"的，因此交换留下三条痕迹：

- **日志**，来自两个脚本，在 `logger` 存在时通过它，始终通过 stderr；
- **更新日志**，作为 `Outcome::RolledBack`，在其原因中命名失败的单元——这正是 `robotctl update log` 显示的，而且它是永久的，不像被清除的面包屑；
- **`robotctl version`**，间接但有用：一个运行比安装的版本更旧的机器人正是它报告的情况。

## 什么未被测试

决定是：`xtask/tests/rescue.rs` 针对一个临时树向两个脚本询问每个问题，用一个存根 `systemctl` 提供单元状态并记录是否要求了重启，而 `scripts/board-test.sh` 在真实的 ARM64 Linux 上覆盖安装程序那一半。

**systemd 没有。** 计时器是否在 `OnBootSec=180` 触发、`Conflicts=shutdown.target` 是否在关机途中保持一次性服务关闭、以及 `NRestarts` 是否在崩溃循环的单元上按谓词假设的方式读取，全部未验证。除了真实的 systemd——`systemd-nspawn`，或以它为 pid 1 的特权容器——没有任何东西能回答其中任何一个，而 [`install-path-gap.md`](../project/install-path-gap.md) 是为此存在的案例所在的地方。这是它的第二个论据：恢复网络是必须在其他一切都不工作时工作的代码，也是最不适合测试的代码。

在那之前，这个机制要么在台架板上验证，要么根本不验证，而做到这一点的方法是给板一个其 `robotd` 无法启动的版本。

它没有任何一部分在硬件上运行过，在那里有趣的路径需要一个其版本无法启动的板。

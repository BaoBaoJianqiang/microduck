# 应用路径 —— `btd` 与 `configd`

状态：草稿 · 日期：2026-08-04 · 负责人：pierre

手机如何配置机器人：wifi、名称、重启、版本以及触发更新。

[`architecture.md`](architecture.md) 的姊妹篇，后者负责服务拆分与跨切面契约。本文覆盖一同落地的两个服务，因为**它们是一个特性**，且其中每一个决策都约束着另一个：`btd` 不拥有任何东西，于是才有 `configd`；`configd` 提供 PIN，于是 `btd` 才能配对；在 `btd` 中路由的方法，正是 `configd` 必须应答的方法。

标有 **measured** 的章节是在 Radxa Zero 3W 上实测建立的，而非推理得出。

**该路径已在硬件上端到端跑通**（2026-08-05）：一台 Mac 发现了机器人、绑定、读取 API 版本、传入 PIN，并收到了真实的 `system.info` —— GATT 发现、双向分块 NDJSON、PIN 闸门、路由表以及经由 unix socket 跳入 `configd`。`configd` 同样对真实的 NetworkManager 作出应答，上报实时的 SSID 与地址。

尚**不成立**的事：链路不携带加密（§5.5），`net.connect` 尚未经 BLE 驱动过，也尚未用手机而非笔记本测试过任何东西。

## 1. 形态

```
        phone ──BLE──▸ btd ──┐
     robotctl ──unix socket──┼──▸ configd ──D-Bus──▸ NetworkManager   (wifi)
    (mediad) ──WebSocket────┘                    └──▸ logind          (reboot)
                             │                    └──▸ config file     (name, PIN)
                             └──▸ updaterd  (update.*)
                             └──▸ robotd    (robot.health)
```

来自 `architecture.md` 的两条规则产生了这一形态，其余无自由可变：

- **§4.1：`btd` 不拥有任何东西。** 如果配置或初始化存在于 BLE 服务中，每个其他服务都会依赖它，而 SDK 荒谬地必须经由蓝牙来设置机器人的名称。
- **§3.1：当 `robotd` 死亡时配置必须仍可访问。** 初始化 wifi 正是机器人损坏时有人需要做的事，因此配置不能存活于控制守护进程中。

在两者之间，没有剩余的服务可以放置 `net.*` 与 `system.*`，于是有了第五个服务。

**这项工作大部分不是蓝牙。** API 面与拥有它的服务，被手机 app、SDK、`robotctl` 以及 `mediad` 的远程网关以完全相同的方式需要。`btd` 只是其上的一根细管道 —— 而验证这一说法的方式是：添加七个 `net.*`/`system.*` 方法，每个方法只让 `btd` 在路由表中增加一行。

## 2. Wifi：NetworkManager，以及为什么板子必须迁移到它 · **measured**

`architecture.md` §3 选择了 NetworkManager。板子上没有它。

Armbian 的无桌面镜像运行 netplan + `systemd-networkd` + `wpa_supplicant`。板子上的三个发现让该选择再次被做出，而非继承：

- **启用 D-Bus 的 `wpa_supplicant` 不持有任何接口。** `fi.w1.wpa_supplicant1` 被声明并处于空闲（`Interfaces` 是空数组）；netplan 运行*第二个*、经 `-c` 配置的 supplicant，它拥有 `wlan0` 且完全没有 D-Bus。因此直接驱动 `wpa_supplicant` 无论如何都意味着取代 netplan —— 且没有 NM 的任何失败上报。
- **netplan 无法上报手机需要的内容。** 它是一个配置*生成器*：任何层都没有扫描 API，且 `netplan apply` 返回"配置已应用"而非关联是否成功。"给我看看网络"与"密码错了"是初始化流程最需要的两样东西，而它两样都不回答。
- **`RequiredForOnline=no` 让启动更糟，而非更好。** Armbian 自带一个 drop-in，将 `systemd-networkd-wait-online` 变成 `--any`：当*任一* networkd 链路变为在线时即成功。一旦 wifi 归 NM 所有，networkd 的唯一链路是通常无网线的以太网口，于是 `--any` 永远无法被满足。将该链路标记为非必需移除了唯一的候选，并保证了失败。屏蔽该单元是修复；`NetworkManager-wait-online` 才是诚实的闸门。

`scripts/migrate-network.sh` 执行一次迁移，且在它把板子现有的凭据复制到 NM profile 之前拒绝切换 —— 否则无桌面板子会下线且无法回来。它会武装一个启动时的回退机制：若 `wlan0` 在 90 秒后仍无地址，则恢复 netplan 并重启，这是把更新系统的启动计数器思路应用到网络变更上。

### 2.1 `BadKey` 是全部意义所在

`ConnectFailure::BadKey` 正是 NM 值得迁移的原因。被拒绝的密码是最常见的初始化失败，而一个无法说明这一点的客户端会让用户无所适从。NM 将其报告为设备状态原因 7；`configd` 将 NM 的原因映射为 `BadKey`、`NotFound`、`Timeout`、`Unsupported` 与 `Other`，且一个未映射的原因绝不能变成 `BadKey` —— 否则会让人陷入循环，反复重输入一个原本正确的密钥。

`configd` 在 `AddAndActivateConnection` 之后轮询 NM，而非在激活*开始*时返回，因为"配置已应用"正是 netplan 给出的答案，也是我们拒绝的答案。

### 2.2 初始化新网络，这正是整条路径的意义

为 BLE 提供正当性的场景：一块板子来到新地方，它已知的 wifi 不在那里，网络上没有任何东西能触达它。三个属性使之可行，只有第三个需要修复。

- **守护进程不等待网络。** `btd` 为 `After=dbus.service bluetooth.service`，`configd` 为 `After=NetworkManager.service`，两者都不随 `network-online.target`。一块没有可达 AP 的板子仍会启动并提供 BLE。
- **已初始化的 profile 可在重启后存活。** `AddAndActivateConnection` 留下一个已保存的 profile，`autoconnect` 默认为开启，因此重新加入是 NM 的事，`configd` 完全不参与重连循环。
- **扫描等待扫描完成。** · **measured** `RequestScan` 在 NM *接受*请求时返回，而非在无线电扫过信道时返回，且 NM 会剪除其最近未见的接入点 —— 因此在已关联时，缓存列表往往除了机器人已经连接的 AP 外什么也没有。立即读取它得到的是*上一次*扫描：第一次调用只有一个网络，完全相同的第二次调用有八个。`configd` 现在等待 `LastScan` 属性推进，上限 10 秒，并将被限流的请求视为"缓存已经是新鲜的"而非错误。对于一个全部职责就是在陌生地方选择网络的客户端来说，"问两次"不是一个值得交付的契约。
- **结果从激活而非设备读取。** · **measured** 这条路径上最严重的 bug。`connect` 轮询*设备*状态，而设备在新激活在其旁失败的同时，仍在它已经使用的网络上保持 `ACTIVATED` —— 因此针对一个甚至不在范围内的网络调用 `connect("Tehaupoo", psk: "lol")`，返回了 `{"outcome":"connected","ssid":"SFR-e994"}`，报的是机器人一直连着的网络。为一次从未发生的加入报告成功，是可获得的最坏答案：手机断定机器人已初始化完毕，然后继续下一步。

  现在改为轮询 `AddAndActivateConnection` 返回的活动连接对象，上报的是被请求的 SSID 而非 `status` 所说的任何东西，无线电看不见的 SSID 被预先拒绝为 `NotFound`，而失败的激活会删除 NM 添加的 profile —— 否则 autoconnect 会永远重试一个已知错误的密钥，`net.status` 也会声称该网络是 `saved`。

  隐藏 SSID 也被该预检拒绝。加入一个隐藏网络需要 `802-11-wireless.hidden` 和一个能说"这个是隐藏的"的客户端，而 API 尚无相应形态。
- **重新初始化是替换，而非累积。** · **measured** `AddAndActivateConnection` 总是添加，而 NM 容忍两个承载相同 id 的 profile。因此普通路径 —— 在手机上输错密码、`BadKey`、然后输入正确的 —— 会让机器人保留两者，且无法保证下次重启后 NM 会用哪个 autoconnect。`net.forget` 通过移除两者之一并报告成功，使情况更糟。现在某个 SSID 的已保存 profile 被作为一个*集合*枚举并在连接前删除，`net.forget` 则删除所有。

  在添加前而非添加后删除，因为替代方案只要添加成功而清理失败就会留下重复。如果添加随后失败，该 SSID 就没有 profile，对于一个正在被替换的配置来说这是诚实的结果，并会上报给客户端。

  注意：当被替换的 profile 是活动的那个时，这会断开机器人。不可避免 —— 更改密钥意味着重新关联 —— 而 BLE 上的客户端不受影响，这正是整个设计所赖以成立的属性。

## 3. GATT 面：一根管道，而非一个 API

一个服务，**一个特征值**。客户端读取一次以获取机器人的 API 版本，向其写入 NDJSON 请求字节，并订阅它以获取应答 —— 与每个其他传输所承载的相同的 JSON-RPC 行。读取不是可选的；为何存在见 §5。

**它返回的版本是用于说明这一点，而非用于拒绝。** `API_VERSION` 说明两个对端不是一起构建的；它不说明哪些调用会停止工作，且在这条链路上通常没有任何调用会停止。其上的任何东西都不检查这个数字 —— `configd` 不以版本为门槛限制任何 `net.*` 或 `system.*` 调用，`updaterd` 在 `update.status` 之前不要求握手，`updaterd` 的 `hello` 也不再因它而拒绝。因此一个因偏差而拒绝的客户端会拒绝机器人本会应答的调用 —— 而它是在为一个没有网络的机器人存在的传输上拒绝这些调用，而 `net.connect` 正是走出偏差的方法。`duckctl` 会警告并继续，app 也应如此：暴露不匹配、让调用继续，并在真正到达一个形态已变的方法时上报 JSON-RPC 错误。这些错误会自我命名 —— `METHOD_NOT_FOUND` 表示此版本没有的路由，`INVALID_PARAMS` 表示它不认识的参数 —— 这正是让继续安全而非仅仅乐观的原因。

**无分帧头。** 已经分隔 NDJSON 消息的换行符就是双向的帧定界符。这是安全而非侥幸：`serde_json` 会把字符串中的换行符转义为 `\n`，因此原始的 `0x0A` 永远不会出现在序列化的对象内部 —— 这正是使 NDJSON 在 unix socket 上工作的同一属性。长度前缀会是一种 BLE 专属方言，每个客户端都得实现；相反，手机做 `robotctl` 所做的事：写字节、读到换行为止。

重组上限为 8 KiB，因为该缓冲区对无线电范围内的任何人都可达。

**替代方案，以及为何不采用：**

| | 为何不采用 |
|---|---|
| 按字段的特征值（name、ssid、ip、connect…） | 在通用 BLE app 中可浏览，但这是同一 API 的第二种方言：每个字段变成一个 UUID 加上 `btd` 代码，而 `net.scan`（一个列表）与 `update.subscribe`（一个流）难以适配 |
| 两个特征值，写与通知 | 常规形态，且最初就是这样写的。BlueZ 将一次写入与一次订阅报告为*分离的事件*，因此两个特征值必须按设备地址匹配它们 —— 猜测一种本由一个特征值凭构造获得的关联 |

一个特征值的代价是它在 nRF Connect 中读起来奇怪，同一行既是写又是通知。

### 3.1 被路由的子集就是安全边界

BLE 暴露一个子集（§4.1）。`btd/src/route.rs` 中的一张表决定一个调用是否被允许、由*哪个 socket* 应答、以及到该 socket 的*哪个连接*承载它。前两个是同一个问题 —— 一个调用仅当表为其命名了一个服务时才被允许 —— 第三个也在同一张表中，因此一个新方法无法在不应答它的情况下被添加（§3.5）。

**对 `Call` 的匹配故意是穷尽的。** 添加一个协议方法会让 `btd` 的构建失败，直到有人对其做出决定。一个 `_ => None` 通配符在当时会是安全的默认值，但随时间会是错的 —— 它会静默地拒绝新方法，而第一个症状会是手机 app 缺少一个没人记得路由的特性。这已经回本过一次：七个 `net.*`/`system.*` 方法打破了构建，`updaterd` 的等价匹配也是如此。

被拒绝，各有原因：

| 被拒绝 | 原因 |
|---|---|
| `update.pin` | 一个被误触锁定的机器人会拒绝之后的每一次更新并自称是最新的 —— 这是这里唯一一个看起来像正确行为的失败。`robotctl`，以及一个有意为之的人 |
| `update.resetToGolden` | 名义上是恢复出厂设置。绝不能经由无线电 |
| `robot.safeToRestart`、`robot.modelApi`、`robot.remoteSessionActive` | `updaterd` 对 `robotd` 的私有询问；手机读取它们学不到任何可据此行动的东西 |
| `system.pairingPin`、`system.setPairingPin` | **承重的那个。** 一个未配对对端能读取 —— 或覆写 —— 的 passkey 会让配对沦为作秀。`btd` 改为通过 unix socket 读取 |

**`update.rollback` 与 `update.select` 曾在该列表上，现在不在了。** 它们被拒绝的理由是引擎会自行回滚坏版本，它确实如此 —— 那个未通过健康门的版本。但那不是所有者拿起手机要处理的情况，那个情况是：一个版本安装成功、通过健康门、然后行为*更糟*：一个走路不稳的策略而非完全不能走，一个停止重连的 pad。除了人之外没有东西能回滚它，而那个人正拿着手机且没有 ssh。两者都会移到一个已在本板运行过的版本，不下载任何东西，且像任何其他转换一样被门控并自动回滚。`update.apply` 早已被路由，且是三者中更具后果的一个，因此这几乎不扩大无线电范围内对端的能力范围。`docs/project/update-over-ble.md` §2.4 是该决策及其权衡。

## 4. 授权：两层，分开

| 层 | 机制 | 决定 |
|---|---|---|
| 1 | socket 模式 `0660`，组 `robot` | 谁可以**连接并通话** |
| 2 | `allow_users` / `--allow-user` | 谁可以发起**变更性**调用 |

只读调用完全跳过第 2 层，因此技术支持可以检查一个它不得更改的机器人。

两层是因为 `btd` 必须在 `robot` 组中才能到达 sockets，而处于该组中绝不等于"可以替换固件"。因此两个服务都把更改权限授予**具名服务** —— `updater.toml` 中的 `allow_users = ["btd"]`，`configd.service` 中的 `--allow-user btd` —— 且两者都有一个测试拒绝将 `robot` 作为组。

**按名，绝不按 uid。** `systemd-sysusers` 动态分配，因此写入随附配置中的一个数字在写入它的板子上是正确的，在下一块板子上就是错的。名称在启动时解析；无法解析的名称会警告而非中止，因为缺少一个可选服务的机器人仍须提供状态。

`SO_PEERCRED` 只报告对端的**主** gid，这就是这里的陷阱：`SupplementaryGroups=` 让一个进程通过 socket 模式，再无其他。漏掉这点正是让每个经由 BLE 的变更性调用都返回 `PERMISSION_DENIED` 而一切只读调用正常工作的原因 —— 这是 bug 最坏的形态，因为它读起来像个谜团而非配置错误。

### 4.1 权限，以及解析器的位置

`btd` 无特权；`configd` 以 root 运行。这看起来反了，其实没有。

`btd` 是解析来自无线电范围内任何人字节的进程。`configd` 只看到经由对端凭据本地 socket 到达的带类型的 JSON。**把解析器放在该边界的安全侧，比加固分发器更重要。**

`configd` 需要 root 有一个狭隘的原因：NM 的 connection-modify 与 logind 的 `Reboot` 都被 polkit 门控，本镜像上**没有 polkit**，而 systemd 对无会话的非 root 调用者都拒绝。替代方案是安装一个 JS 策略引擎来授权两个调用。与 `robotd` 不同，它不接触任何硬件，因此其 unit 对它做了正确的沙箱化 —— `ProtectSystem=strict`、一个可写路径、仅 `AF_UNIX`、空的 `CapabilityBoundingSet`。`CAP_SYS_BOOT` 被故意缺失：logind 执行重启而 `configd` 只是请求，因此那里的一个能力会允许本设计要避免的不洁 `reboot(2)`。

如果哪天 polkit 因其他原因到来，`configd` 应降为一个专用用户加两条规则。

### 3.2 每个订阅一个会话，以及决定这一点的那个 bug · **measured**

`btd` 维护一个会话 —— 一个重组缓冲区、一个出站队列、一个授权状态 —— 问题是它活多久。第一个答案是"与服务同寿命"，因为 BlueZ 的回调模型给订阅的没有对端身份，且每个特征值只持有*一个*通知状态，因此按对端会话看起来像是为一种不会发生的情况准备的机器。一个过期的部分行看起来最多代价是一个坏请求。

它反而让*下一个*客户端付出代价，这更糟，且在板子上出现三个症状才看出：

| 症状 | 原因 |
|---|---|
| 一个请求得到应答，然后下一个超时 | 出站接收器被第一次泵出共享槽，于是第二个订阅没有泵：应答被写到一个无人读取的通道 |
| `":0,"result":{"authenticated":true}}` —— 一个开头缺失的应答 | 那些孤立的块通过后来的通知器浮现 |
| `no robot found`，然后同一命令又能工作 | 无关：客户端扫描在固定 sleep 后取一个快照，因此广告是否落在该窗口内是运气 |

只有第三个是客户端 bug。前两个是同一个缺陷：**比其所属对端活得更久的状态。** 在此模型中断开是不可见的，因此没有东西重置它。

于是会话在中心订阅时创建，在其离开时丢弃 —— 重组器与队列随之而去，而重连的手机从未认证状态开始，这正是 §5.2 已经声称的行为。两个细节是承重的而非附带的，且最初都错了：

- 泵同时等待 `notifier.stopped()` 与队列。仅从一次失败的通知得知离开需要有一个应答要发，因此一个空闲时断开的客户端会一直占着槽，直到有一个给无人的请求到达。
- 销毁仅在槽仍持有*它自己的*发送者时才清空它。向一个已消失的中心发送通知需要 BlueZ 放弃所花的时间，届时重连的中心可能已经安装了一个更新的会话，而盲目清空会杀死它。

写入路径仍拒绝没有活动订阅的写入。接受一个会是谎言：无处发送应答。

### 3.3 移动 app 会撞到的一件事：不要带服务过滤扫描 · **measured**

`duckctl` 是一个测试工具，且有意仅此而已 —— 真正的客户端是手机 app。但它的一个 bug 是 CoreBluetooth 的属性而非该工具的属性，因此值得在有人在 iOS 上重新发现它之前写下来。

`btd` 广播服务 UUID 与主机名。带服务过滤扫描仍只*有时*找到机器人：**CoreBluetooth 严格遵守过滤，而一个已绑定的外设频繁以空服务列表广播。** 过滤后，它就完全不被报告 —— 不是"无服务被报告"，而是缺席。这表现为一次运行 `no robot found`、下一次成功，期间什么都没改，且它在第一次修复后仍然存在，因为基于名称的回退只能匹配过滤扫描已经返回的外设。

app 应无过滤扫描并自行辨别候选，最强证据优先：广播的 UUID，然后是已知名称或已存储的外设标识符，并将"服务于我们的特征值"视为唯一权威的身份测试 —— 它仅在连接后才可得知。iOS app 比 `duckctl` 有更好的第三层，`retrievePeripherals(withIdentifiers:)`，`btleplug` 不暴露它；在第一次成功连接后存储标识符是那里的正确做法，且完全消除了猜测。

也值得知道：在固定 sleep 后取一个单一快照是不够的。广播是周期性的，适配器对已绑定外设的看法时有时无，因此轮询直到候选出现。

### 3.4 机器人必须足够频繁地广播以被捕获 · **measured**

`duckctl` 在大约一半的运行中报告 `no robot found`，有一段时间这被读为工具的不稳定 —— 或归因于手柄，其 LE 链路共享无线电。两者都不是。`btd` 注册其广播时没有指定间隔，因此 BlueZ 使用内核的默认 **1.28 秒**，而一个以低占空比扫描的中心无法可靠地捕获一个 1.28 秒的广播者。

从一台连续扫描两分钟的 Mac 测量，按设备统计到达数：

| 设备 | 信号 | 120 秒内到达数 |
|---|---|---|
| 智能插座 | −66 dBm | 130 |
| 信标 | −91 dBm | 159 |
| 机器人 | **−36 dBm** | **16** |

机器人是房间里信号最强的，却比其中任何其他东西少听到一个数量级，因此距离、干扰与客户端都被排除而非争论。它平均每 7.5 秒到达一次，有 9 秒、14 秒、17 秒及一次 31 秒的静默；大间隙以接近 1.28 秒的整数倍出现，这正是从到达数中识别出间隔的方式。落在这些静默之一中的八秒扫描什么也找不到。

对 app 有两点推论。

**手机不会因为是手机就逃脱这个问题。** 第一次连接是一次扫描，因此引导会撞到同样的静默 —— 而那是机器人必须可被找到的时刻。§3.3 的 `retrievePeripherals(withIdentifiers:)` 带来的好处比看起来窄：已存储的标识符让 iOS 可以*不*经过新的目击就连接，因此重连退化为延迟而非失败。它对第一次连接毫无作用，而那是最重要的一次。

**广播间隔是机器人的属性，因此是 `btd` 的职责**：100-150 ms，是默认的 8-12 倍，这正是普通外设使用的值。不是规范允许的 20 ms —— 一根天线承载着这个、手柄的 LE 链路与 wifi，而花在喊叫上的空中时间来自机器人的本职用途。

`duckctl/examples/advwatch.rs` 是该测量，保留它是因为该断言只能通过重新运行它来检验：按设备的到达数与信号强度，然后是机器人的静默。

**已在板子上确认。** 安装 100-150 ms 后，同一台 Mac 的同样两分钟观察：

| | 120 秒内到达数 | 平均间隔 | 最坏静默 | ≥ 8 秒的静默 |
|---|---|---|---|---|
| 1.28 秒，默认 | 16 | 7.5 秒 | 30.8 秒 | 7 |
| 100-150 ms | 151 | 0.8 秒 | 3.8 秒 | **0** |

九倍频繁，且 —— 重要的部分 —— 没有任何东西留在 `duckctl` 八秒窗口的两倍以内，因此它被诊断出的那个失败不可能再发生。机器人从听到的 106 个设备中的第 34 位升至 74 个中的第 7 位。

### 3.5 每条泳道一个连接，因为守护进程一次服务一个请求

`btd` 按需打开到 `updaterd`、`robotd` 与 `configd` 的 socket 并为会话保留它们（`btd/src/upstream.rs`）。它曾每个服务保留**一个**，而其后的两个守护进程对一个连接一次服务一个请求：读一行、等待整个调用、然后读下一行（`updater/src/ipc.rs::handle_connection`、`configd/src/main.rs::handle`）。因此会话上的每个调用都排在该队列上最慢的东西之后，而 app 最先会用的两种排序都因此被破坏：

| 客户端做的事 | 发生的事 |
|---|---|
| `update.apply`，然后在其运行时 `update.status` | status 行在一个 `updaterd` 数分钟不会读取的 socket 中等待。客户端在一无所闻中超时，而机器人好好的在更新 |
| `update.subscribe`，然后 `update.apply` | 更糟。`stream_progress` 一直持有其连接直到对端离开且从不读取另一个请求，因此 apply 被写到一个无人读取的 socket：它从不运行、从不应答、从不报错 |

第二个是值得记住的那个。所有者点击"更新"，机器人什么都不做，且各处都找不到错误 —— 请求正躺在一个 socket 缓冲区中。

因此调用按**持有连接多久**分组，每组获得自己的连接。泳道在 `route.rs` 中与权限和服务一起决定（§3.1），这正是让穷尽匹配也覆盖它的原因：一个新的长运行方法无法在无人选择的情况下被添加。

| 泳道 | 持有其连接的时长 | 调用 |
|---|---|---|
| `Prompt` | 一次查询那么久 | `hello`、`update.status`、`update.log`、`update.listInstalled`、`robot.health`、`net.status`、`net.forget`、`system.*`、`pad.status`、`pad.forget` |
| `Slow` | 数秒 —— 网络或无线电扫频 | `update.check`、`net.scan` |
| `Operation` | 所需那么久，且更改机器人 | `update.apply`、`update.rollback`、`update.select`、`net.connect`、`pad.pair` |
| `Stream` | 永远，且不应答任何东西 | `update.subscribe` |

共享一条泳道就是排队，且每个分组都是排队为正确答案的情况：`updaterd` 在文件锁后单飞变更并对第二个返回 `BUSY`，而在 `configd` 上同时进行两个无线电操作不是值得想要的事。`update.check` 被故意*不*放在 `Operation` 泳道 —— 在更新期间被问到时它有即时答案，而把它排队会把 `BUSY` 变成一个数分钟后才解决的转圈。

每个服务每个会话最多四个 socket，实际上是两个。每个调用一个连接会是更整洁的模型，但需要 `btd` 知道一个调用何时结束，这需要它解析应答 —— 它从不这么做（§3），而正是这一属性让被路由的子集保持为一个传输而非 API 的第二个实现。

## 5. 配对：just-works，以及一个传输检查的 PIN

一个六位 PIN，由 `configd` 存储，由 `btd` 在服务任何东西之前检查。**不是**由蓝牙绑定检查 —— 而这是规范强制的，而非选择。

### 5.1 为何 BLE 无法承载一个印在机器人上的 PIN · **measured**

第一个设计是让机器人用其存储的 PIN 应答 BlueZ 的 passkey 请求。在硬件上，macOS 显示*它自己的*随机六位代码并等待有人把它输入机器人。

在 LE passkey entry 中，一方**显示**一个 passkey，另一方**输入**它，角色遵循每方声明的 IO 能力。实现 `request_passkey` 声明"本设备可以输入"，因此 macOS 承担显示角色。一个没有键盘的机器人无法承担该角色。

反过来也不行。用 `DisplayPasskey` 让机器人承担显示角色，但**规范让显示方随机生成 passkey** —— BlueZ 选择它并交给代理。没有办法让它呈现我们存储的值，而一个无头机器人也没有东西来显示它。

因此一个固定的、印在机器人上的 PIN 无法在 BLE passkey entry 中表达。剩下三个选项：

| | |
|---|---|
| 仅 just-works | 加密，未认证，无 PIN。安全即物理在场。大多数无头 BLE 设备的做法 |
| 带外（QR） | 真正认证且真正逐机。BlueZ 的 OOB 支持薄弱，且没有手机 app 来驱动它。对 v1 来说工程量大 |
| **just-works 加一个应用层 PIN** | **已选。** 配对以加密；在会话中检查 PIN，规则由我们定义 |

### 5.2 它如何工作

配对是 just-works：每个代理处理器都是 `None`，`bluer` 将其发布为 `NoInputNoOutput`。对 RPC 特征值的读取要求 `encrypt_read`，这正是让中心进行绑定的原因 —— 普通加密，而非 `encrypt_authenticated_*`，因为 just-works 绑定永远无法满足已认证的变体，而要求它们会拒绝每个客户端。

然后 `btd` 在客户端发送 `system.authenticate` 之前不服务任何东西。该调用由传输应答而非转发，这就是为什么路由表有第三种结果（`Route::Local`），与"转发"和"拒绝"并列。`hello` 是另一个被允许未认证通过的调用，因为它只报告版本 —— 与 GATT 读取已经告诉未认证客户端的东西相同 —— 而拒绝它会让一个不匹配的客户端无法得知为什么一切都不工作。

三个承重而非附带的细节：

- **PIN 每次尝试都从 `configd` 获取**，不缓存，因此 `robotctl system set-pin` 在下一次尝试而非下次重启时生效。一个无法应答的 `configd` 意味着会话被拒绝而非放行。
- **按字符串比较。** `042042` 与 `42042` 是不同的秘密；数值解析会让它们相同。有一个测试正是为此。
- **三次尝试，然后会话关闭。** 一个六位 PIN 在一条加密但未认证的链路上有百万种猜测，因此限额是唯一让暴力破解代价高昂的东西：重连需要一次完整的 BLE 连接与绑定。`attempts_remaining` 会返回给客户端，以便它可以说"还剩两次"而非静默地失去连接。

### 5.3 这值什么与不值什么

**PIN 穿过一条加密但未认证的链路**，因此一个*在配对时刻*在场的攻击者可以捕获它。这是该权衡的代价，也是威胁模型若有理由证明则应偏好 OOB 的原因。相比仅 just-works，它买到的是：一个仅仅绑定的设备 —— 对范围内任何人都微不足道 —— 仍然什么都做不了。

**出厂 PIN 是 `000000` 且在本仓库中公开。** 因此开箱即用，这只证明物理在场，别无他物。`btd` 在每次用默认值认证时记录警告，`robotctl system pin` 也这么说。安全完全依赖于 PIN 是逐机的，这使它成为一项**初始化义务**：必须有东西生成它、打印它、并记录打印了什么。那就是 `updater-design.md` §5.7 的逐设备状态，与欠我们一个序列号的是同一个槽。

**无配对窗口，且这是决定而非延后。** 机器人在广播时随时可配对。一个逐机 PIN 已经承载了窗口会添加的东西：知道一个印出的 PIN 需要物理访问，而任何能读贴纸的人都能拿起机器人。一个按钮会添加一个可见的同意时刻、一个丢失 PIN 的恢复路径，以及在贴纸被拍照时的纵深防御 —— v1 都不需要，每个都是之后可添加的，因为带按钮的外壳可以门控 `set_pairable` 而不改变此设计。

### 5.5 加密目前是关闭的，且尚未定论 · **measured**

特征值上的 `encrypt_read` 会让读取在 macOS 上**挂起**：CoreBluetooth 发出读请求，BlueZ 因加密不足拒绝它，而什么都不会解决它 —— 没有提示、没有错误、没有重试。客户端对一个工作正常的机器人等超时。关闭该标志后读取即时应答，因此该要求就是原因。

因此 `btd` 当前在测试板上以 `--insecure-no-pairing` 运行，且 **PIN 穿过一条未加密的链路**。这比 §5.3 描述的更糟：不是"加密但未认证"，而是两者都不是。交换期间无线电范围内的任何人都能读取 PIN，此后可做任何客户端可做的事。

未解决，接下来要确立的是绑定是否根本存在 —— `bluetoothctl info <mac>` 报告 `Paired: no` 将意味着永远无法建立加密，而该标志是症状而非原因。在那之前，把要求移到写入上是猜测：如果没有可用来加密的绑定，它会同样失败。

**默认是不安全的，有意为之，目前如此。** 该标志是 `--require-pairing` 且它是**关闭的**。因此从一个版本安装的板子提供一条未加密的链路，开箱即用。

替代方案首先被尝试并被拒绝：默认要求配对时，全新安装是安全的且**不可用** —— 每个客户端都在版本读取上挂起，因为那正是破坏 CoreBluetooth 的配置。一个没人能与之对话的机器人保护不了任何东西，而项目远未到交付时；在一个不能用的默认与一个能用的默认之间，开发工具选择能用的那个。

代价被陈述而非对冲：**每个运行此版本的机器人都有 wifi 凭据和一个可被旁观者读取的 PIN。** `btd` 在每次启动时记录一个指明此事的警告，因此该选择保持可见，而非变成没人记得的事。旧的 `--insecure-no-pairing` 标志被接受并忽略，纯粹是为了让一个在 drop-in 中携带它的板子不会在移除它的更新上启动失败。

这必须被关闭 —— 翻转该标志并默认开启 —— 在任何东西被交给任何人之前。一个其初始化秘密可被旁观者读取的机器人，不是一个你可以交给陌生人的机器人。

### 5.6 开放

- **绑定撤销。** 没有东西解除手机配对；`bluetoothctl untrust` 是手动逃生通道。需要一个 API 和一条关于谁可调用它的规则 —— 可能不是 BLE 本身。
- **限流仅在会话内存续。** 三个错误 PIN 关闭会话，但没有东西跨重连计数，因此一个坚定的对端可以每次三次猜测、以一次绑定为代价无限重试。`btd` 中按地址的退避是显而易见的下一步，且需要某个地方跨会话保持该状态。

### 2.3 假实现是规范，没有东西对照它检查 NM

值得直白陈述，因为它现在描述的是三个 bug 而非一个。在板子上发现的每个 wifi bug 中，**`FakeNet` 已经有正确的行为，而 NetworkManager 实现已经偏离它**：

| 行为 | `FakeNet` | NM 路径，交付时 |
|---|---|---|
| 无线电看不见的 SSID | `NotFound` | 报告 `connected`，命名另一个网络 |
| 失败的尝试 | 什么都不保存 | 留下一个带坏密钥的已保存 profile |
| 重新初始化一个 SSID | 替换 | 堆叠第二个 profile |

因此该 trait 不只是一个测试接缝；它是契约的唯一书面形式。问题在于检查的方向 —— 套件验证假实现对照契约，没有东西验证 NM 对照其中任何一个。两者都实现 `Net`，因此相同的断言*可以*对两者运行；阻止它的是 NM 侧需要真实的 NetworkManager 与真实的无线电，这意味着一块板子而非 CI —— 见 `install-path-gap.md` §"What would close it"，其中板子按设计是按需的且故意不是 CI runner。

在那存在之前，诚实的总结是：`configd` 的 wifi 行为被测试了，而在机器人上运行的代码没有。以上每个 bug 都是在硬件上手、在一个会话内发现的。

### 2.4 什么真正在板子上跑过

记录下来是因为"构建过"与"工作过"在本文档中太久是同一个词，且四个"修复"是对照从未运行的二进制文件验证的。

端到端已证明，在一块 Radxa Zero 3 上以一台 Mac 为客户端：发现、连接、版本读取、PIN 认证、`system.info`、`net.status`、`net.scan`、拒绝边界（`robot.move`、`system.pairingPin`、`update.select` 都被 `btd` 自身以代码 14 拒绝）、`update.check` 路由到 `updaterd`、一个无线电看不见的 SSID 被拒绝为 `NotFound`，以及**一个机器人从未见过的网络经 BLE 被初始化、加入并在重启后自行重新加入** —— 这正是整条路径存在的场景。被拒绝的密码以携带 NM 原因 7 的 `BadKey` 返回，这正是手机据此行动的答案：重新提示输入密码而非显示一个通用失败。

`net.forget` 清除一个 SSID 的每个 profile：五个重复的 `kek` profile，被修复前的二进制留下，在一次调用中消失。整个 `net.*` 面现在已对一个真实的 NetworkManager 运行过。

在板子上仍不成立：链路是未加密的（§5.5）。这是此路径与可以交给某人的东西之间剩下的唯一一件事。

## 6. 没有无线电的测试 · **measured**

套件在一台没有硬件、没有网络、没有 D-Bus 且没有 Docker 的笔记本上运行，且这必须保持为真。两个接缝使之如此：

- **`configd` 的 wifi 是一个 trait**，带有一个内存中的假实现，正如 `duck-control` 有 `RobotIo`。`--fake-net` 服务于整个 `net.*` 面，包括按需的错误密钥失败，这在真实接入点上难以引发。
- **`btd` 的无线电是两个通道，而非一个 trait。** 一个 `GattLink` trait 需要一个异步 `recv` 与一个异步 `send`，而会话循环同时等待两者 —— 意味着关联类型或在 `select!` 中与借用检查器搏斗。一个持有两个 `mpsc` 通道的普通结构体表达同样的东西，而测试构造一个而非实现任何东西。

因此会话测试经由真实 unix socket 驱动一个完整的 BLE 对话：一个被拒绝的调用永远不到达守护进程，`robot.*` 路由到 `robotd` 而非 `updaterd`，以及订阅流的每个通知都通过 23 字节 MTU 到达。

`board-test.sh` 覆盖只在 Linux 上出现的东西：socket 模式、`--allow-user` 解析一个名称、一个组成员读取、一个非成员被 socket 模式阻止、一个无名成员被拒绝变更性调用**且被拒绝的更改未生效**、一个被拒绝的密码以 5 而非 1 退出、PIN 保留其前导零、以及日志中无密码。加上 `btd --version`，这是一个真实的跨链接检查：`btd` 是除 `zstd` 外唯一拉取 C 的二进制，因为 `bluer` 链接由 `zig cc` 从 vendored 源构建的 libdbus。

`duckctl`（`cargo run -p duckctl`）是手机的替身，也是唯一能演练无线电的方式。一个**示例，而非二进制**，因此 `btleplug` 永远不到达机器人；用 `btleplug` 而非 `bluer` 是因为它必须运行在开发者的 Mac 上。它复用 `btd::framing`，因此分块确实是机器人自身代码的客户端半部分，而非一个可以自由地与自己达成一致的重新实现。

### 6.1 什么未被测试

- 两个服务都未见过**真实的无线电**或**真实的 NetworkManager**。两者都对 aarch64 通过类型检查；仅此而已。
- `migrate-network.sh` 中的**切换**只在刚烧录的板子上运行。它被手动一步步执行过一次；然后脚本在结果上重新运行以确认幂等路径。第一个烧录板子的人是真正的测试。
- **BLE 应答前约 73 秒。** `hci0` 直到 `aic-bluetooth.service` 挂载 AIC8800 的 UART 才存在，而 `bluetooth.service` 在 `dbus` 后阻塞 26 秒。`btd` 等待并重试而非退出 —— 与 `robotd` 等待电机总线是同一课 —— 但一个围绕即时发现设计的手机 app 会失望。

## 7. 已接受的代价

- **产物中有两个 D-Bus 协议栈。** `btd` 通过 `bluer` 链接 libdbus；`configd` 使用 `zbus`。几 MB。`bluer` 被选中是因为一个 GATT 服务器、广播与配对代理正是它存在的目的，对应大约 700 行手写的 `org.bluez` 对象管道。如果 `bluer` 长出一个 `zbus` 后端，值得重新审视。
- **一个 vendored libdbus** 由我们而非发行版来保持更新。对于一个仅由我们编写的守护进程通过本地 socket 访问的库来说可接受。
- **`btd` 被故意排除在 `on_apply` 的重启集之外。** 它可能是*发起更新所经由的传输*：重启它会丢弃承载 `update.subscribe` 的连接，而发起更新的手机永远不会得知结果。与 `updaterd` 不在更新中途重启自身是同一原因。代价是有界的而非无界的 —— 一旦应答上线该排除即过期，因此引擎在 5 秒后重启 `btd`，下一次 `updaterd` 启动会验证它已发生（`restart-order.md` §1 与 §5）。

## 8. 接下来

按什么阻塞什么排序，而非按大小。

### 8.1 加密 —— 阻塞项

完整见 §5.5。链路**默认**未加密 —— `--require-pairing` 存在且关闭，因为要求它会让每个客户端挂起 —— 因此 PIN 与每个 wifi 密码以明文传输。关闭这意味着让安全配置工作*并且*翻转默认；只做第一个会让每块板子都不安全。决定修复的一个事实尚不知道：绑定是否根本存在（在机器人上 `bluetoothctl info <mac>`）。*已绑定但不加密*与*从未绑定*需要相反的修复，而交付错误的那个会让问题看似解决实则原地不动。

### 8.2 区分机器人 —— 三个人，三个机器人，一个房间 · **已构建**

三个朋友开箱三个机器人。每个都必须连上*自己的*，而在这落地之前他们没人能：每块从同一镜像烧录的板子都广播 `radxa-zero3`。

这首先是一个可用性问题。它有一个安全尾巴 —— 一部选错机器人的手机可以向它认证并把其所有者的 wifi 凭据写进去，因为 PIN 在所有机器人上都是 `000000` —— 但这个尾巴不是让它值得修复的原因。一个你无法从列表中挑出的机器人是一个没人能用的机器人，这本身就站得住脚。§8.1 单独追踪，不门控此处任何东西。

#### 机器人叫什么

**身份来自 SoC 序列号**，从 `/proc/device-tree/serial-number` 读取并由 `system.info`（`configd::identity`）上报。熔合进芯片并由 bootloader 交出，因此它在重刷后存活、在更换无线电模块后存活，且无需初始化步骤即可存在 —— 这正是让手刷板子仍能工作的原因。它也是一个普通文件读取：无 root、无 D-Bus，且立即可用而非 `hci0` 出现所需的约 73 秒之后。

这在本仓库中不是新想法，值得一说：`updater-design.md` §5.6 已经选了同一个值作为更新日志的稳定设备 ID，出于同样的原因 —— 它工作且无需初始化步骤即可获得。复用它意味着机器人有一个而非两个身份。

蓝牙适配器地址是看起来更好的候选，因为对端在链路层已经看到它，因此从它派生的名称不会泄漏新东西。它基于证据被拒绝 —— 见 §8.6。

**默认名称是 `duck-` 加上序列号的 SHA-256 的四个十六进制字符**：`duck-c51b`。哈希而非切片，因为没有东西保证芯片 id 的哪一部分在芯片间变化。用 SHA-256 而非 `std` 的 hasher，其输出在 Rust 版本间不稳定 —— 一个工具链升级会重命名现场的每台机器人，且没人会把两件事联系起来。

四个十六进制字符是 65 536 种可能，因此一个房间里三个机器人碰撞约为 22 000 次一次。这是一个旨在*可区分*的默认值，而非唯一键。

名称在**扫描响应**中传输，而非广播，且现在永远如此：标志（3）、128 位服务 UUID（18）与地址字段（8，见下文）占去了传统广播可容纳的 31 字节中的 29。加地址之前是 21，一个 8 字符或更短的名称本可以挤进去 —— `duck-c51b` 是 9，超了一个，因此实际上从未行得通。扫描响应是中心可能自行错过的第二次交换，这就是为什么一个无名称无服务被报告的设备是一个可能的机器人而非该过滤掉的东西。

#### 广播的名称是机器人被赋予的那个

`btd` 询问 `configd` 机器人叫什么，每隔几秒把其广播与该答案对齐。在此之前它广播 `/etc/hostname` 而 `system.setName` 写入一个从未被读取的文件：重命名机器人不改变任何手机能看到的东西，甚至重启后也不，而树中的三条注释把预期行为描述得好像它存在。

对齐与适配器监视一起在一次启动内部运行，因此失去无线电会同时结束两者 —— 而下次启动会再问一次，这正是拾取蓝牙关闭期间所做重命名的方式。

**机器人有两个名称，且两者都被设置。** 广播承载一个 Local Name；适配器另外服务一个 GAP Device Name（`0x2A00`），BlueZ 从 `Adapter.Alias` 取并默认为主机名。只设置第一个意味着一个重命名的机器人广播 `duck-c51b`，却对任何读取特征值的人应答 `radxa-zero3` —— 而读取特征值正是中心连接时做的事。BlueZ 随后把该答案缓存在广播名称之上，因此在 Linux 上一个机器人在首次联系前是 `duck-c51b`，之后是 `radxa-zero3`，而 `--name duck-c51b` 不再能找到它；CoreBluetooth 保留两者并报告 `radxa-zero3 [duck-c51b]`。手机自己的蓝牙设置显示 GAP 名称，这正是此处最重要的情况，也是本树中没有工具能看到的情况。`advertise` 与广播一起设置别名，因此每个发布名称的路径都发布两者。缓存了旧名称的客户端会保留它直到被遗忘，这是一个有客户端修复的客户端问题。

故意是轮询而非事件驱动。`btd` 转发 `system.setName` 而不读取应答 —— 解释应答正是这个守护进程避免的事 —— 且在转发的瞬间重新询问会与它刚转发的写入竞争。轮询是更少的活动部件，且覆盖通过 `robotctl` 进行的重命名，那根本不经过 `btd`。`--name` 为工作台工作固定*名称* —— 对齐循环仍在运行，因为下面的地址无论名称是否变化都会移动。一个不可达的 `configd` 回退到主机名：`btd` 在恢复路径上，且必须在机器人其余部分尚未启动时起来。

#### 广播承载机器人的 IPv4 地址

`duckctl scan` 不连接任何东西，这正是它在机器人不可达时是该用的命令的原因 —— 也是列表只能报告广播所承载内容的原因。因此列表最常被读来回答的问题，*我 ssh 到哪？*，其中没有答案：地址在 `net.status` 中，而读取它每个机器人都需要一次连接、一次绑定与 PIN。

四个字节的 IPv4 放入一个 manufacturer-data 字段，公司 id 为 `0xFFFF` —— 蓝牙 SIG 为内部与互操作性测试保留的 id，这对一个尚未被分配 id 的项目来说是正确的。任何人都可以使用该 id，因此**该字段不是身份检查**：它仅从一个也广播了服务 UUID 的设备读取，那才是鉴别器。

**SSID 不在其中且不能在其中。** 一个 SSID 本身就最多 32 字节，对比上面预算剩下的 6 字节载荷。它保持是一个 `wifi status` 问题，而当列表中的地址说出意外情况时，那正是该问的问题。

没有地址的机器人广播 `0.0.0.0` 而非丢弃该字段，因此列表可以区分三种状态：一个地址、一个没有网络的机器人、以及一个来自此特性存在之前版本的机器人（它不广播任何字段）。把后两者合并会让读者去检查一个需要更新的机器人的 wifi。

地址与名称在同一节拍上对齐，每隔几秒 —— 远快于 DHCP 租约变化，且重点是另一种情况：刚运行完 `wifi connect` 的人正等着读它产生的地址。`configd` 未能应答会保留最后已知的地址而非清除它，否则 `configd` 重启会在每个节拍注销并重新注册广播，让一个盯着地址的客户端看到它闪烁。而如果 BlueZ 某天拒绝一个承载该字段的广播，`btd` 会不带它重试：一个没有地址的广播是一个某人仍能触达的机器人，而一个被拒绝的广播是一个变黑的机器人。

#### 初始化可以命名一块板子，且不必如此

`provision.sh --name`，`provision-board.sh --name` 透传它，在最后调用 `robotctl system set-name`。故意是可选的：派生的默认值已经区分了一块板子，因此初始化是*改进*一个可用的名称而非提供它的东西。这正是让它能在一块手刷板子上存活的原因，而那正是排除在初始化时分配身份的反对意见。

#### app 应该做什么

- **把序列号作为键存储。** 这是唯一在重命名与蓝牙地址变更后都存活的句柄，也是"收藏"或用户选择的标签应该挂载的地方。
- **也存储外设标识符**，作为快速路径 —— iOS 上的 `retrievePeripherals(withIdentifiers:)` 完全跳过扫描。它是缓存，不是身份：它随地址死亡（§8.6），而序列号是重新确立收藏指的是哪台机器人的东西。
- **RSSI 是排序键，绝不是身份。** 适合把最近的机器人放第一。不是证据：穿过身体或桌子的信号会随意重排机器人。

一旦一台机器人被连接过一次，这就解决了 —— app 直接回到它并显示所有者给它起的任何名字。

#### 仍开放

- **三个中哪一个是我的，最最第一次。** 列表中三个不同的名字，不等于知道你手中的那个鸭子是哪一个。架桥需要一个物理信号：印在机器人上的东西、一个 `identify` 动作、或接近性。最便宜的缓解不花成本且不是代码 —— 一次只给一台机器人通电，并让 app 这么说。
- **`identify`** —— 让*这台*机器人点头、眨眼或鸣叫。树中没有东西驱动 LED、扬声器或屏幕，且电机控制被设计为经 BLE 拒绝（§3.1），因此这是一个缺失的设备路径而非它看起来的策略问题。当它存在时，会带来两个决定：它可以驱动什么，以及它必须在认证*之前*工作，因为首先要求 PIN 在把 PIN 对准正确机器人本身就是问题时是循环的。
- **一个贴纸，以及印在上面的逐机 PIN。** §5.3 想要 PIN；两者都等待没人定下的硬件。注意 PIN 不能从身份派生：身份被发布在广播中，因此从它计算的任何东西都是公开的。
- **恢复出厂设置做什么。** 今天没有东西清除 `configd` 的配置 —— 它按设计在更新与回滚中存活，`update.resetToGolden` 回滚的是版本而非配置 —— 因此一个初始化的名称与一个用户重命名无法区分。一个单独的"出厂名称"槽只有在有东西能清除一个而不清除另一个时才值得保留。

#### 测试不覆盖什么

身份与派生名称是普通的单元测试。此特性存在的场景 —— 三台机器人同时广播且客户端正确选择 —— 无法在板子外测试，且想要要么三台要么一个假外设。值得直白说出来，而非让绿色套件暗示否则。

### 8.4 跨重连的 PIN 尝试

§5.6。三个错误 PIN 关闭会话；没有东西跨重连计数，因此一个对端以每次三次猜测、一次绑定为代价无限重试。需要某个地方保持按地址的状态。

### 8.6 适配器地址不固定 —— **未调查**

记录下来以免从零重新发现。此处的东西没有被追查到底，且它被故意搁置而非作为开放工作。

一块板子在十六次启动中报告了两个不同的蓝牙地址，来自 `btd` 自己的启动行（`serving BLE ... address=`）：

- `50:37:CD:16:2B:EC` —— 一次启动内两次 `btd` 启动，10:04 与 10:05
- `50:37:CD:16:1B:92` —— 之后每次启动，从 10:18 起，十五次

其间：无重刷。对板子除了通过 `duckctl` 的 BLE 连接与手柄配对外什么都没做。高四字节保持；只有低两字节移动，这符合一个在厂商前缀后生成一次地址并缓存而非从模块读出的驱动。`configd` 从不给适配器上下电 —— 它只给一个关闭的上电 —— 因此手柄配对没有明显的机制，这使它成为该测试的东西而非该责怪的东西。

为什么它除了一条令人困惑的日志行之外还重要：

- **每个绑定都存活在 `/var/lib/bluetooth/<address>/` 下**，因此地址变更会让它们全部成为孤儿。一个已配对的手柄与一个已绑定的手机都会停止工作，而重新配对看起来像是对一个无关故障的修复。
- **iOS 从设备地址派生出外设标识符**，因此 app 保存的"我的机器人"会随之断裂。这就是为什么 §8.2 让 app 把收藏挂在*序列号*上。

它不再是一个身份问题 —— §8.2 不再依赖此值做任何事 —— 这就是为什么这可以等。

当有人接手时，最便宜的下一步。`sudo ls -la --time-style=long-iso /var/lib/bluetooth/` 给出第二个地址首次出现的时刻，因为 BlueZ 以它见过的每个适配器命名一个目录。然后在 `robotctl pad pair` 前后 `bluetoothctl show | head -3` 可以不用重启就判定手柄假设。如果地址结果来自一个文件，它可以被有意固定 —— 这也会让它在重刷后存活。

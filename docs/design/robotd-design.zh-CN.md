# robotd 设计

`robotd` 控制循环设计。

本页面拥有控制循环、IMU 读取、电机通信、安全、跌倒检测、bring-up 状态机和健康检查。[`architecture.md`](architecture.md) 拥有 `robotd` 在整体中的位置；[`restart-order.md`](restart-order.md) 拥有 `robotd` 在更新时如何重启。

## 一个进程，一个串口总线，一个 50Hz 循环

`robotd` 是一个单进程，通过一个串口总线与所有电机和传感器通信，运行一个 50Hz 的控制循环。

### 为什么是一个进程

最初的设计是多个进程：一个用于电机控制，一个用于 IMU 读取，一个用于高级行为。这被证明是错误的，因为：

1. **时序**：电机命令和 IMU 读取需要在同一个 50Hz 循环中同步。跨进程的 IPC 会引入不可预测的延迟。
2. **简单性**：一个进程比多个进程更容易调试和推理。
3. **故障隔离**：如果电机进程崩溃，IMU 进程继续运行是没有用的——没有电机控制，IMU 数据是无用的。

### 为什么是一个串口总线

所有电机（12 个舵机）和 IMU 都在同一个串口总线上。这是硬件设计——舵机使用 Dynamixel 协议，IMU 被模拟为一个 ID 为 200 的舵机。一个总线意味着一个串口文件描述符，一个读写循环。

### 为什么是 50Hz

50Hz（每 20ms 一次）是舵机的更新率。更快的循环不会让电机移动得更快（它们有自己的内部控制循环），更慢的循环会导致运动不平稳。50Hz 是响应性和 CPU 使用率之间的平衡点。

## IMU 在 motors 的 sync_read 中

### ID 200

IMU 不连接到单独的总线或 I2C。它被模拟为一个 ID 为 200 的 Dynamixel 舵机。这意味着它可以在与电机相同的 `sync_read` 操作中被读取。

### 为什么这很重要

在每个 50Hz 循环中，`robotd` 执行一个 `sync_read`，同时读取所有 12 个电机的位置和 IMU 的加速度/陀螺仪。这意味着 IMU 数据与电机位置数据在时间上是同步的——它们是在同一个总线事务中读取的。

如果 IMU 在单独的总线上，IMU 读取和电机读取之间会有延迟，使得姿态估计更加困难。

## TIOCEXCL 排他

### root 不被阻止

`robotd` 在串口文件描述符上设置 `TIOCEXCL`。这应该阻止其他进程打开同一个串口。但 `TIOCEXCL` 不阻止 root——root 可以随时打开任何设备。

因此 `TIOCEXCL` 是安排的而非强制的：它阻止非 root 进程（如调试脚本）意外打开总线，但不阻止 root 进程（如另一个以 root 运行的守护进程）。

### 为什么这很重要

如果两个进程同时写入串口总线，舵机会收到混乱的命令，可能导致不可预测的运动。`TIOCEXCL` 是第一道防线，但真正的保护是"只有 `robotd` 应该接触电机总线"的架构规则。

## MissedTickBehavior::Skip

### 踩坑点：延迟累积

`tokio::time::interval` 默认的 `MissedTickBehavior` 是 `Burst`——如果循环错过了一个 tick（因为 I/O 花费的时间比预期长），它会立即快速触发后续 tick 来"赶上"。这导致控制循环在延迟后突发运行，可能在短时间内发送多个电机命令。

对于电机控制来说，这是危险的——突发的命令可能导致舵机过载或运动不平稳。

### 修复：Skip

`MissedTickBehavior::Skip` 意味着如果循环错过了一个 tick，它只是跳过它，然后等待下一个常规 tick。没有突发，没有追赶。如果一个循环迭代花费了 30ms（超过 20ms 的 tick 间隔），下一个迭代在 40ms 标记处开始，而不是立即。

这意味着循环的平均速率可能低于 50Hz（如果持续延迟），但它永远不会突发。对于电机控制来说，稳定的速率比精确的速率更重要。

## safety owns 唯一 RobotIo

### 借用检查器强制

`RobotIo` 是串口总线的封装。它是唯一可以读写电机总线的结构体。`safety` 模块拥有 `RobotIo` 的唯一实例——其他模块（如 `control`、`telemetry`）必须通过 `safety` 请求访问。

这不是设计选择——它是 Rust 借用检查器强制的。`RobotIo` 不是 `Clone`，也不是 `Sync`，因此只有一个 `&mut RobotIo` 可以存在。`safety` 持有它，并在每个循环迭代中将其借给需要它的模块。

### 为什么这很重要

这意味着没有代码可以绕过安全检查直接写入电机。每个电机命令都必须通过 `safety`，它可以在命令发送之前检查安全条件（如跌倒检测、温度限制）。

## fall verdict 是报告不是门控

### 踩坑点：跌倒检测不应停止电机

最初的设计是，当跌倒检测触发时，`safety` 会停止所有电机（将它们设置为 limp 模式）。这被证明是错误的，因为：

1. **假阳性**：跌倒检测可能误报（例如，机器人被推但没有真正跌倒）。停止电机会导致机器人摔倒，而不是防止摔倒。
2. **恢复**：如果机器人跌倒了，它需要电机来恢复（站起来）。停止电机会阻止恢复。
3. **责任**：跌倒检测应该报告"机器人跌倒了"，而高级行为层应该决定做什么（停止、恢复、呼救）。

### 修复：verdict 是报告

`fall` 模块输出一个 verdict（`Ok` 或 `Fallen`），但它不直接控制电机。verdict 被报告给高级行为层，由它决定如何响应。`safety` 只在真正危险的情况下（如电机过热、电池电压过低）才门控电机命令。

## limp_fall 第二检测器

### 速率而非位置

主跌倒检测器使用 IMU 的加速度和陀螺仪来检测机器人是否跌倒。但它有一个盲点：如果机器人处于 limp 模式（电机断电），它会慢慢倒下，IMU 可能检测不到（因为加速度很低）。

`limp_fall` 是第二个检测器，专门检测这种情况。它不看加速度——它看关节位置的变化速率。如果机器人处于 limp 模式，关节位置会由于重力而缓慢变化。`limp_fall` 检测到这种缓慢变化并报告跌倒。

### 为什么需要两个检测器

主检测器对快速跌倒（机器人被推倒）很敏感，但对缓慢跌倒（limp 模式下的重力坍塌）不敏感。`limp_fall` 对缓慢跌倒很敏感，但对快速跌倒不敏感（因为快速跌倒时关节位置变化太快，可能被误认为是正常运动）。两者结合覆盖了所有情况。

## bring-up 状态机

### Limp → Homing → Ready

`robotd` 启动时经历三个状态：

```
Limp → Homing → Ready
```

| 状态 | 电机状态 | 接受命令？ | 持续时间 |
|---|---|---|---|
| Limp | 断电（自由移动） | 否 | 2 秒 |
| Homing | 缓慢移动到起始位置 | 否 | 5-10 秒 |
| Ready | 正常控制 | 是 | 无限 |

### 为什么是这个序列

1. **Limp**：启动时，电机首先断电 2 秒。这给了用户时间将机器人放在平坦的表面上，并确保电机没有卡住。如果 `robotd` 在启动时立即给电机通电，而机器人处于不稳定位置，它可能会摔倒。
2. **Homing**：电机缓慢移动到预定义的起始位置（站立姿势）。这确保所有电机都在已知位置，然后才接受用户命令。homing 是缓慢的（每个电机约 1 秒），以避免突然运动。
3. **Ready**：电机接受正常控制命令。机器人可以被驾驶、执行动作、改变姿势。

### 状态转换

- Limp → Homing：2 秒后自动
- Homing → Ready：所有电机到达起始位置后自动
- Ready → Limp：`robotd` 关闭时，或收到 `system.shutdown` 命令时

## health 只看循环是否满足截止线

### 踩坑点：健康检查不应看电机是否移动

`updaterd` 在更新后调用 `robotd` 的健康检查。最初的设计是健康检查验证电机是否实际响应命令（发送一个小的移动命令并检查位置是否变化）。这被证明是错误的，因为：

1. **硬件依赖**：健康检查需要实际的电机硬件。在没有电机的开发机器上，健康检查总是失败。
2. **危险**：健康检查移动电机会导致机器人在更新后突然运动，可能导致摔倒。
3. **不可靠**：电机可能因为多种原因不响应（卡住、断电、总线故障），而健康检查无法区分"robotd 不健康"和"电机有问题"。

### 修复：只看循环

健康检查只看控制循环是否满足其截止线——即每个 20ms 的 tick 是否在 20ms 内完成。如果循环持续错过截止线（例如，因为 I/O 阻塞或 CPU 过载），`robotd` 报告不健康。如果循环满足截止线，`robotd` 报告健康，即使电机没有实际连接。

这意味着健康检查可以在没有硬件的情况下通过，并且它只测量 `robotd` 自身的健康，而不是整个机器人的健康。一个真正不健康的 `robotd`（崩溃循环、卡住的循环）会被捕获，而一个健康的 `robotd` 连接到有问题的电机会报告健康（这是正确的——问题在电机，不在 `robotd`）。

## 控制循环细节

### 每个迭代的步骤

每个 20ms 的循环迭代执行以下步骤：

```
1.  sync_read：读取所有电机位置 + IMU（一个总线事务）
2.  跌倒检测：使用 IMU 数据检查是否跌倒
3.  姿态估计：融合 IMU 和电机位置，计算当前姿态
4.  行为层：根据当前状态和命令，计算目标电机位置
5.  安全检查：验证目标位置在安全范围内
6.  sync_write：将目标位置写入所有电机（一个总线事务）
7.  遥测：将当前状态发送到订阅者
8.  等待下一个 tick
```

### sync_read 和 sync_write

Dynamixel 协议支持 `sync_read` 和 `sync_write`——在一个总线事务中读取或写入多个电机。这比逐个读取/写入每个电机要快得多。

每个循环迭代有两个总线事务：一个 `sync_read`（读取所有电机 + IMU）和一个 `sync_write`（写入所有电机）。在 1Mbps 的总线速度下，每个事务约 1-2ms，因此总线 I/O 总共约 2-4ms，为控制逻辑留下 16-18ms。

## 什么未被测试

- 真实硬件上的 50Hz 循环时序——在 Radxa 上测量每个循环迭代的实际时间
- 跌倒检测的准确性——在各种场景（被推、绊倒、从桌子上掉下来）中测试假阳性和假阴性
- homing 序列的安全性——homing 期间电机是否可能碰撞或过载
- limp_fall 检测器的敏感性——在各种 limp 场景中测试
- 高遥测订阅者数量下的循环延迟——如果多个客户端订阅遥测，序列化和发送遥测数据是否会使循环错过截止线
- 电机总线错误恢复——如果 `sync_read` 或 `sync_write` 失败（例如，由于总线噪声），循环是否能优雅恢复
- 温度限制——电机过热时的安全行为尚未实现或测试

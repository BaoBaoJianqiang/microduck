# 应用路径设计

手机如何配置机器人——wifi、名称、重启、版本、触发更新。

本页面拥有 `btd` 与 `configd` 的联动设计、GATT 协议、配对和安全。[`architecture.md`](architecture.md) 拥有整体架构；[`updater-design.md`](updater-design.md) 拥有更新系统；[`remote-webrtc.md`](remote-webrtc.md) 拥有 WebRTC 远程访问。

## 为什么手机应用存在

机器人没有屏幕、没有键盘、没有以太网。首次设置时，它没有 wifi 凭据，因此无法连接到网络。用户需要某种方式来：

1. 告诉机器人他们的 wifi 凭据
2. 给机器人起个名字
3. 查看机器人运行的版本
4. 触发更新
5. 基本控制（姿势、动作）

手机应用是唯一合理的方式。每个人都有手机，BLE 内置于每部现代手机中，而且不需要机器人先连接到网络。

## `btd` owns nothing，所以 `configd` 存在

最初的设计是让 `btd` 做所有事情：BLE 连接、配置存储、wifi 管理、更新触发。这被证明是错误的，原因有三：

1. **`btd` 是无状态管道**。它的工作是将 BLE GATT 特征转换为 IPC 调用。如果它也存储配置，它就不再是无状态的——它不能在不丢失配置的情况下被杀掉并重启。
2. **配置必须在 `btd` 死亡时可达**。如果 `btd` 崩溃，用户仍然需要能够配置机器人。如果配置在 `btd` 中，他们就不能。
3. **wifi 管理很复杂**。NetworkManager D-Bus API 很大，而且需要 root。将其与 BLE 协议混合会使 `btd` 难以测试和维护。

因此 `configd` 被创建为配置所有者。`btd` 只是一个管道——它接收 BLE 命令，通过 IPC 转发到 `configd`（或 `updaterd` 或 `robotd`），并返回回复。

## GATT 协议

### 单 characteristic 承载 NDJSON JSON-RPC

`btd` 暴露一个 GATT service，包含两个 characteristic：

| Characteristic | 属性 | 用途 |
|---|---|---|
| `write` | WRITE | 手机 → 机器人：JSON-RPC 请求 |
| `notify` | NOTIFY | 机器人 → 手机：JSON-RPC 响应 + 通知 |

所有通信都是 NDJSON（换行分隔的 JSON）——每个 JSON-RPC 消息是一行，以换行符结尾。这比二进制协议更容易调试，而且 GATT 的 MTU（最大传输单元）足够大，可以容纳大多数消息。

### 为什么是 JSON-RPC 而非自定义协议

- **标准**：JSON-RPC 2.0 是一个定义明确的标准，有库可用于大多数语言
- **人类可读**：可以用 LightBlue 或 nRF Connect 手动调试
- **灵活**：可以在不破坏客户端的情况下添加字段和方法
- **足够快**：对于配置命令（用户输入速度），JSON 解析开销可以忽略不计

### 分块

GATT 写入限制为 MTU-3 字节（通常约 500 字节）。大于此的消息被分块：

```
手机 → 机器人：[chunk 1][chunk 2][chunk 3]...
```

每个块以一个 1 字节的头开头：

- `0x00`：更多块跟随
- `0x01`：最后一块

机器人累积块直到看到 `0x01`，然后解析完整的 JSON-RPC 消息。

**踩坑点：分块乱序**。最初的实现使用多线程运行时，BlueZ 的每写入独立任务意味着块可能以 1,3,2 的顺序到达。重组产生有效的 JSON，但内容错误。修复：使用单线程 `current_thread` 运行时 + 同步 `try_send`（无 await），确保块按顺序处理。

## 按 Lane 分连接

最初的设计是一个 BLE 连接承载所有通信。这被证明是错误的，因为 GATT 写入是阻塞的——一个缓慢的命令（如 wifi 扫描）会阻塞所有其他命令。

解决方案：按 Lane 分连接。每个 Lane 是一个独立的 BLE 连接，承载一种类型的通信：

| Lane | 用途 | 延迟敏感度 |
|---|---|---|
| Prompt | 用户输入（wifi 凭据、名称、PIN） | 低（用户在等待） |
| Operation | 命令（更新触发、重启、姿势） | 中 |
| Stream | 通知（遥测、更新进度） | 高（必须实时） |

手机可以同时打开多个连接。一个缓慢的 Operation 不会阻塞 Stream 通知。

### 为什么不是多个 characteristic

多个 characteristic 共享同一个连接，因此一个缓慢的写入仍然会阻塞所有其他 characteristic。独立连接是获得真正并行性的唯一方法。

## 配对：just-works + 传输层 PIN

### BLE 无法表达固定 PIN

BLE 配对有三种安全级别：

1. **Just Works**：无用户交互，加密但无认证
2. **Passkey Entry**：用户在一个设备上输入 6 位数字
3. **Numeric Comparison**：两个设备显示相同的数字，用户确认

Passkey Entry 看起来是固定 PIN 的自然选择——用户在手机上输入 `000000`。但它不是固定的：每次配对时，Passkey 是随机生成的。没有办法说"这个设备的 PIN 永远是 000000"。

### 解决方案：just-works 加密 + 传输层 PIN

配对使用 Just Works——它提供加密（防止窃听），但不提供认证（任何在范围内的设备都可以配对）。

认证在传输层：`btd` 在执行任何变更命令之前验证 `system.authenticate` PIN。手机必须先发送：

```json
{"jsonrpc":"2.0","method":"system.authenticate","params":{"pin":"000000"},"id":1}
```

如果 PIN 正确，`btd` 将会话标记为已认证。后续的变更命令（wifi 设置、名称更改、更新触发）需要已认证的会话。

读取命令（查看版本、查看名称、查看 wifi 状态）不需要认证——它们是公开信息。

### 出厂 PIN 是 `000000`

出厂 PIN 是 `000000`。用户可以在设置后更改它。字符串比较保留前导零——`000000` 不等于 `0`。这很重要，因为如果比较是数字的，`000000` 和 `0` 将匹配，而一个试图用 `0` 认证的攻击者将成功。

## 广告间隔 100-150ms

### 默认 1.28s 致 31s 缺席

BLE 广告间隔默认是 1.28 秒。这意味着手机每 1.28 秒才能看到一次机器人。在 BLE 扫描窗口和广告间隔之间，手机可能需要长达 31 秒才能发现机器人。

这对于用户体验来说是不可接受的——用户打开应用，期望立即看到机器人。

### 修复：100-150ms

广告间隔改为 100-150ms。这意味着手机在几秒钟内就能发现机器人。代价是功耗——更频繁的广告消耗更多电池。但对于一个插电的机器人来说，这不是问题。

## GAP 名称 vs Local Name

### 踩坑点：两个名称

BLE 有两个名称字段：

1. **GAP 名称**：存储在蓝牙适配器中，由 `hci0` 报告
2. **Local Name**：在广告数据中广播

最初的实现只设置 GAP 名称。这在 iOS 上有效，但在 Android 上，某些设备只显示 Local Name。结果是机器人在 Android 上显示为"未知设备"或适配器的默认名称。

### 修复：同时设置两者

`btd` 同时设置 GAP 名称（通过 `Adapter.Alias`）和 Local Name（在广告数据中）。这确保机器人在所有平台上显示正确的名称。

## 73s 适配器等待

### 踩坑点：hci0 通电后约 73 秒才存在

在 Radxa Zero 3W 上，蓝牙适配器（`hci0`）在系统启动后约 73 秒才出现在 D-Bus 上。其中 26 秒是 `bluetooth.service` 被阻塞在 `dbus` 后面。

最初的实现假设 `hci0` 在 `btd` 启动时就存在。结果是 `btd` 在启动时崩溃，因为它找不到适配器。

### 修复：等待适配器

`btd` 在启动时等待 `hci0` 出现在 D-Bus 上。它每 5 秒重试一次，直到适配器出现或达到超时（5 分钟）。这意味着 `btd` 可能需要长达 73 秒才能开始广告，但它不会崩溃。

## 加密当前关闭

### 踩坑点：macOS CoreBluetooth hang

最初的实现要求 BLE 连接加密（通过 Just Works 配对）。这在 Android 和 iOS 上有效，但在 macOS 上，CoreBluetooth 在尝试配对时会挂起。macOS 的 BLE 栈有一个已知的 bug，在某些情况下配对会无限期阻塞。

### 修复：加密当前关闭

为了支持 macOS 开发，加密当前被关闭。BLE 连接是明文的。这对于 v1 是可以接受的，因为：

- 机器人在家庭/实验室网络上，而不是在公共空间
- 变更命令需要 PIN 认证（即使加密关闭，PIN 也保护）
- wifi 凭据在 BLE 上传输，但它们也可以通过其他方式被截获（如果攻击者在范围内）

当 macOS bug 被修复或解决时，加密将被重新启用。

## 命令集

### `system.*`

| 方法 | 参数 | 用途 | 需要认证？ |
|---|---|---|---|
| `system.info` | — | 获取机器人信息（名称、型号、版本） | 否 |
| `system.authenticate` | `pin` | 使用 PIN 认证会话 | 否 |
| `system.set_name` | `name` | 设置机器人名称 | 是 |
| `system.reboot` | — | 重启机器人 | 是 |
| `system.shutdown` | — | 关闭机器人 | 是 |

### `net.*`

| 方法 | 参数 | 用途 | 需要认证？ |
|---|---|---|---|
| `net.state` | — | 获取网络状态（wifi 是否已连接、SSID、IP） | 否 |

| `net.connect` | `ssid`, `password` | 连接到 wifi 网络 | 是 |

## 什么未被测试

- 多个同时连接（按 Lane 分连接）——手机可以同时打开 3 个连接，但尚未在真实硬件上测试
- BLE 范围内的恶意设备——加密关闭意味着命令可以被截获，但 PIN 应该阻止变更
- wifi 凭据的安全性——它们在 BLE 上明文传输（加密关闭），但在 `configd` 中安全存储
- 长命令的分块——大于 MTU 的命令被分块，但尚未测试非常大的命令（如长 wifi 密码）
- 连接丢失时的会话状态——如果 BLE 连接丢失，已认证的会话会发生什么未定义
- Android 后台扫描——Android 限制后台 BLE 扫描，应用可能需要前台服务才能持续发现机器人

# 从手机更新机器人

状态：已交付，尚未在板子上运行 · 日期：2026-08-19 · 负责人：pierre

经由蓝牙的更新路径已经走了大半，而没人驱动过它。`btd` 已经路由了更新子集，`updaterd` 已经向任何询问者流式传输进度，`duck-btctl` 可以通过 `call` 到达所有这些。驱动它发现了一个缺陷，使 app 自身的流程 —— 启动一个更新，观看它 —— 变成一个机器人静默从未执行的更新，两个 `updaterd` 中的较小缺陷，以及一个值得键入的客户端面。

本文记录发现了什么与决定了什么。机制位于代码旁边：[`app-path-design.md`](../design/app-path-design.md) §3.5 负责连接泳道，§3.1 负责路由子集，`btd/src/route.rs` 承载使它们成立的每条路由上的推理。

## 1. 已经工作的，且未重建

**被路由的子集覆盖了读取与触发。** `hello`、`update.check`、`update.apply`、`update.status`、`update.subscribe`、`update.log` 与 `update.listInstalled` 已经到达 `updaterd`，`robot.health` 到达 `robotd`。此处没有给协议添加方法。

**一个 apply 已经流式传输其自身的进度。** `updaterd` 的 `run_mutating` 在应答之前把 `update.progress` 通知写到 apply 到达的连接上；`btd` 把上游的每一行泵入会话而不读取它；`duck-btctl` 打印无 id 的行并继续等待。因此进度在 apply 期间到达一个 BLE 客户端，根本不需要订阅 —— 而 `duck-btctl.md` 声称相反，*"在其自己连接上的 apply 在完成前是沉默的"*，这已被纠正。

**一个在更新中途重连的客户端不会丢失。** `updaterd` 按组件保留最新的 `Progress` 并向新订阅者重放，`update.status` 在更新期间从一个缓存快照应答并打入实时阶段。两者都是链路断开后手机需要的。

**且应答在传输死亡之前出去。** `updaterd` 与 `btd` 是更新从不重启的两个单元，且两者都在应答后约五秒重启（[`restart-order.md`](../design/restart-order.md) §1）。

## 2. 出了什么问题

### 2.1 一个长调用让会话其余部分沉默 · `btd` · **已修复**

`Pool` 每个服务每个会话持有一个连接，而其后的两个守护进程对一个连接一次服务一个请求。因此 `update.subscribe` 后跟 `update.apply` 把 apply 写进一个 `stream_progress` 已停止读取的 socket：它从不运行、从不应答、从不报错。所有者点击"更新"，机器人什么都不做，且各处都找不到错误。`update.apply` 后跟 `update.status` 是同一个缺陷，症状更温和 —— 一个状态轮询在机器人好好的且正在更新时超时。

调用现在按持有连接多久分组，每组获得自己的连接：`app-path-design.md` §3.5 有泳道、为什么在发生的地方共享一个是正确的、以及为什么每个调用一个连接被拒绝。两个失败都有在没有修复时会失败的测试。

这是此处唯一一个移动 app 无法绕过的变更。

### 2.2 进度是一根对准 20 字节管道的消防水带 · `updaterd` · **已修复**

源报告它写入的每一个 HTTP 块 —— 对一个版本产物来说数千个 —— 每个订阅者都为所有这些付出代价。一个进度行约一百字节，是 `btd` 分帧到的 20 字节下限的五六个通知，而 `btd` 在客户端落后时丢行，因此手机看到百分比的任意子集和一个从 12 → 61 → 34 跳跃的进度条。

现在每个整百分之一最多一个通知，每秒最多四个，在生成数字的引擎中合并，因此 `robotctl update watch` 获得相同的流。被间隙抑制的百分之一在下载结束时仍会发布，否则一个快速下载会可见地停在 97%。

### 2.3 `update.check` 阻塞在引擎锁上 · `updaterd` · **已修复**

`ipc.rs` 在其自己的头部陈述了规则 —— 只读请求使用 `try_lock`，以便 `status` 与 `subscribe` 在更新期间仍可应答 —— 而 `check` 没有遵守。在 apply 期间被询问时，它在 apply 完成时（几分钟后）应答，这在手机上与一个已经停止应答的机器人无法区分。它现在立即应答 `BUSY`，`update.pin` 也是。

### 2.4 决定：回退可从手机到达

`update.rollback` 与 `update.select` 曾被拒绝；两者现在都被路由。`update.pin` 与 `update.resetToGolden` 保持拒绝。推理在 `btd/src/route.rs` 的分支上，并在 `app-path-design.md` §3.1 中总结；决定它的是：

`update.apply` 已被路由，且是三者中更具后果的一个 —— 它安装从未在本板运行过的代码，从网络 —— 而 rollback 与 select 移到一个昨天在它上面运行过的版本，不下载任何东西，且像任何其他转换一样被门控并自动回滚。引擎自己的自动回滚覆盖未通过健康门的版本，那不是所有者拿起手机要处理的情况：那种情况是一个版本安装成功、通过健康门、然后行为*更糟* —— 一个走路不稳的策略而非完全不能走，一个停止重连的 pad。除了人之外没有东西能回滚它，而那个人正拿着手机且没有 ssh。

两者都被开放而非只有 `rollback`，因为 `update.listInstalled` 已被路由：一个 app 可以显示板子上的每个版本，而能显示它们却不能选择一个是奇怪的一半。`select` 需要从列表中挑一个版本，这是一个更大的、更容易被误触弄错的面，这就是被接受的代价。

`pin` 是有趣的拒绝。一个错误的 `select` 离撤销只差一个版本，且机器人说它在哪个版本上；一个被误触锁定的机器人会拒绝之后的每一次更新并自称是最新的，这是这里唯一一个看起来像正确行为的失败。

### 2.5 一个手机触发的更新被记录为 `btd` · **记录，未修复**

`updaterd` 在每次变更上从 `SO_PEERCRED` 记录调用者的 uid 与 pid，这就是技术支持回答"谁触发了这次回滚"的方式。经由 BLE，答案永远是 `btd`，对每部手机。`btd` 逐字转发参数，添加一个"谁"字段会让它成为请求的作者而非管道。只有在技术支持需要区分两部手机时才值得重新打开。

### 2.6 客户端截止时间是总时间，而非空闲时间 · `duck-btctl` · **已修复**

一个固定预算要么切断一个正在工作的更新，要么等待一个死掉的机器人，而有用的信号已经在到达：每个进度通知都是机器人在工作的证明。截止时间现在是静默期 —— 更新三分钟，这是一个人可以合法拥有的最长间隙（一个安装后钩子），而非一个人可以花的最长时间。手机 app 继承该原则，而非代码。

### 2.7 链路在守护进程 apply 应答后约五秒断开

不是缺陷 —— §1 的排序，工作正常 —— 但每个客户端都得预期它，且机器人宣布的断开绝不能读为一次失败的更新。要据此构建的序列：

1. `update.apply` 以其结果应答。那就是答案；更新完成。
2. 约五秒后 `btd` 重启，连接断开。
3. 重连，读取 `update.status`。`last_attempt` 携带结果，因此错过了步骤 1 应答的客户端仍能报告它。

`duck-btctl` 在它发生之前打印步骤 2。

### 2.8 故意开放：经蓝牙的 `from_dir`

`ApplyOptions.from_dir` 命名机器人上的一个目录，这对手机无意义，在工作台上有用。过滤它意味着 `route.rs` 决定参数而非方法，而检查参数正是 `btd` 不做的事。预检已经拒绝会咬人的情况 —— 且说明了 —— 因此这保持原样，在此命名以便下一个人找到一个决定而非一个疏忽。

## 3. `duck-btctl` 现在提供什么

`version`，以及带 `check`、`apply`、`status`、`versions`、`log`、`rollback`、`select` 与 `watch` 的 `update` —— 与 `robotctl update` 使用相同的词，因此在机器人上学的命令经无线电也能工作。参数从 `duck_ipc_proto` 自己的类型构建，而非手写 JSON，这正是 `call` 留给任何键入者的事：`update.apply` 的目标是一个外部标记的枚举，因此 `--ref` 与 `--version` 是不同的 JSON *形态*，一个错误的是一个其中没有任何可据以行动内容的解析错误。[`duckctl.md`](../robot/duckctl.md) 有每个命令。

进度在 stderr 上作为每个事件一行打印，这是该页面已经承诺而工具没有做的。

`duck-btctl` 是一个临时替代品，而这正是它重要的地方：§2.1、§2.2 与 §2.3 是机器人侧的，因此 app 继承修复，而 §2.6 的截止时间形态是客户端侧的，因此工具做对了，而 app 自己的笔记将不得不说明为什么。

## 4. 剩下什么

**这些都没有在板子上运行过。** 以上所有都被测试覆盖，而测试看不到手机看到的东西：进度是否在一条真实的 20 字节链路上平滑到达，apply 的应答是否在 `btd` 重启前到达客户端，以及每个服务的第四个 socket 在 Zero 3W 上是否有任何代价。那是下一个会话，用 `duck-btctl update apply --ref` 对抗一个 dev 板。

**`duck-btctl.md` 中的陈旧声明是从读代码纠正的，而非从板子。** 如果经 BLE 的 apply 结果终究是沉默的，要看的机制是 `btd/src/link.rs` 中的出站队列，而非路由。

## 5. 这故意不做什么

**无取消。** 引擎没有，一个半应用的更新比一个慢的更新更糟。一个走开的客户端已经被处理：更新完成。

**无来自手机的自动应用开关。** `deploy/updater.toml` 故意不让客户端机器人选择无人值守重启，且在有一个机群可推理之前，这不是一个该作为开关暴露的决定。

**无加密。** `app-path-design.md` §8.1 负责它，它在这里不阻塞任何东西，且以上关于无线电范围内对端能做什么的每个断言都假设它仍然关闭。

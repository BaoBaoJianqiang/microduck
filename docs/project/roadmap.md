## 第一个路线图到达了它的目标

M1 到 M4 是一个有一个目的地的序列：一个会走路、空中自我更新、且做这件事时不会变砖的机器人。那已经到达。自 `0.2.0` 以来的每个版本都通过 M1 与 M2 构建的机器到达一块板子，且 `0.9.x` 是一只会走、会滚、会看、会说、会唱的鸭子。

接下来的不是那个队列的延续。剩下的工作是独立的轨道，有不同的风险且它们之间没有顺序，因此**下面的数字是标识符，不是序列** —— [工作顺序](#工作顺序) 是它自己的一节。

**创始断言对了一半。** *难的部分是产品化，而非能力* 正确判断了难度：更新路径、健康门、恢复网与 BLE 面都被构建了，且都成立。它错误判断了体量。自 `0.5` 以来几乎所有东西都是能力 —— 运动学、里程计、ToF、凝视、语音、chorale、摄像头 —— 且其中最大的一块，自主大脑，仍未移植。

## 里程碑

每个都有一个说"完成"的测试，因为没有测试的里程碑会漂移。

### M1 —— 闭合回路 · **完成**

更新器得到了一些真实的东西来门控，且团队得到了一个共享的 crate 边界：一个 `robotd` 骨架，其状态是原子而非互斥（一个循环卡住的机器人仍须能应答*我不健康*），`duck-ipc-proto` 被抽出，以便恢复路径上没有任何东西链接引擎的 http/tar/crypto 树，一个健康门是一个真实的 socket 探测，`robotd` socket 的唯一真相源，每个守护进程在任何东西可能失败之前以 `warn` 记录的一行身份，以及通过普通引擎的首次安装引导。

**完成：** `robotd/tests/updater_gate.rs` 针对一个真实 `robotd` 进程经一个真实 socket 门控一次更新并提交；`robotd --unhealthy` 回滚 `current` 背后的内容。

### M2 —— Dev 通道 · **完成**

`sudo robotctl update apply daemon --ref my-branch` 安装一个分支构建，且 `scripts/dev-push.sh` 通过 ssh 安装一个笔记本构建，完全没有 CI 运行。两个属性让这在每次推送时都安全，两者都在工作流之外强制执行：一个 dev 构建**不能变成 `latest`**（版本是一个 semver 预发布，且 `version_under` 拒绝把一个 dev 标签读作发布版本），且它**不能安装在客户机器人上**（那里 `allow_dev_keys` 为 false，且一个受信任密钥仅当其文件名以 `.dev.pub` 结尾才算 dev 密钥）。

**完成：** 对照真实仓库验证 —— `dev.yml` 已发布，`--ref main` 经网络安装，且一个客户机器人配置拒绝了同一构建。

**它留下的一件开放的事，现在已决定：** 一个私有仓库的发布资产用一个 token 可达，而客户机器人没有，因此当这个仓库是私有的时，现场的机器人无法下载任何东西。**决定是发布它**，这解决了那个且不更改任何代码 —— 引擎使用的 API 路径对公共仓库也工作（[`updater-design.md`](../design/updater-design.md) §6.1）。

### M3 —— 真正的 `robotd` · **完成**，分两片

`robotd` 通过把 `microduck_runtime` 的控制核心抽进 `duck-control` **替换**了它，而非重新实现，因此对等作为抽取的结果到达，而非作为与一个移动目标的赛跑。切片 1 是一个真实的 50 Hz Dynamixel 循环保持其姿态 —— 这正是让 `robot.health` 意味着*循环在满足其截止期限*的东西。切片 2 是一个 61-D 观测构建器、main-plus-standing 策略、意图面，以及一个经过它的手柄客户端。

**安全权威落在这里而非 M6**，持有对总线的唯一写句柄，因此没有策略与没有客户端*能*绕过它命令电机：关节钳制、跌倒 → 松弛、以及一个意图死人开关。

**硬件优先，模拟在后** —— 且板子产生了测试无法产生的唯一一个 bug：`ort` 在一个低于其下限的运行时上*恐慌*而非报错，这杀死了控制线程并让健康责怪了错误的东西。

**完成：** 三者都在一块 Radxa Zero 3W 上。它经意图 API 被驱动走路；用 `robotctl` 应用的一次更新干净地重启它且门通过；一个起来不健康的版本自行回滚。

### M4 —— 硬件启动 · **收尾中**

一个测量里程碑，非特性里程碑：它存在是为了把猜测变成真实 Radxa 上的数字。几乎全部作为交付的副作用被回答 —— 循环在一个非 RT 内核上保持 50.0 Hz（15022 个滴答中 `missed=3`），总线与 `imu_to_dxl` 板在 `/dev/ttyS2` 上应答，温度在每个区域有真实读数，`on_apply` 中的 `systemctl restart` 对真实 systemd 工作，且门真实地提交与回滚。

**日志保留问题通过决定而非测量解决。** `/var/log` 在这个镜像是一个 zram 设备，因此 `Storage=persistent` 给 journald 一个本身在内存中的目录：它在一次干净的 `reboot` 中存活，在断电时丢失近期日志。那是预期的安排 —— 持久记录是 `/var/lib` 下的更新历史，每条目 `fsync`（[`deploy/README.md`](../../deploy/README.md)）。因此原始的"日志在断电中存活"准则被退休：它要求一个本项目决定不具有的属性。

**完成条件：** 它在硬件上走路，一次经 `robotctl` 应用的更新干净地重启 `robotd` 且门通过，且 `journalctl --list-boots` 在一次重启后报告前一次启动。前两个已完成；最后一个是板子上的一条命令，是唯一剩下的事。

**两个故意未测量的数字**，因为没有东西在等它们：eMMC 写入时序与负载下的电池。它们属于 M7，那是关于知道一块板子在做什么的里程碑。

### M5 —— `mediad`、WebRTC、SDK · **进行中**

**已落地，在硬件上。** `mediad` 在版本中交付且作为它自己的 unit 运行。摄像头通过 VPU 到达 LAN 上的浏览器 —— `mpph264enc` → `webrtcsink`，constrained baseline —— 带一个承载与每个其他传输所说相同 JSON-RPC 的 `control` 数据通道，且控制台由机器人自己服务，因此有一个 URL 且无需安装任何东西（[`remote-webrtc.md`](../design/remote-webrtc.md) §0、[`webrtc-console.md`](../design/webrtc-console.md)）。必须从源码构建两个 GStreamer 插件才能到达那里（[`media-bringup.md`](media-bringup.md)），且摄像头此后通过 `rkaiq` 得到 3A。

**三件事让它保持开放。**

**LAN 之外。** 同一个设计，前面加一个会合服务与 TURN（§7），故意作为第二个构建。

**SDK，以及一个小的 Python 客户端。** §5.3 把它设计为 WebSocket 加快照：相同的 JSON-RPC、无媒体栈、`get_frame` 返回一个 JPEG、几十行 —— 且 `mediad` 的会话层被构建以便那个面原样复用它（`mediad/src/session.rs`）。一个经 **WebRTC** 的 Python 客户端改为从一个连接获得实时视频与 `control` 数据通道，代价是 `aiortc`、一次 ICE 协商与一次信令往返，对一个只想发一个意图并读一帧的调用者。**调查是一个客户端是否覆盖两者** —— WebSocket 用于控制与快照，WebRTC 仅当调用者要求一个流时 —— 或是否仅 WebSocket 面就是一个脚本想要的，而实时视频留在控制台。在写任一个之前回答那个，因为它决定 SDK 是五十行还是一个项目。

**隐私，且现在是两项而非一项。** *同意* —— 在一个流开始前的明确逐会话批准 —— 是一个 `mediad` 会话层变更且不阻塞任何东西。*可见指示器*需要一个软件控制下的 LED，这在这个硬件上不存在（[`remote-webrtc.md`](../design/remote-webrtc.md) §11）；它是一个硬件问题，应该作为一个硬件问题被问，而非停在一个软件里程碑上。`architecture.md` §7 说得对，两者现在都便宜且以后都贵，因此同意不该等 LED。

**完成条件：** 远程临场从 LAN 外工作，且一个服务端脚本可以在几十行内取一帧并发送一个意图。

### M6 —— 交付就绪

一个陌生人需要的东西。预购已开放，因此这按**交付周期**而非难度排序 —— 代码最少的条目交付周期最长。

- **配对 PIN。** BLE 配对安全依赖一个逐机 PIN；出厂默认是 `000000` 且在本仓库公开，因此开箱即用的配对证明物理在场，别无他物。必须有东西生成一个、打印它、并记录打印了什么 —— 一个工厂流程，非补丁。它不能来自身份，身份被发布在广播中。
- **校准**，初始化的另一半。身份不再等它：一个机器人从它自己的 SoC 序列号派生一个并命名自己 `duck-c51b`。
- **恢复网，在一块板子上演练。** 它被构建并交付，且从未针对一个守护进程无法启动的版本运行过，那是唯一重要的路径。这里最便宜的条目：一块板子，一个故意坏掉的版本。
- **同意**，来自 M5。
- **清单陈旧报告**（§8.4.2）。
- **权限仲裁**，已完成 —— 包括 #52 浮出的边缘情况：`Call::is_mutating()` 不覆盖 `robot.enable`，因此那个让一个策略在一个走路的机器人上开始运行的调用被与 `hello` 归为一类。
- **app。** #107 设计它且什么都没建。阻塞是一个手机尖峰 —— 扫描、连接、`hello`、认证、开 `--require-pairing` 的 `system.info`，在一台真实 iPhone 与一台真实 Android 上 —— 因为 §5.5 目前是一个关于笔记本上 CoreBluetooth 的事实。

一个条目通过被决定离开了 M6：客户机器人从哪里下载。决定是发布这个仓库，因此一个交付的机器人无需 token 与第二个主机就能到达它的版本。它留下的后续是一个预算而非阻塞 —— 匿名 GitHub API 请求每 IP 每小时上限 60，一只鸭子远未达到，而一个 wifi 上二十只的房间不是（§6.1）。

**完成条件：** 一个非开发者从手机更新机器人，且一个故意变砖的版本无需笔记本就能恢复。

### M7 —— 知道一块板子在做什么

一只在别人手中的鸭子会出现故障，且今天对*哪个部分*的答案是一个开发者通过 ssh 读日志。还没有这个的形态；它是一个开放调查，问题是它拥有什么。

**已经存在的东西**比看起来多：`robotctl health` 报告总线、IMU、电池、每个电机温度与 SoC；`robotctl monitor` 绘制循环、手柄流、ToF 矩阵、3D 机器人与一行电源；`scripts/pad-stack-report.sh` 是把一个子系统的整个故事收集成一个人可以粘贴的东西的先例；`board-test.sh` 运行 60 个检查，但在 CI 中模拟的 aarch64 上而非你面前的板子上。

**缺失的，作为问题：**

- **一个支持包。** 一个命令，在故障后，产生一个某人可以发送的文件。没有东西把健康、版本、日志、更新历史与 unit 状态收集在一起。`robotctl update show` 是一个子系统的形态 —— 一个持久的逐运行记录，拼接了那个窗口的日志 —— 且只覆盖更新。
- **一个非开发者能运行的硬件通过/失败。** 总线扫描与每个舵机应答、IMU 健全性、ToF 存在、摄像头存在、NPU 存在、麦克风与扬声器、负载下的电池。精神上更接近 `board-test.sh`，针对硬件而非版本。
- **历史，因为间歇故障在快照中不可见。** 总线读取失败、错过滴答、舵机温度峰值、掉电。日志按设计在断电中不存活（M4），因此这里任何重要的东西需要更新历史的持久性而非日志的。
- **与 #52 的重叠。** IPC 监控器设计是同一个问题的软件半，且它的崩溃记录 —— 最后事件被刷新到 `/var/lib` 下一个固定大小的文件，在版本目录外以便它在更新与回滚中存活 —— 正是一个硬件故障报告需要的持久性属性。两者应该一起决定而非长出两个答案。

M4 的两个未测量数字落在这里：eMMC 写入时序与负载下的电池。

**完成条件：** 一个非开发者在故障后可以运行一个命令并产生一个命名故障部件的东西，或说硬件没问题。

### M8 —— 模型通道：来自 Hub 的策略

今天每个策略**在守护进程产物内部**交付 —— `robotd` 加载 `.../current/policies/alpha_walking.onnx` 及伙伴 —— 因此一个新步态需要一个守护进程版本，且一个在笔记本上训练的策略只能通过 CI 或整个守护进程的侧载到达一只鸭子。这个里程碑的要点是，一个在 `microduck_rl` —— 训练仓库，私有的 —— 中训练的策略可以在它自己的版本线上被发布、安装、试用与回滚。

**引擎是为那种安排设计的，且大部分已经构建：**

- `hf_hub` 源解析 `https://huggingface.co/{repo}/resolve/{revision}/{file}` 并验证**我们自己的** minisign 签名，因为 HF 不为我们签名任何东西（§5.1）；
- 一个模型是一个普通组件 —— 它自己的版本线、安装目录、回滚目标、pin、启动计数器试用与已知坏历史。`robotctl update apply model-walk` 与 `robotctl update select model-walk 1.1.0` 在配置了一个之后立即工作（§5.5）；
- `on_apply = { action = "reload", unit = "robotd", signal = "SIGHUP" }` 在引擎中已实现，因此一次权重交换不必重启电机控制；
- `xtask sign` 已经签名任何产物目录。

**缺失的在两端，不在中间：**

- **`robotd` 无法重载。** 没有 SIGHUP 处理器且没有办法在一个运行中的 50 Hz 循环下交换一个 `ort` 会话。这是里程碑真正的工程：交换不能丢一个滴答，且一个形态不是 `obs[1,61] → actions[1,14]` 的模型必须在它上线*之前*被拒绝，而非在第一次推理时。
- **没有东西发布一个包。** `xtask package --channel model-walk` 接近 —— 它把 `--version` 对照 crate 版本检查，而一个模型没有 —— 且 HF 仓库布局与命名不存在。
- **第三把签名密钥。** `release-1` 是 CI 的，`team.dev` 不在客户机器人上安装任何东西，因此*谁可以发布一个机器人会运行的策略*是一个新的保管问题，非对现有一个的复用。
- **`model_api`**（§5.5）已设计且两边都未实现。
- **训练循环。** `microduck_rl` 训练并导出到 ONNX；没有东西把结果带到一块板子上而无需一个守护进程版本。`dev-push.sh` 的模型等价物正是让"训练它并试试"变成一分钟而非一次 CI 运行的东西。

**看看别人做了什么**是需求的另一半，且它落在信任模型而非管道上。我们自己的策略是基础的且我们签名它们；一个陌生人的被这个机器人不信任的任何人签名，且引擎安装的每个产物都对照一个受信任密钥验证。三件事与里程碑一起而非之后解决：

- **策展或开放。** 一个发布到我们为之签名的组织中的模型保留组件系统已经给出的每个保证 —— 回滚、pin、已知坏、健康门 —— 且不花新代价。一个开放集合需要一个明确未验证的安装路径：默认关闭、永不自动应用，且像 `allow_dev_keys` 已经拒绝 dev 构建那样在客户机器人上被拒绝。
- **形态门停止是一个美好事物。** `obs[1,61] → actions[1,14]` 必须在一个模型上线前被检查，无论谁签名，因为一个任意策略驱动十五个舵机。
- **让它可存活的东西已经构建。** 安全层持有对总线的唯一写句柄 —— 关节钳制、跌倒 → 松弛、一个意图死人开关 —— 因此一个坏策略是有界的而非危险的。那是允许一个陌生人模型的论点。

**槽保持固定，源不固定。** `walk`、`stand`、`kick_left` 及其余是有自己版本线的组件；"寻找其他"是一个对 Hub 的查询，寻找为这个机器人标记的模型，加上把一个槽的源重指向另一个仓库。让任意组件在运行时出现意味着配置不再是一个机器人可以运行什么的权威，那是整个组件设计赖以成立的属性。

**一个决定先于所有这一切，且倾向是策略离开产物。** 两件事随之而来，且两者都不是逆转它的理由：

- 一块刚刷好且没有网络的板子没有步态。
- 更尖锐的一个：`robotd` 在一个它想要的策略无法加载时报告**不健康**（`deploy/robotd.toml`，`[policy] enabled`），因此在一块没有安装模型的板子上，每个后续的守护进程更新都会失败其健康门并回滚 —— 一个由一个更新本无法提供的缺失文件引起的更新循环。

两者都有已经存在的答案：

- **一个缺失的模型是 `degraded`，非不健康。** `HealthResult::degraded` 正是为这个形态构建的 —— 一个作为*板子*属性而非被门控版本属性的情况，那里回滚守护进程无法修复它且只会搅动启动计数器。哪些模型组件被安装正是那个，因此门提交且 `robotctl health` 说哪个策略缺失。
- **初始化安装引导集**，如 `setup-board.sh` 已经安装 ONNX 运行时与 `setup-gstreamer.sh` 安装插件那样。网络依赖落在一个已经存在的地方，且运行时一个策略恰好有一个源 —— 组件的安装目录 —— 版本副本与 Hub 副本之间无优先规则。

替代方案 —— 版本保留其副本作为一个 Hub 组件覆盖的下限 —— 买到一只完全无网络也能走路的鸭子，代价是一个文件的两个源与一个关于谁赢的规则。如果初始化时引导证明脆弱，它仍在桌面上。

这个里程碑*不*继承 M6 的下载问题：Hub 是公开的，无论源仓库做什么。

**完成条件：** 一个在 `microduck_rl` 中训练的策略被发布到 Hub，用 `robotctl update apply model-walk` 安装到一只鸭子，并用 `robotctl update select` 回滚 —— 控制循环在两者中都不丢一个滴答 —— 且一个没训练它的人可以从机器人找到它并试用。

### M9 —— 自主大脑

最大的未追踪缺口：运行时的 `autonomous.rs` 在守护进程中无处存在，且没有设计文档负责它。[`ideas/autonomous_behavior.md`](../ideas/autonomous_behavior.md) 是暂存区 —— 一个基于能量/心情模型的 16 状态机、新颖度网格探索、ToF 避让、惊吓、声音反应、玩球、小睡周期、抚摸。

它需要的每个输入现在都存在，且一些它从未有过：环境声音事件、深度帧、分类后的躯干帧障碍点、语音标签、按稳定 id 的附近鸭子、一个共享节拍、作为粗粒度距离的 RSSI、一个实时合成器音色、来自 ToF 的手距离。

**形态比状态更重要。** 在场、心情与节拍是*一个大脑的输入*，而非其旁的模式。chorale 与泰勒明琴作为显式模式增长是因为没有大脑可以挂载它们 —— chorale 是 55 KB 的 `robotd` —— 且那是这个里程碑存在以阻止重复的模式。它先得到一个设计文档，再得到代码。

**完成条件：** 一只被单独留在房间里的鸭子做一些值得看十分钟的事，且 chorale 是它决定的东西而非一个命令启动的东西。

## 工作顺序

上面的数字是标识符。这是顺序。

1. **M8，模型通道。** 下一个特性。没有其他东西被它阻塞，且它解锁产生机器人实际行为的循环：训练、发布、安装、试用、回滚。
2. **M5 的传输调查。** 便宜，且它的答案决定 Python 客户端是五十行还是一个项目。
3. **M6，随着交付临近**，按交付周期：客户机器人从哪里下载，然后 PIN，然后恢复网的硬件测试。同意可以任何时候落地且应该早落地。
4. **M7** —— 一个无日期的调查。它在第一次一只在别人手中的鸭子出现一个没人能命名的故障时赢得优先级，且准备好的最便宜方式是与 #52 一起而非之后决定它。
5. **M9，大脑** —— 稍后，故意。它是剩下的最大块工作且最可能在构建时增长。

1. ~~**签名密钥保管**~~ —— 守护进程的**已完成**。三把加密的发布密钥加一把未加密的 dev 密钥在 `~/.duck-keys`；只有 `release-1` 进入 secrets。发布在 CI 中在 `environment: release` 下签名，这限定 secrets 但**不门控任何东西** —— 无必需审查者，无分支策略。在现场没有机器人时被故意接受，且该声明是一个用一次设置变更打开真正闸门的钩子。见 [`ci-setup.md`](ci-setup.md)。**随 M8 重新打开**：发布一个策略是第三类密钥。

## 我们在哪里

| | |
|---|---|
| `updater/` | 引擎、验证、存储、日志、钩子、预检、GitHub/HF/本地来源、IPC 服务器、systemd 单元——**完成** |
| `duck-control/` | 机器人模型 · 总线 · IMU · `RobotIo` · 观察 · ONNX 策略 · 安全。一个库：没有 tokio，没有 socket，没有 systemd |
| `duck-ipc-proto/` | 每个 `*.` 命名空间的线路契约，API v14——只有 serde/serde_json/semver，因此恢复路径上的任何东西都不拉入引擎的树 |
| `robotd/` | 一个 50 Hz 循环，通过安全层驱动行走/站立/翻滚，意图，来自截止遵守和策略状态的健康。自 M3 起：运动学、接触里程计、凝视 IK、语音、ToF 特雷门琴和合唱，全部挂在同一个滴答上（[`robotd-design.md`](../design/robotd-design.md) §4.4–4.5） |
| `padd/` | 手柄 → 意图，作为普通 socket 客户端；在 release 中交付并从启动起作为自己的单元运行，因此配对手柄是唯一的步骤 |
| `robotctl/` | 操作员 CLI——`update`、`health`、`version`、`monitor`、`net`、`system`、`robot`、`pad`、`configure`、`quack`、`chorale`、`theremin`、`completions`；依赖 `duck-ipc-proto`，不依赖 `updater`，因此它保持在恢复路径上 |
| `configd/` | 通过 NetworkManager 的 wifi，机器人名称和从 SoC 序列号派生的身份，配对 PIN，重启，单元报告。`--fake-net` 在板外服务整个界面 |
| `btd/` | BLE 传输适配器——成帧、路由子集、BlueZ 后端、配对代理。在硬件上工作，默认未加密——[`app-path-design.md`](../design/app-path-design.md) §5.5 |
| `duckctl/` | 从笔记本控制机器人。今天是 BLE；以机器人而非无线电命名 |
| `mediad/` | 摄像头、麦克风、编码和 WebRTC 网关，加上它服务的控制台。**从 Radxa Zero 3W 向 LAN 上的浏览器流式传输**，通过 `mpph264enc` 的硬件 H.264，旁边有 `control` 数据通道 |
| `tof/` | `tofd`：头部的 8×8 ToF 矩阵在自己的 socket 上以 15 Hz 运行。没有安装传感器的板仍然运行它并说明情况 |
| `xtask/` | 打包 · 签名 · 升级——字节相同的升级已验证 |
| `.github/` | ci · release · promote · dev——四个都真实运行；自 `0.2.0` 以来的每个发布都通过它们到达了一块板 |
| bootstrap | `updaterd install` + `scripts/install.sh`——机器人通过**普通引擎**安装其第一个发布，因此没有 bootstrap-only 代码路径会漂移 |
| recovery | `robot-boot-check.timer` + `robot-rescue` + `golden` 符号链接交付并启用。**从未在板上演练过**（[`boot-recovery-net.md`](../design/boot-recovery-net.md)） |
| tests | **942 个通过**，在 Mac 上没有排除任何东西，在 Linux 上还有几个——包括健康门、电池和温度读数，以及针对真实 `robotd` 进程的策略/安全路径，还有 `configd` 在 `board-test.sh` 中通过真实 socket 的授权 |
| in flight | `maploc` (#127)、NPU 鸭子检测器、合唱选举修复 (#151)；两个没有构建任何东西的设计 PR——手机应用 (#107) 和 IPC 监控器 (#52) |
| missing | 应用、SDK、模型通道、自主大脑，以及从 LAN 外到达机器人 |

## 第一条路线图达到了它的目标

M1 到 M4 是一个序列，有一个目的地：一个会走路、能空中自我更新、且不会因此变砖的机器人。那已经到达了。自 `0.2.0` 以来的每个发布都通过 M1 和 M2 构建的机器到达了一块板，而 `0.9.x` 是一只会走路、会翻滚、能看见、会说话和会唱歌的鸭子。

接下来的不是那个队列的延续。剩下的工作是独立的轨道，有不同的风险，它们之间没有顺序，因此**下面的数字是标识符，不是序列**——[工作顺序](#the-order-of-work) 是它自己的章节。

**创始主张对了一半。** *困难的部分是产品化，而不是能力*正确判断了难度：更新路径、健康门、恢复网和 BLE 界面都被构建了，而且都成立。它判断错了体量。自 `0.5` 以来几乎所有东西都是能力——运动学、里程计、ToF、凝视、语音、合唱、摄像头——而其中最大的一块，自主大脑，仍未移植。

## 里程碑

每个都有一个说"完成"的测试，因为没有测试的里程碑会漂移。

### M1 — 闭环 · **完成**

更新器有了真实的东西来门控，团队有了共享的 crate 边界：一个状态是原子而非互斥锁的 `robotd` 骨架（循环被卡住的机器人必须仍然能回答*我不健康*），`duck-ipc-proto` 被提取出来，因此恢复路径上的任何东西都不链接引擎的 http/tar/crypto 树，一个是真实 socket 探测的健康门，`robotd` socket 的唯一真相来源，每个守护进程在任何东西可能失败之前以 `warn` 记录的身份行，以及通过普通引擎的首次安装 bootstrap。

**完成：** `robotd/tests/updater_gate.rs` 针对真实 `robotd` 进程通过真实 socket 门控一次更新并提交；`robotd --unhealthy` 回退 `current` 背后的内容。

### M2 — 开发通道 · **完成**

`sudo robotctl update apply daemon --ref my-branch` 安装一个分支构建，`scripts/dev-push.sh` 通过 ssh 安装笔记本构建，完全不需要 CI 运行。两个属性使这在每次推送时都是安全的，两者都在工作流之外强制执行：开发构建**不能变成 `latest`**（版本是 semver 预发布，`version_under` 拒绝将 dev tag 读取为发布版本），并且它**不能安装在客户机器人上**（那里 `allow_dev_keys` 为 false，而受信任密钥只有在文件名以 `.dev.pub` 结尾时才算作 dev 密钥）。

**完成：** 针对真实仓库验证——`dev.yml` 已发布，`--ref main` 通过网络安装，客户机器人配置拒绝了相同的构建。

**它留下的一个开放问题，现在已决定：** 私有仓库的发布资产可以用 token 访问，而客户机器人没有，因此当这个仓库是私有时，现场的机器人无法下载任何东西。**决定是公开它**，这解决了那个问题且不改变任何代码——引擎使用的 API 路径对公开仓库也有效（[`updater-design.md`](../design/updater-design.md) §6.1）。

### M3 — 真实的 `robotd` · **完成**，分两片

`robotd` **替换**了 `microduck_runtime`，通过将其控制核心提取到 `duck-control` 而不是重新实现它，因此对等性作为提取的结果到达，而不是作为与移动目标的竞赛。Slice 1 是一个真实的 50 Hz Dynamixel 循环保持其姿势——这就是使 `robot.health` 意味着*循环在满足其截止时间*的原因。Slice 2 是一个 61-D 观察构建器、主加站立策略、意图界面，以及一个经过它的手柄客户端。

**安全权威落在这里而不是 M6**，持有对总线的唯一写句柄，因此没有策略和没有客户端*能*绕过它命令电机：关节钳制、跌倒→松弛，以及意图 deadman。

**硬件优先，仿真在后**——而板产生了测试无法产生的一个 bug：`ort` 在运行时低于其下限时*崩溃*而不是报错，这杀死了控制线程并使健康归咎于错误的东西。

**完成：** 三者都在 Radxa Zero 3W 上。它通过意图 API 被驱动行走；用 `robotctl` 应用的更新干净地重启它且门通过；一个启动不健康的发布自己回退。

### M4 — 硬件启动 · **收尾中**

一个测量里程碑，不是功能里程碑：它的存在是为了在真实 Radxa 上把猜测变成数字。几乎所有内容都作为发布的副作用被回答了——循环在非 RT 内核上保持 50.0 Hz（15022 个滴答中 `missed=3`），总线和 `imu_to_dxl` 板在 `/dev/ttyS2` 上应答，温度在每个区域都有真实读数，`on_apply` 中的 `systemctl restart` 对真实 systemd 工作，门真实地提交和回退。

**日志保留问题是通过决定而非测量解决的。** `/var/log` 在这个镜像上是一个 zram 设备，因此 `Storage=persistent` 给 journald 一个本身在内存中的目录：它在干净的 `reboot` 后幸存，在断电时丢失最近的日志。这是预期的安排——持久记录是 `/var/lib` 下的更新历史，每个条目都 `fsync`（[`deploy/README.md`](../../deploy/README.md)）。因此最初的"日志在断电后幸存"标准被退役：它要求的是这个项目决定不拥有的属性。

**完成条件：** 它在硬件上行走，通过 `robotctl` 应用的更新干净地重启 `robotd` 且门通过，以及 `journalctl --list-boots` 在重启后报告上一次启动。前两项已完成；最后一项是板上的一条命令，是唯一未完成的事情。

**两个故意未测量的数字**，因为没有东西在等它们：eMMC 写入时序和负载下的电池。它们属于 M7，那是关于知道板在做什么的里程碑。

### M5 — `mediad`、WebRTC、SDK · **进行中**

**已落地，在硬件上。** `mediad` 在 release 中交付并作为自己的单元运行。摄像头通过 VPU 到达 LAN 上的浏览器——`mpph264enc` → `webrtcsink`，受限 baseline——带有承载与每个其他传输所说相同 JSON-RPC 的 `control` 数据通道，控制台由机器人自己服务，因此有一个 URL 且不需要安装任何东西（[`remote-webrtc.md`](../design/remote-webrtc.md) §0，[`webrtc-console.md`](../design/webrtc-console.md)）。两个 GStreamer 插件必须从源码构建才能到达那里（[`media-bringup.md`](media-bringup.md)），摄像头此后通过 `rkaiq` 获得了 3A。

**三件事让它保持开放。**

**LAN 外。** 前面有会合服务和 TURN 的相同设计（§7），故意第二个构建。

**SDK，以及一个小的 Python 客户端。** §5.3 将其设计为 WebSocket 加快照：相同的 JSON-RPC，没有媒体栈，`get_frame` 返回 JPEG，几十行——而 `mediad` 的会话层被构建为该界面不加修改地复用它（`mediad/src/session.rs`）。一个通过 **WebRTC** 的 Python 客户端反而从一个连接获得实时视频和 `control` 数据通道，代价是 `aiortc`、ICE 协商和一个只想要发送意图和读取帧的调用者的信令往返。**调查是一个客户端是否能覆盖两者**——WebSocket 用于控制和快照，WebRTC 仅在调用者要求流时——或者是否单独的 WebSocket 界面就是脚本想要的，而实时视频留在控制台中。在写任何一个之前回答这个，因为它决定 SDK 是五十行还是一个项目。

**隐私，现在是两项而不是一项。** *同意*——在流开始之前明确的每会话批准——是 `mediad` 会话层变更，不被任何东西阻塞。*可见指示器*需要一个软件控制下的 LED，这在这个硬件上不存在（[`remote-webrtc.md`](../design/remote-webrtc.md) §11）；它是一个硬件问题，应该向硬件提出而不是停在软件里程碑上。`architecture.md` §7 说得对，两者现在都便宜以后都贵，因此同意不应该等待 LED。

**完成条件：** 远程呈现从 LAN 外工作，服务器端脚本可以在几十行内获取一帧并发送意图。

### M6 — 交付就绪

陌生人需要的东西。预购已开放，因此这按**交付周期**而非难度排序——代码最少的项目交付周期最长。

- **配对 PIN。** BLE 配对安全依赖于每机器人 PIN；出厂默认是 `000000` 且在这个仓库中公开，因此开箱配对证明物理存在，仅此而已。必须有东西生成一个、打印它、并记录打印了什么——一个工厂流程，不是一个补丁。它不能来自身份，身份在广播中公开。
- **校准**，配置的另一半。身份不再等待它：机器人从自己的 SoC 序列号派生一个并命名自己 `duck-c51b`。
- **恢复网，在板上演练。** 它已构建并交付，从未针对一个守护进程无法启动的发布运行过，这是唯一重要的路径。这里最便宜的项目：一块板，一个故意损坏的发布。
- **同意**，来自 M5。
- **清单陈旧报告**（§8.4.2）。
- **权限仲裁**，已完成——包括 #52 暴露的边缘情况：`Call::is_mutating()` 不覆盖 `robot.enable`，因此在行走的机器人上启动策略运行的调用与 `hello` 归为一类。
- **应用。** #107 设计它且什么都没构建。阻塞因素是一个手机尖峰——扫描、连接、`hello`、认证、`system.info` 且 `--require-pairing` 开启，在真实 iPhone 和真实 Android 上——因为 §5.5 目前是关于笔记本上 CoreBluetooth 的事实。

一个项目通过被决定离开了 M6：客户机器人从哪里下载。决定是公开这个仓库，因此已交付的机器人不需要 token 和第二个主机就能到达其发布。它留下的后续是预算而非阻塞——匿名 GitHub API 请求每 IP 每小时上限 60，一只鸭子远达不到，而一个 wifi 上二十只的房间也达不到（§6.1）。

**完成条件：** 非开发者从手机更新机器人，一个故意变砖的发布在没有笔记本的情况下恢复。

### M7 — 知道板在做什么

一只在别人手里的鸭子会出现故障，而今天对*哪个部分*的回答是开发者通过 ssh 读取日志。这还没有形状；它是一个开放调查，问题是它拥有什么。

**已经存在的**比看起来多：`robotctl health` 报告总线、IMU、电池、每电机温度和 SoC；`robotctl monitor` 绘制循环、手柄流、ToF 矩阵、3D 机器人和电源行；`scripts/pad-stack-report.sh` 是将一个子系统的整个故事收集成一个人可以粘贴的东西的先例；`board-test.sh` 运行 60 项检查，但是在 CI 中的模拟 aarch64 上而不是在你面前的板上。

**缺少什么，作为问题：**

- **支持包。** 一条命令，在故障后，产生一个人可以发送的文件。没有东西将健康、版本、日志、更新历史和单元状态收集在一起。`robotctl update show` 是一个子系统的形状——一个持久的每次运行记录，拼接了该窗口的日志——且只覆盖更新。
- **非开发者可以运行的硬件通过/失败。** 总线扫描和每舵机应答、IMU 健全性、ToF 存在、摄像头存在、NPU 存在、麦克风和扬声器、负载下的电池。精神上更接近 `board-test.sh`，针对硬件而非发布。
- **历史，因为间歇性故障在快照中不可见。** 总线读取失败、错过的滴答、舵机温度峰值、欠压。日志按设计在断电后不幸存（M4），因此这里重要的任何东西都需要更新历史的持久性而不是日志的。
- **与 #52 的重叠。** IPC 监控器设计是同一个问题的软件一半，它的崩溃记录——刷新到 `/var/lib` 下固定大小文件的最后事件，在发布目录之外因此它在更新和回退后幸存——正是硬件故障报告需要的持久性属性。两者应该一起决定，而不是长出两个答案。

M4 的两个未测量数字落在这里：eMMC 写入时序和负载下的电池。

**完成条件：** 不是开发者的人可以在故障后运行一条命令并产生一个命名故障部件的东西，或者说硬件没问题。

### M8 — 模型通道：来自 Hub 的策略

今天每个策略都**在 daemon 制品内部**交付——`robotd` 加载 `.../current/policies/alpha_walking.onnx` 等——因此新步态需要 daemon 发布，在笔记本上训练的策略只能通过 CI 或整个 daemon 的侧载到达鸭子。这个里程碑的要点是，在 `microduck_rl`——训练仓库，是私有的——中训练的策略可以在自己的版本线上发布、安装、试用和回退。

**引擎是为这种安排设计的，大部分已经构建：**

- `hf_hub` 来源解析 `https://huggingface.co/{repo}/resolve/{revision}/{file}` 并验证**我们自己的** minisign 签名，因为 HF 不为我们签名任何东西（§5.1）；
- 模型是普通组件——它自己的版本线、安装目录、回退目标、pin、启动计数器试验和已知坏历史。`robotctl update apply model-walk` 和 `robotctl update select model-walk 1.1.0` 在配置了一个的那一刻就工作（§5.5）；
- `on_apply = { action = "reload", unit = "robotd", signal = "SIGHUP" }` 在引擎中实现，因此权重交换不必重启电机控制；
- `xtask sign` 已经签名任何制品目录。

**缺少的在两端，不在中间：**

- **`robotd` 不能重新加载。** 没有 SIGHUP 处理程序，也没有办法在运行的 50 Hz 循环下交换 `ort` 会话。这是这个里程碑真正的工程：交换不能丢一个滴答，而形状不是 `obs[1,61] → actions[1,14]` 的模型必须在它上线*之前*被拒绝，而不是在第一次推理时。
- **没有东西发布包。** `xtask package --channel model-walk` 很接近——它对照 crate 版本检查 `--version`，而模型没有——且 HF 仓库布局和命名不存在。
- **第三个签名密钥。** `release-1` 是 CI 的，`team.dev` 在客户机器人上什么都不安装，因此*谁可以发布机器人会运行的策略*是一个新的托管问题，不是对现有问题的复用。
- **`model_api`**（§5.5）已设计且在两端都未实现。
- **训练循环。** `microduck_rl` 训练并导出到 ONNX；没有东西在没有 daemon 发布的情况下将结果带到板上。模型等效的 `dev-push.sh` 是使"训练它并试用它"变成一分钟而不是一次 CI 运行的东西。

**看看其他人做了什么**是需求的另一半，它落在信任模型上而不是管道上。我们自己的策略是基础的且我们签名它们；陌生人的策略由这个机器人不信任的任何人签名，而引擎安装的每个制品都对照受信任密钥验证。三件事要与里程碑一起而不是之后解决：

- **策展还是开放。** 发布到我们签名的组织中的模型保留组件系统已经给出的每个保证——回退、pin、已知坏、健康门——且不需要新成本。开放集合需要一个明确未验证的安装路径：默认关闭，永远不自动应用，并且像 `allow_dev_keys` 已经拒绝 dev 构建一样在客户机器人上拒绝。
- **形状门不再是锦上添花。** `obs[1,61] → actions[1,14]` 必须在模型上线前检查，无论谁签名它，因为任意策略驱动十五个舵机。
- **使它可存活的东西已经构建。** 安全层持有对总线的唯一写句柄——关节钳制、跌倒→松弛、意图 deadman——因此坏策略是有界的而不是危险的。这就是允许陌生人模型的根本理由。

**槽位保持固定，来源不固定。** `walk`、`stand`、`kick_left` 等是有自己版本线的组件；"寻找其他"是对 Hub 上标记为适用于此机器人的模型的查询，加上将一个槽位的来源重指向另一个仓库。让任意组件在运行时出现将意味着配置不再是机器人可以运行什么的权威，这是整个组件设计所依赖的属性。

**一个决定先于所有这一切，倾向是策略离开制品。** 随之而来两件事，两者都不是推翻它的理由：

- 刚刷入且没有网络的板没有步态。
- 更尖锐的一个：`robotd` 在它想要的策略无法加载时报告**不健康**（`deploy/robotd.toml`，`[policy] enabled`），因此在没有安装模型的板上，每个后续的 daemon 更新都会失败其健康门并回退——一个由更新无法提供的缺失文件引起的更新循环。

两者都有已经存在的答案：

- **缺失的模型是 `degraded`，不是不健康。** `HealthResult::degraded` 正是为这种形状构建的——一个是*板*的属性而不是被门控的发布的属性的条件，回退 daemon 无法修复它且只会搅动启动计数器。哪些模型组件被安装正是那样，因此门提交且 `robotctl health` 说明哪个策略缺失。
- **配置安装引导集**，就像 `setup-board.sh` 已经安装 ONNX Runtime 和 `setup-gstreamer.sh` 安装插件一样。网络依赖落在一个已经存在的地方，且在运行时策略恰好有一个来源——组件的安装目录——发布副本和 Hub 副本之间没有优先级规则。

替代方案——发布保留其副本作为 Hub 组件覆盖的底线——换来一只完全没有网络也能走路的鸭子，代价是一个文件的两个来源和一个关于哪个赢的规则。如果配置时的引导被证明脆弱，它仍然在桌面上。

这个里程碑*不*继承 M6 的下载问题：无论来源仓库做什么，Hub 是公开的。

**完成条件：** 在 `microduck_rl` 中训练的策略发布到 Hub，用 `robotctl update apply model-walk` 安装到鸭子上，并用 `robotctl update select` 回退——整个过程中控制循环从不丢一个滴答——且没有训练它的人可以从机器人找到它并试用。

### M9 — 自主大脑

最大的未跟踪缺口：runtime 的 `autonomous.rs` 在 daemon 中不存在，没有设计文档拥有它。[`ideas/autonomous_behavior.md`](../ideas/autonomous_behavior.md) 是暂存处——一个基于能量/情绪模型的 16 状态机、新奇网格探索、ToF 避障、惊吓、声音反应、玩球、午睡周期、抚摸。

它需要的每个输入现在都存在，有些它从未有过：环境声音事件、深度帧、分类的躯干帧障碍点、语音标签、按稳定 id 的附近鸭子、共享节拍、作为粗距离的 RSSI、实时合成语音、来自 ToF 的手距离。

**形状比状态更重要。** 存在、情绪和节拍是*一个大脑的输入*，而不是它旁边的模式。合唱和特雷门琴作为显式模式生长，因为没有大脑可以挂它们——合唱是 `robotd` 的 55 KB——这就是这个里程碑存在以停止重复的模式。它在得到代码之前先得到设计文档。

**完成条件：** 一只独自留在房间里的鸭子做一些值得看十分钟的事情，且合唱是它决定的东西而不是命令启动的东西。

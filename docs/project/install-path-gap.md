# 安装路径没有测试

状态：已关闭 · 日期：2026-08-05，2026-08-07 与 2026-08-11 修订 · 负责人：pierre

连续四个 bug 到达了一块板子，全在安装路径中，没有一个被 418 个测试或 `board-test.sh` 捕获。本文记录为什么，以及什么关闭了它。它教给的一般规则 —— 全新安装对一块板子做的任何事也属于一个 hook，因为那是唯一在每次更新时在每块板子上运行的东西 —— 超出了本文档，现在位于 `updater-design.md` §9.1。**那是该读的地方；本页是故事，不是规则。** 自那以后它又被弄错了两次，因此在添加一个安装步骤之前而非之后读 §9.1 是值得的。同一天写的，当时原因仍具体，且保持在它赢得的过去时态中而非重写为参考 —— 它现在有用的是错误的形态，而非树的状态。

第二节覆盖两个*看起来*像同一件事但不是的发现：一个已经运行的守护进程与一个刚安装的版本之间的版本偏差。两者都不会被任何数量的安装测试捕获，且它们需要自己的修复 —— 放在这里而非它们自己的文档中，因为任何调查其中一个的人都会相信它是另一个。

**修订注。** 所有四个 bug 都已修复，其后的版本偏差部分也是：案例 1 的 `serde(default)` 纪律落地，案例 2 的握手提议被*否决*且其推理被写下来，"units 比安装它们的版本活得更久"的后果现在是一个拒绝而非涌现行为。

**且标题命名的缺口已关闭。** 一个测试安装一个真实产物 —— `board-test.sh` 解包一个并对它运行 `install.sh` 与 `hooks/postinstall` —— 每个 unit 的 `ExecStart` 二进制都对照交付它的 tarball 检查，一次板子检查在每个 `dev-push.sh` 上运行，且 `scripts/systemd-test.sh` 对真实 systemd 驱动一次真实更新。这些来自的计划在下面，每个发现了什么；两个引擎 bug 被最后一个发现。

自第一稿以来的一个变动足以挪动本文档的足够内容，值得在此指出：`updaterd` 与 `btd` 现在在更新应答后几秒*才*重启（`RESTART_AFTER_REPLYING`），且版本自己的 `updaterd` 被证明在提交前启动（`updaterd --self-test`）。下面两个主张是针对旧行为写的，现在为假 —— 两者都已就地纠正，尤其是第二节的前提不再成立。

**第二次修订注。** §4 的偏差部分现在由代码而非论点关闭。每个守护进程发布它在运行什么（`duck_ipc_proto::publish_identity`），`updaterd` 在每次启动时把每个 unit 与活动版本比较并重启过时的（`updater/src/reconcile.rs`、`Engine::reconcile_running_units`）。下面还有两个主张在写时为真现在不为真：运行/安装不匹配是未决定的，以及 `btd` 的运行修订无法读取。两者都已就地纠正。`docs/design/restart-order.md` §5 与 §7 负责该机制以及如何读取偏差；留在这里的是为什么需要它。

## 什么通过了

全部四个都在一天内落地，全是在把 `btd` 与 `configd` 安装到一块 dev 板上时。（数量在添加下面的 §4 之前读为"三个"。）

**1. `on_apply` 在一个命令中重启多个 unit。** 如果*任一* unit 未知，`systemctl restart robotd configd` 整体失败 —— 且不重启存在的那个就失败。因此一个引入新守护进程的版本无法重启任何东西，因为 unit 文件*随*该版本到达，且没有东西安装它。回滚原因是 `not healthy within 30s: unreachable`，既不命名 unit 也不命名命令。

潜伏的而非致命的，因为一块板子保留它自己的 `/etc/robot/updater.toml`。

修了两次，第二次是真正的修复。首先，防御性地：unit 一次重启一个，且 systemd 不认识的 unit 被跳过。然后正确地：**`hooks/postinstall` 安装版本的 unit。** 引擎一直有一个安装后钩子点 —— `extract → [pre_install] → swap → [post_install] → apply → health gate` —— 它在 `current` 移动后运行，因此 `ExecStart` 解析，且在重启前，因此 `on_apply` 找到一个存在的 unit。没有东西使用它；只有 `scripts/install.sh` 曾从一个版本中复制 unit，因此每个新服务都需要在每块板子上的一个手动步骤，永远。该机制存在却未被使用是在 review 中指出的，不是我发现的。

**2. 产物不包含新 unit。** 打包工作流用一个显式的 `--include` 命名每个交付的文件，而 unit 被添加到 `install.sh` 却没有被添加到那里。手动发现：板子上的 `ls current/systemd/`。

**3. 产物不包含新二进制。** Package 步骤用每个二进制一个显式的 `cp` 复制二进制。`cargo board --bins` 构建了 `btd` 与 `configd`；没有东西暂存它们。`btd.service` 以 `203/EXEC` 失败，这读起来像一个坏掉的守护进程而非一个不完整的产物。

Bug 3 与 bug 2 同类，在同一文件中，**在添加了一个阻止 bug 2 复发的测试之后两个提交** —— 那个测试检查 unit 而不检查它们 exec 的二进制。每个修复都是正确的且每个都太窄，这是值得攻击的模式而非 bug。

**4. `on_apply` 的重启列表活在板子上，因此一个新守护进程永远不被重启。** · **measured** 代价最高的一个，且已经在这里作为"潜伏的而非致命的"写下来。

`[component.daemon.on_apply].units` 从 `/etc/robot/updater.toml` 读取 —— 那是*操作者的*文件，`install.sh` 故意保留它。`configd` 在引入它的分支中被添加到随附的 `deploy/updater.toml`，因此在那之前设置的板子永远保持 `units = ["robotd"]`。因此每个 `configd` 版本都交换了二进制并让旧进程继续运行。

让它花了两小时而非两分钟的是失败的形态：

- 更新报告**成功** —— 交换发生了，健康门通过了，没有东西失败；
- `robotctl update apply` 然后报告 **`already_current`** 且什么都不做，因此明显的恢复命令是空操作；
- 守护进程继续应答，用旧代码，因此它看起来像修复错了而非缺失。四个 wifi 修复被对照从未运行的二进制验证为坏掉。

`robotctl version` *确实*诊断这个，逐字地："configd is running X but the installed daemon release is Y … either the restart did not happen, or it failed"。没人运行它。一个存在却不被求助的诊断与一个不存在的诊断价值一样多，这是一个让更新自己注意到而非更多诊断的论点。

**已修复**（`engine.rs::units_to_restart`）：重启集从版本的 `systemd/*.service` 文件派生，与配置命名的任何东西取并集，减去 `updaterd` 与 `btd` —— 它们从一个由测试强制执行的配置约定变成代码中的 `NEVER_RESTART` 常量，因为它们是那些守护进程本质的属性而非操作者选择。一个 `updater.toml` 早于某个守护进程的板子现在仍会重启它，且无需编辑。下面是推理，保留因为它是此类列表归属的论点。

**从版本而非板子派生重启集。** 一个版本交付 `systemd/*.service`，因此它已经声明它提供哪些 unit —— 与让 `hooks/postinstall` 成为*安装*它们的正确答案是同一个领悟。引擎可以重启版本交付的东西，减去两个有文档的排除（`updaterd`，正在执行更新的；`btd`，可能是更新被请求所经由的传输）。然后一个添加守护进程的版本在每块板子上重启那个守护进程，无需操作者编辑，也无法让板子的配置静默过时。

两个较小的选项在此作为上面的同伴而非替代被记下：`apply` 可以获得一个 `--force`，在一个已经当前的版本上重新运行 hook 与重启（有先例 —— `install --force` 为同类鸡生蛋问题存在），且 `already_current` 可以比较*运行*修订而非仅安装的，因此它恰好在有东西出错时停止是空操作。

**第二个有了答案，且不在它被提出的地方。** 它真正提出的问题是一个运行/安装不匹配应该被报告并拒绝还是被修复，答案是修复 —— 由 `updater/src/reconcile.rs`，它在每次 `updaterd` 启动时运行而非在 `apply` 内部。每个 unit 的运行版本来自其进程发布的身份文件，与它的组件有什么活动比较，任何过时的都被重启。由于 `updaterd` 在每次应用更新后五秒重启自己，那个检查在每次 `apply` 后几秒运行，因此本节关于的状态现在在 `Engine::apply` 不变的情况下自愈。

那留下的比任一书写的选项都窄，且现在也关闭了。`reconcile` 故意不修复一种偏差 —— `updaterd` 自己的，因为在拥有恢复的进程中的一个自重启循环是唯一一个无路可走的失败 —— 而那在单个案例中遇到了一个仅在安装版本上返回 `AlreadyCurrent` 的 `apply`：一个过时的 `updaterd`，操作者伸手去拿 `apply`，`already_current`，没有计划的重启，且除了手动运行 `systemctl restart updaterd` 外没有东西能修复它。

**已修复**（`engine.rs::restarts_owed`、`reconcile::stale_units`）。`apply` 与 `select` 在它们的 already-current 路径上读取相同的身份文件，在 `already_current` 结果中命名运行别的东西的 unit，并像更新调度其延迟对一样调度那些重启。它不是启动检查防范的那个循环：它在一个请求上触发一次，且通过 `systemd-run` 而非从被重启的进程内部。

**且 `apply --force` 被丢弃而非延后。** 它的全部职责是在一个已经当前的版本上重新运行重启；那现在就是 `apply` 在 —— 且仅在 —— 有东西实际过时时做的事。一个标志会添加第二种请求方式，被一个花了一段才写对的问题门控：`install --force` 在 `robotd` 应答时拒绝，因为它禁用健康门，`apply` 保留那个门，因此对称地复制守卫会恰好在机器人起来且偏差时禁用该标志。现在没有东西需要回答那个。

**已修复，且本段曾说相反。** `btd` 被排除在*进行中*的重启之外，因为重启它会丢弃承载更新自身进度流的 BLE 连接 —— 那部分过去且现在仍是对的。从中得出的结论不是：这曾说一个 `btd` 修复"需要手动重启或重启……一个手机驱动流程中的真正缺口"，而它不再是了。该排除在结果上线的那一刻过期，因此 `btd` 与 `updaterd` 都在五秒后通过 `systemd-run --on-active=5s`（`RESTART_AFTER_REPLYING`）重启。一个客户端看到其结果，然后一个断开的连接，对 BLE 来说这是一次普通的重连。

**也已修复，且本段也曾说相反。** 可观测性那半曾说会存活：`robotctl version` 看不到 `btd`，因为 `btd` 不服务 socket，因此没什么可问。前提是答案必须通过 socket 来。它不必 —— 每个守护进程现在在启动时把它的身份写到一个文件，`btd` 与 `padd` 包括在内，因此 `robotctl health` 读取每个进程被启动自的版本并在它与安装的不一致时警告。没有守护进程因这里声称的原因而不可观测。

### 一个值得知道的后果：unit 比安装它们的版本活得更久

`hooks/postinstall` 安装一个版本交付的 unit，且按设计在回滚时留下它们 —— 替代方案是记录添加了什么以便一次还原可以撤销它，且 hook 自己的注释论证这不值得，因为下一次成功的更新会重新安装它交付的任何东西。

该推理对回滚成立。对**降级到一个早于某个守护进程的版本**不成立：unit 留下，其 `ExecStart` 命名一个旧版本不包含的二进制，且守护进程以 `203/EXEC` 失败。一旦那个守护进程也在 `on_apply` 的重启集中，失败的重启会让*更新*失败，它就会回滚。

正好这样观察到：在一块运行 dev 构建的板子上 `robotctl update apply daemon` 解析到 stable `0.2.0`，它早于 `configd`；`configd.service` 无法启动；引擎回滚并说明了。结果是对的 —— 一块板子不应该静默降级到低于引入它现在运行的守护进程的版本 —— 但没有东西陈述规则，且错误命名一个 systemd 失败而非原因。

**现在被陈述而非涌现。** `updater/src/orphan.rs` 拒绝一个缺少某个已安装 unit exec 的二进制的候选，且拒绝命名 unit、缺失的二进制以及绕过它的方式 —— 移除 unit，`systemctl disable --now configd.service && rm /etc/systemd/system/configd.service`。没有覆盖标志：移除 unit 正是操作者的意思，因为一个低于引入某个守护进程的版本的板子不应该运行那个守护进程，且下一个交付该 unit 的更新会重新安装它。

关于它在哪里运行有两点。它**不**在预检中，预检看不到候选的文件列表 —— 两个预检通过都在产物下载之前运行 —— 因此它在提取后、交换前运行，那里暂存仍是可丢弃的且没有东西被武装。且**没有目标被豁免**，不像 `Error::WouldDowngrade`，它仅在 `Latest` 触发：那个守卫是关于一个镜像提供陈旧清单的，这个是关于一个不会启动的 unit，而 `Ref` 正是它被观察到的方式。

它不在回滚、reset-to-golden 或 `select` 上运行。那些是故意向后移动的，是一块板子摆脱坏版本的方式，因此一个可以拒绝的检查绝不能坐在恢复路径中（`docs/design/architecture.md` §1.1）—— 回滚到一个孤立的 unit 保持上面的有文档行为，且保持自我纠正。

## 为什么现有测试无法捕获它们

不是对测试的指责；它们覆盖它们声称的。要点是什么都没覆盖。

这写于答案是"什么都没有"的时候，且那么说的行此后变了。保留为缺失了什么的记录，以及每个检查**今天**覆盖什么：

| | 覆盖 | 不覆盖 |
|---|---|---|
| `board-test.sh` | 在真实 aarch64 Linux 上执行的二进制，**以及一个真实产物被解包并由 `install.sh` 与 `hooks/postinstall` 针对一个存根的 `systemctl` 安装** —— 放置、模式、排序、幂等，以及每个 unit 的 `ExecStart` 二进制存在 | 服务实际启动，这需要真实 systemd |
| `xtask` 测试 | 工作流 YAML 对 `install.sh`，以及 unit `ExecStart` 对暂存的二进制 | *构建的产物*是否匹配任一个 —— 它读源文件 |
| `updater` 测试 | 引擎、日志、验证、回滚，带假实现 | 完全没有 `install.sh` |
| `shipped_config_is_safe_for_a_client_robot` | `deploy/updater.toml` 的内容 | 配置是可安装的 |

第一行过去说的是"解包一个产物、安装 unit、启动服务"，且下面的句子是：**没有测试拿一个真实产物并安装它。** 那是本文档存在的发现，且它已被修复 —— `xtask` 行仍是较弱的形式，断言两个源文件一致而非观察它们产出什么，但它不再是站在一个打包错误与一块板子之间的唯一东西。

## 什么会关闭它

2026-08-11 修订，在下面的重启机制落地后，且有一个第一次没陈述的约束：**CI 已经是迭代中最慢的部分，因此计划按它给等待增加什么来评判，而非仅按它覆盖什么。** 因此这里的所有东西都命名它在哪里运行。

### 先看预算

CI 在每次推送与每个触碰代码的 PR 上运行，作为并行作业，因此等绿色的时间是*最慢的*作业 —— 不是总和。这一单一事实决定新测试属于哪里：

| 作业 | 什么让它慢 |
|---|---|
| `check` | fmt、clippy、`cargo test --workspace`、安装程序 lint，以及一个真实的 `xtask package` |
| `board` | 从源码 `cargo install cargo-zigbuild`，加上 aarch64 的 QEMU 模拟 |
| `coverage` | 一个完整的插桩构建 |

因此添加到 `cargo test` 的毫秒级测试不花任何人注意到的代价，而任何落在 `board` 或 `coverage` 中的东西在每次推送时都要付出。三条规则随之而来，且它们是本节的要点：

- **默认的 `cargo test --workspace` 只接受进程内测试。** 无 tarball、无 systemd、无网络、无 sleep。
- **任何解包产物或驱动服务的东西按需运行**，作为一个脚本或一个 `#[ignore]`d 测试 —— 绝不在 PR 路径上。
- **无新 CI 作业。** 如果一个检查需要一个产物，它挂在 `check` 已经运行的 `xtask package` 步骤上，并复用该步骤已经构建的 tarball。

那两个数字过去更糟，且修复它们的两个移除正是本节主张的形态 —— **把工作拿出 CI 比下面任何测试增加的都更有价值**：

- **`coverage` 在一个 PR 上把整个插桩套件运行两次**，head 与 base，纯粹为了打印一个增量。已移除：`--fail-under-lines` 才是捕获回归的东西，且该作业从超过七分钟降到约两分钟。代价被陈述而非粉饰 —— 一个降低覆盖率但保持在底线之上的变更不再说明，且底线现在是一个棘轮。
- **一个仅文档的变更付出了全部代价。** `on:` 没有路径过滤，因此编辑本文件会为 aarch64 在 QEMU 下交叉编译并在插桩下构建工作区。三个连续的文档 PR 正好在本计划被写时做了那件事。用一个针对 `docs/**` 与 `*.md` 的 `paths-ignore` 移除。

  那个有一个附带的陷阱，被检查而非假设：一个被跳过的作业报告**完全没有状态**，因此过滤一个合并*必需*的检查会让文档 PR 永远挂起。在这里安全是因为 `main` 没有必需的状态检查 —— 分支保护 API 在本计划上回答 403。打开保护意味着重新审视它，且那时的形态是一个过滤的作业加上一个同名的空操作作业。

### 1. 两个不需要新机器的测试

进程内，在 `cargo test` 中，且它们覆盖让更新自愈的两个机制的行动半 —— 两者之前都无法被任何测试观察到。两者都已写；下面是为什么它们是第一件要做的事。

- **`systemd-run` 不可观测。** `schedule_deferred_restarts` 硬编码 `Command::new("systemd-run")`，而两个函数之外的 `SYSTEMCTL` 是一个 `const`，正是为了让 `restart_tests` 可以替换一个存根脚本。同样的处理，然后断言从未被断言的东西：`--on-active=5s`、每个 unit 一次调用、`updaterd` 与 `btd` 都被命名。该标志今天可能是错的，每个测试仍会通过。
- **`reconcile::check` 从未被一个测试调用**，只有它纯的 `verdict_for`。它已经把 `systemctl` 作为参数，且身份通过 `DUCK_RUNTIME_DIR` 读取 —— 一个接缝，其自己的注释说它存在就是为了让这可测试。把身份文件写进一个临时运行时目录并断言四个结果：过时的被重启，`updaterd` 被报告且不被重启，一个缺失的身份文件被置之不理，一个失败的重启报告自己。

### 2. 产物安装 —— 已完成，以及它留下了什么

**这不再开放，且本文档的标题不再为真。** `scripts/board-test.sh` 从 `_build-release.yml` 中的 `--include` 列表打包一个真实版本，解包它，并在容器内对它运行 `scripts/install.sh` *以及* `hooks/postinstall`，带一个存根的 `systemctl`（PR #47，2026-08-07）。十一个断言：unit 以模式 644 字节相同地安装、sysusers drop-in、通过 `current` 解析的 `robotctl` 符号链接、journald drop-in、在任何 `enable` 之前 `daemon-reload` 且在 `btd` 之前 `configd`、操作者配置文件被保留、第二次运行的幂等性、一个 `install.sh` 不认识的 unit 被安装但未启动，以及 postinstall 独自复现全部。

这覆盖了本节过去要求的东西，以及"断言产物内容"的想法，因为那时 tarball 是打开的。**Bug 2 是对照产物而非 YAML 关闭的。**

留下了一个缺口，就是 bug 3 —— 四个中唯一一个没有强测试的类别。没有东西问一个 unit `ExecStart` 的二进制是否*在*交付该 unit 的产物中，这正是 `btd.service` 如何在一块版本看起来完整的板子上以 `203/EXEC` 失败。保护是 `xtask/tests/artifact.rs`，把一个工作流与 `install.sh` 比较 —— 上面批评的两个文件一致形式。现在直接问，三行，在那个已经有树解包且 `current` 指向它的作业中。

只检查版本内部的 `ExecStart` 路径：一个 unit 可能故意从 base 外部 exec —— 启动恢复网就是这样，以便一个坏掉的版本不能破坏它 —— 且要求那些被打包会是错的而非严格。

**这里真正缺失的东西什么都没有。** 剩余项是下面两个，且它们覆盖不同的东西而非更多这个。

### 3. 板子检查 —— 已完成，在 `dev-push.sh` 内部

**已完成，且不是作为一个单独的场景脚本。** `dev-push.sh` 过去结束于"is live"，那意味着交换发生且健康门通过 —— 不是五个守护进程在运行交换进来的东西。那个缺口就是一个下午去的地方：四个 wifi 修复曾被对照一个从未重启的 `configd` 验证为坏掉。

因此检查在每次推送而非晋升前运行。它读取每个守护进程在启动时发布的身份，把那里命名的版本与板子的 `current` 比较，且 —— 单独地，因为否则一切在*前一个*版本上一致也会通过 —— 与本次推送构建的版本比较。`robotd`、`configd` 与 `padd` 预期立即匹配；`updaterd` 与 `btd` 轮询最多 30 秒，因为它们在应答后五秒重启。

这是唯一一个端到端观察整个重启机制的东西，且 CI 中没有任何东西能替代它：瞬时计时器、持有每个身份的 `RuntimeDirectory=`、以及五秒延迟全是 systemd，在真实时序上。一个过时的 unit 会让推送失败并命名该看什么。

两个故意的非失败。一个什么都没发布的守护进程被报告且不失败 —— systemd 在一个 unit 停止时移除运行时目录，因此这也是一个故意禁用的 `padd` 看起来的样子。且 `robotctl health` 只需要*应答*：一块没有舵机电源的工作台板子报告降级，这是关于工作台而非关于构建的事实，正好如健康门对待它。

### 4. 真实 systemd —— 已完成，作为 `scripts/systemd-test.sh`

**已完成，且在断言任何东西之前就回本了。** `scripts/systemd-test.sh` 把 systemd 作为 pid 1 启动，铸造三个携带真实 unit 与一个真实 `updaterd` 的签名版本，安装一个，通过运行中的守护进程应用下一个，然后应用一个交付一个无法启动的 unit 的版本。

四件它观察到的、树中其他任何东西都做不到的事，因为其他一切都有一个存根的 `systemctl`：

- **`on_apply` 真的重启**版本交付的东西 —— 在 unit 的主 PID 变化上断言，而非命令已被发出；
- **延迟的瞬时计时器真的触发且真的替换 `updaterd`**，在约四秒内，且后继者运行新版本。一个子进程做不到这个：它会坐在被杀死的 cgroup 中，这正是 `systemd-run` 的理由，且直到现在都是一个未测试的断言；
- **`hooks/postinstall` 真的安装、启用并启动**一块板子从未有过的 unit；
- **一个干净安装却无法启动的 unit 让更新失败并命名自己** —— `restart failed: Job for broken.service failed` —— 而非以 `not healthy within 30s: unreachable` 回滚。那是 bug 1，且是上面各项无法触及的唯一类别。

**Docker 而非 `systemd-nspawn`**，这与本节过去提议的不同。在 CI 中对特权容器的反对仍然成立，且这不是 CI。决定它的是本节自己为把真实 systemd 排最后所做的论点：一个只能在没人开发的机器上运行的检查会停止被阅读。Docker Desktop 在开发它的笔记本上以 systemd 为 pid 1 运行一个特权容器；nspawn 不行。

它在第一次运行时就发现了一个 bug，在代码中而非自身。`self_test_updaterd` 用没有 `--config` 的新二进制运行，因此它以运行中的守护进程被启动的任何方式验证 `/etc/robot/updater.toml` —— 击败了检查的全部目的，即捕获一个拒绝*板子的*配置文件的新二进制。

这里命名的两个注入也在其中，且两者都落地了其他任何东西无法做的断言：

- **`systemd-run` 无法运行。** 更新仍成功 —— 按设计调度是尽力而为，因为那时更新已提交 —— 日志说明，且 `btd` 与 `updaterd` 被留在旧版本上，正像一个错过的计时器留下它们那样。然后下一次 `updaterd` 启动把过时的 `btd` 调到活动版本且**不**重启自己，在那个进程中那会是一个无路可走的循环。那是 `reconcile.rs` 第一次在单元测试外关闭循环。
- **一个其 `User=` 由版本带来的 unit。** `postinstall` 安装 `sysusers.d` 文件并在 unit 之前运行 `systemd-sysusers`，且它的注释称该排序是承重的。账户存在且其 unit 运行。另一半 —— 同一个 unit 没有任何东西创建用户 —— 让更新失败并命名 unit 而非账户。

### 工具包在路上发现的缺口 —— 已修复

**一次失败的更新为一个它已成功放回的机器人报告了一次失败的回滚。** 被上面的缺失用户版本复现，而 `RollbackFailed` 是设计称为最严重的一种结果 —— 因此它值得超过一个注释。

原因不是回滚。`hooks/postinstall` 覆盖 unit 文件且按设计不把它们放回：hook 论证一个未成功的版本会让一个服务失败直到下一个成功，这两种情况相同。该推理成立且不变。它没预料到的是 unit 在被回滚*到*的版本的重启集中 —— 然后回滚重新运行同样的重启并继承同样的失败。可由一个普通的坏版本而非仅上面的降级案例触及：两个连续版本交付相同的 unit 名，且较新的那个是坏的。

**修复把交换与 apply 动作分开，因为只有其中一个是恢复。** 过了 `swap_to` 且试用被清除，机器人*已经*回到它来自的版本；一个随后无法重启的 unit 是第二个事实，而非对第一个的矛盾。因此 `Error::RollbackFailed` 保留其含义 —— 机器人根本无法被放回 —— 且一次回滚期间失败的 apply 动作被带入报告的结果并以 `error` 级别记录：

```text
not healthy within 30s: …; the release was reverted, but restarting robotd failed: …
`Restart=` may have brought it back since — `robotctl health` says whether it did.
```

两个事实，按某人需要它们的顺序：首先为什么更新失败，然后没有随回滚回来的那个 unit。

该句子的后半过去读为"因此这台机器人上有东西挂了"，且它错得足够频繁值得命名。这里每个守护进程都运行 `Restart=always`，而一个立即退出的守护进程在健康门的三十秒用完之前很久就烧完了 systemd 的每十秒五次启动 —— 因此回滚的重启通常以 `Start request repeated too quickly` 被拒绝，而 unit 片刻后自己回来了。一块工作台板子直接在它自己的 `robot healthy` 行下面打印了那个停机声明。`restart_one` 现在用 `reset-failed` 清除计数器并再试一次，这移除了原因；结果报告它观察到的拒绝并命名回答它无法回答的东西的命令。

两个被拒绝的替代方案，因为两者都不明显错。让 `postinstall` 可逆是 hook 明确拒绝的变更；它需要版本外的状态并给恢复路径添加一个失败模式，而恢复路径是必须保持无聊的那个地方。在*任何地方*容忍失败的重启会削弱 `restart_one` 故意画出的区分 —— 一个存在却不会启动的 unit 是坏版本被捕获的方式，且那在*进入*时仍是致命的。

### 不做

**一块板子作为自托管 runner。** 运维成本，且是 CI 的单点故障。第 3 项按需获得大部分价值，那正是一个房间里的机器人该在的地方。

## 第二个独立问题：dev 通道上的版本偏差

在同一会话中发现且容易与上面混淆，但任何数量的安装测试都不会捕获任一 —— 在两种情况下产物都是完整且正确的。

形态总是一样的，且**过去打开本节的那个句子不再为真。** 它读："`updaterd` 在更新期间从不重启自己（§4.1），因此它继续运行旧二进制直到下次重启，而盒子上的其他一切立即移到新版本。"那是下面两个实例的根本原因，且它已被修复 —— `updaterd` 现在在更新应答后五秒重启自己。偏差窗口是秒，而非"直到某人重启"。

带着那个记住读这两个案例。两者都不再是现场事件，且**两者现在都关闭** —— 案例 1 通过修复它提议的东西，案例 2 通过决定反对它：

- 案例 1 的 `serde(default)` 修复**没有**被更短的窗口变得多余：版本偏差只是击中它的最常见方式，且任何更新解析器-旧发送者对都会。已完成，在默认零是诚实的那些节上。
- 案例 2 的握手修复**大部分**被它变得多余，从"恢复命令本身停止工作"降到"一个五秒的窗口期间它不工作" —— 且当设计论点终于被写出来时，它所依赖的前提没有存活。精确的 `!=` 保留；变了的是消息。见下与 #77。

两个实例，都是真的，都花了约一小时。

### 1. 一个添加到 `HealthResult` 的必需字段

`main` 给 IMU 节添加了 `consecutive_stale_blocks` 并从它发布了 0.2.0。一个在那之前合并了 `main` 的分支没有发送该字段。`robotd` 完美起来 —— 服务 socket、加载两个策略、以 50 Hz 运行循环 —— 而常驻的 0.2.0 `updaterd` 因一个缺失字段拒绝它的应答。`RobotIo::health` 把一个不可解析的应答映射为 `Health::Unreachable`，因此门对一个完全健康的机器人报告 `not healthy within 30s: unreachable`，并回滚了一个好版本。

修复，两个小的，且**都已完成**：

- **在新的 `HealthResult` 字段上加 `#[serde(default)]`**，以便一个较新的 `updaterd` 仍能解析一个较旧的 `robotd`。否则每个 `--ref` 安装一个早于健康字段添加的分支都会命中这个，而那是整个 dev 工作流。

  咬人的那半是嵌套的那个：每个*顶层*字段已经携带 `#[serde(default)]`，包括 `imu`，而嵌套的 `ImuHealth` 上的 `consecutive_stale_blocks` 没有。`ImuHealth` 与 `BusHealth` 现在在容器级别携带它，因此添加到任一个的字段都会默认而非让整个解析失败。

  `LoopHealth`、`Battery` 与 `MotorThermal` 故意**不**携带，且例外是修复中有用的部分：那些节携带*测量值*，那里一个默认零是一个旧发送者从未说过的谎 —— 一个默认的 `percent: 0.0` 在一个电池满的机器人上渲染为一个空包。规则是"默认一个省略诚实意味着什么"，而非"默认一切"，且 `ImuHealth` 的文档注释逐字段论证它。
- **一个不同的 `Health::Incompatible`** 而非复用 `Unreachable`，因此原因读为"answered in a shape this updaterd does not understand"而非暗示机器人挂了。纯诊断，且它本会在一分钟内发现上面的。

  已完成。它在被添加时还翻出了自己的邻居：`safe_to_restart` 以同样方式折叠一个不可读的应答，而 `permits_restart` 然后把它读为*安全* —— 与其自己注释承诺的相反。那变成了 `SafeToRestart::Incompatible` 与 #68。

### 2. `robotctl` 与 `updaterd` 之间的 `API_VERSION` 偏差

`robotctl` 是一个指向 `current` 的符号链接，因此它跟随已安装的版本。`updaterd` 不。因此一个版本更改 `API_VERSION` 的那一刻，两者**保证**不一致，直到 `updaterd` 重启 —— 而停止工作的命令是 `robotctl update apply`，那正是你会用来摆脱它的那个。

通过普通使用而非刻意演示：安装分支 A，在等 CI 时安装分支 B，每个 `robotctl` 调用都失败 `client speaks API v2, daemon speaks v3`。逃生是调用一个来自版本目录的 `robotctl`，其版本匹配运行中的守护进程，或重启 `updaterd` —— 两者都无法从错误中发现。

握手至少*捕获*了它并命名了两个版本，这比案例 1 做到的多。

第一个提议的修复是 **`hello` 应该只在客户端比守护进程*新*时拒绝**，且它被**否决**（#77）：它假设升级是加法的，而它们不是 —— v5 添加了 `pad.*` 是加法的，v4 让 `system.authenticate` 强制不是。凭一个常量不跟踪的模式接受较旧客户端会承诺向后兼容却没有东西强制执行它。

**改为通过完全移除闸门修复。** 那个拒绝的前提存活 —— 一次升级不承诺任何东西 —— 但结论不随之而来。破坏一个不匹配对端的是一个*它无法到达的路由*或一个*移动了的参数形态*，且两者都已经自己拒绝，以名字，在唯一一个无法被服务的调用上：来自 `Request::as_call` 的 `METHOD_NOT_FOUND`，来自参数解码的 `INVALID_PARAMS`。握手上的一个闸门在每个其他调用上也触发 —— 事实上每个调用，因为 `hello` 在所有它们之前 —— 这就是一个一位数的差异如何同时夺走了 `update apply` 与 `version`。因此 `updaterd` 现在记录那对版本并服务调用；差异通过 `HelloResult::api_version` 到达客户端，且 `robotctl` 每次运行打印一行警告。

在闸门可以去掉之前必须有两件事为真，且第二个是有用的部分：

- **拒绝必须是多余的，而非仅仅烦人。** 它是：`robotd`、`configd` 与 `padd` 根本不检查那个数字，且 `updaterd` 在 `update.status` 之前无论如何不要求握手。`duck-btctl` 已经从链路的远端得出了同样的结论（#102）。
- **一个被静默忽略的参数必须停止可能。** `serde` 忽略它不知道的东西，这正是让闸门感觉承重的原因：v7 添加了 `ApplyOptions::from_dir`，而一个忽略它的 v6 守护进程会从它*配置的*源安装，而操作者相信他们正在侧载一个目录。现在每个参数类型都拒绝未知字段，因此那是一个命名该成员的 `INVALID_PARAMS`。它只向前触及 —— 一个在此之前构建的守护进程仍忽略它不知道的东西 —— 这就是为什么一次 `API_VERSION` 升级仍值得做。

消息在此之前被重写且现在随闸门一起消失。它说 `client speaks API v2, daemon speaks v3` 且不命名出路；它长出的补救（重试，或使用 `/usr/local/bin/robotctl` 的符号链接）现在住在 `robotctl` 的警告中，那里没有东西被拒绝。

### 为什么这些不是安装路径 bug

上面计划中的任何东西都不会捕获任一。两次产物都是正确的；出错的是某一时刻运行的*那对*版本，这只存在于一台已经被更新过的机器上。第 4 项（本地真实 systemd）如果容器也运行一个较旧的 `updaterd` 会捕获案例 1 的*健康门*后果，但刻意构造那种偏差是一种不同的测试 —— 更接近兼容性矩阵而非安装测试，且值得保持分开。

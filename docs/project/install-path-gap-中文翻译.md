# 安装路径没有测试

状态：已关闭 · 日期：2026-08-05，修订于 2026-08-07 和 2026-08-11 · 负责人：pierre

连续四个 bug 到达了一块板，全部在安装路径中，没有一个被 418 个测试或 `board-test.sh` 捕获。本文记录了为什么，以及什么关闭了它。这教会的一般规则——任何全新安装对板做的事情也属于一个钩子，因为那是在每次更新时在每块板上运行的唯一东西——超出了本文档，现在存在于 `updater-design.md` §9.1。**那是应该读它的地方；本页是故事，不是规则。** 从那以后它又被弄错了两次，因此 §9.1 值得在添加安装步骤之前而不是之后阅读。写于同一天，当时原因仍然具体，并保持它赢得的过去时态，而不是重写为参考——它现在有用的是错误的形状，而不是树的状态。

第二部分涵盖两个*看起来*像同一件事但不是的发现：已经运行的 daemon 和刚刚安装的发布之间的版本偏差。两者都不会被任何数量的安装测试捕获，且它们需要自己的修复——保留在这里而不是在它们自己的文档中，因为调查任何一个的人都会到达时相信它是另一个。

**修订说明。** 所有四个 bug 都已修复，它们后面的版本偏差部分也是：案例 1 的 `serde(default)` 纪律落地了，案例 2 的握手提议被决定*反对*且其推理被写下来，且"单元比安装它们的发布活得久"的后果现在是一个拒绝而非涌现行为。

**且标题命名的差距已关闭。** 一个测试安装真实制品——`board-test.sh` 解包一个并针对它运行 `install.sh` 和 `hooks/postinstall`——每个单元的 `ExecStart` 二进制对照交付它的 tarball 被检查，板上检查在每次 `dev-push.sh` 上运行，且 `scripts/systemd-test.sh` 针对真实 systemd 驱动一次真实更新。那些来自的计划在下面，每个都发现了什么；其中最后一个发现了两个引擎 bug。

自初稿以来的一个变化移动了足够多的本文档内容，值得在这里指出：`updaterd` 和 `btd` 现在在更新回复后几秒重启（`RESTART_AFTER_REPLYING`），且发布自己的 `updaterd` 被证明在提交之前启动（`updaterd --self-test`）。下面的两个主张是针对旧行为写的，现在是假的——两者都已就地纠正，特别是第二部分的前提不再成立。

**第二次修订说明。** §4 的偏差一半现在由代码而非论点关闭。每个 daemon 发布它正在运行的东西（`duck_ipc_proto::publish_identity`），且 `updaterd` 在每次启动时将每个单元与活动发布进行比较并重启过时的（`updater/src/reconcile.rs`，`Engine::reconcile_running_units`）。下面还有两个主张在写时是真的现在不是了：运行/安装不匹配是未决定的，以及 `btd` 的运行修订无法读取。两者都已就地纠正。`docs/design/restart-order.md` §5 和 §7 拥有机制以及如何读取偏差；这里保留的是为什么需要它。

## 什么通过了

四个都在一天内落地，全部在将 `btd` 和 `configd` 安装到开发板上时。（在添加下面的 §4 之前，计数写的是"三个"。）

**1. `on_apply` 在一条命令中重启多个单元。** 如果*任一*单元未知，`systemctl restart robotd configd` 整体失败——且不重启存在的那个。因此引入新 daemon 的发布无法重启任何东西，因为单元文件*随*那个发布到达，且没有东西安装它。回退原因是 `not healthy within 30s: unreachable`，既不命名单元也不命名命令。

潜在的而非致命的，因为板保留自己的 `/etc/robot/updater.toml`。

修复了两次，第二次是真正的修复。首先，防御性地：单元一次重启一个，systemd 不知道的单元被跳过。然后正确地：**`hooks/postinstall` 安装发布的单元。** 引擎一直有一个安装后钩子点——`extract → [pre_install] → swap → [post_install] → apply → health gate`——它在 `current` 移动之后运行，因此 `ExecStart` 解析，且在重启之前，因此 `on_apply` 找到一个存在的单元。没有东西使用它；只有 `scripts/install.sh` 曾经从发布中复制单元，因此每个新服务永远需要在每块板上手动一步。机制存在且未被使用是在审查中指出的，不是我发现的。

**2. 制品不包含新单元。** 打包工作流用显式的 `--include` 命名每个交付的文件，单元被添加到 `install.sh` 而没有被添加到那里。手工发现：板上的 `ls current/systemd/`。

**3. 制品不包含新二进制。** Package 步骤用每个二进制的显式 `cp` 复制二进制。`cargo board --bins` 构建了 `btd` 和 `configd`；没有东西暂存它们。`btd.service` 以 `203/EXEC` 失败，这读起来像一个损坏的 daemon 而不是不完整的制品。

Bug 3 与 bug 2 同类，在同一个文件中，**在添加了一个阻止 bug 2 复发的测试之后两次提交**——那个测试检查单元而不检查它们 exec 的二进制。每个修复都是正确的且每个都太窄，这是值得攻击的模式而非 bug。

**4. `on_apply` 的重启列表住在板上，因此新 daemon 永远不会被重启。** · **已测量** 最昂贵的一个，也是已经在这里写为"潜在的而非致命的"那个。

`[component.daemon.on_apply].units` 从 `/etc/robot/updater.toml` 读取——*操作员的*文件，`install.sh` 故意保留它。`configd` 在引入它的分支中被添加到交付的 `deploy/updater.toml`，因此在那之前设置的板永远保持 `units = ["robotd"]`。因此每个 `configd` 发布都交换了二进制并留下旧进程运行。

使它花费两小时而非两分钟的是失败的形状：

- 更新报告**成功**——交换发生了，健康门通过了，没有东西失败；
- `robotctl update apply` 然后报告 **`already_current`** 且什么都不做，因此明显的恢复命令是空操作；
- daemon 继续应答，在旧代码上，因此它看起来像修复是错的而非不存在。四个 wifi 修复被验证为针对从未运行的二进制损坏。

`robotctl version` *确实*诊断这个，用同样多的话："configd is running X but the installed daemon release is Y … either the restart did not happen, or it failed"。没人运行它。一个存在但不被到达的诊断与一个不存在的诊断价值一样多，这是支持更新自己注意到而非更多诊断的论点。

**已修复**（`engine.rs::units_to_restart`）：重启集从发布的 `systemd/*.service` 文件派生，与配置命名的任何东西合并，减去 `updaterd` 和 `btd`——它们从由测试强制执行的配置约定变成代码中的 `NEVER_RESTART` 常量，因为它们是那些 daemon 是什么的属性而非操作员选择。`updater.toml` 早于某个 daemon 的板现在仍然重启它，且不需要编辑。下面是推理，保留因为它是此类列表属于哪里的论点。

**从发布派生重启集，而不是从板。** 一个发布交付 `systemd/*.service`，因此它已经陈述了它提供哪些单元——与使 `hooks/postinstall` 成为*安装*它们的正确答案相同的认识。引擎可以重启发布交付的东西，减去两个有记录的排除（`updaterd`，它正在执行更新；`btd`，它可能是请求所通过的传输）。然后添加 daemon 的发布在每块板上重启那个 daemon，无需操作员编辑且板的配置不可能静默过时。

两个较小的选项在这里被指出为上述的伴随而非替代：`apply` 可以获得一个 `--force`，在已经当前的发布上重新运行钩子和重启（有先例——`install --force` 为同类的鸡生蛋问题存在），且 `already_current` 可以比较*运行*修订而非仅安装的，因此它恰好在有问题时停止是空操作。

**第二个已被回答，且不在它被提议的地方。** 它真正提出的问题是运行/安装不匹配应该被报告和拒绝还是被修复，答案是修复——由 `updater/src/reconcile.rs`，它在每次 `updaterd` 启动时运行而非在 `apply` 内部。每个单元的运行发布来自其进程发布的身份文件，与它的组件有什么活动进行比较，任何过时的都被重启。由于 `updaterd` 在每次应用的更新后五秒重启自己，该检查在每次 `apply` 后几秒运行，因此本节关于的状态现在用不变的 `Engine::apply` 自我愈合。

那留下的比写的任一选项都窄，且它现在也关闭了。`reconcile` 故意不修复一个偏差——`updaterd` 自己的，因为在拥有恢复的进程中的自重启循环是唯一一个没有出路的失败——且那遇到了一个 `apply` 在仅安装版本上返回 `AlreadyCurrent` 的单一情况：一个过时的 `updaterd`，操作员伸手去拿 `apply`，`already_current`，没有调度重启，除了手动运行 `systemctl restart updaterd` 没有东西修复它。

**已修复**（`engine.rs::restarts_owed`，`reconcile::stale_units`）。`apply` 和 `select` 在它们的 already-current 路径上读取相同的身份文件，在 `already_current` 结果中命名运行其他东西的单元，并像更新调度其延迟对那样调度那些重启。它不是启动检查防范的循环：它触发一次，在请求时，且通过 `systemd-run` 而非从被重启的进程内部。

**且 `apply --force` 被丢弃而非推迟。** 它的全部工作是在已经当前的发布上重新运行重启；那现在是 `apply` 在——且仅在——有东西确实过时时做的事。一个标志会添加第二种请求方式，被一个花了一段才弄对的问题门控：`install --force` 在 `robotd` 应答时拒绝因为它禁用健康门，`apply` 保持那个门，因此按对称性复制守卫会恰好在机器人启动且有偏差时禁用标志。现在没有东西需要回答那个。

**已修复，且本段曾经说相反的话。** `btd` 被排除在*进行中*重启之外，因为重启它会断开携带更新自己进度流的 BLE 连接——那部分过去且现在仍然是对的。从中得出的结论不是：这里说一个 `btd` 修复"需要手动重启或重启……手机驱动流程中的真正缺口"，且它不再是。排除在结果上线的那一刻到期，因此 `btd` 和 `updaterd` 都在五秒后通过 `systemd-run --on-active=5s`（`RESTART_AFTER_REPLYING`）重启。客户端看到其结果然后一个断开的连接，这对 BLE 来说是普通重连。

**也已修复，且本段也曾经说相反的话。** 可观测性一半据说幸存：`robotctl version` 看不到 `btd`，因为 `btd` 不服务 socket，因此没有东西可问。前提是答案必须通过 socket 来。它不需要——每个 daemon 现在在启动时将其身份写入文件，包括 `btd` 和 `padd`，因此 `robotctl health` 读取每个进程启动自的发布并在它与安装的不一致时警告。没有 daemon 因为这里声称的原因而不可观测。

### 一个值得知道的后果：单元比安装它们的发布活得久

`hooks/postinstall` 安装发布交付的单元，且按设计在回退时留下它们——替代方案是记录添加了什么以便回退可以撤销它，且钩子自己的注释争论这不值得，因为下一次成功的更新重新安装它交付的任何东西。

那个推理对回退成立。它对**降级到早于某个 daemon 的发布**不成立：单元留下，其 `ExecStart` 命名旧发布不包含的二进制，daemon 以 `203/EXEC` 失败。一旦那个 daemon 也在 `on_apply` 的重启集中，失败的重启使*更新*失败，更新回退。

恰好这样观察到：在运行开发构建的板上 `robotctl update apply daemon` 解析为稳定的 `0.2.0`，它早于 `configd`；`configd.service` 无法启动；引擎回退并说明了。结果是对的——板不应该静默降级到低于引入它现在正在运行的 daemon 的发布——但没有东西陈述规则，且错误命名一个 systemd 失败而非原因。

**现在被陈述而非涌现。** `updater/src/orphan.rs` 拒绝缺少某个已安装单元 exec 的二进制的候选，且拒绝命名单元、缺失的二进制和绕过它的方法——移除单元，`systemctl disable --now configd.service && rm /etc/systemd/system/configd.service`。没有覆盖标志：移除单元是操作员无论如何的意思，因为低于引入 daemon 的发布的板不应该运行那个 daemon，且下一个交付该单元的更新重新安装它。

关于它在哪里运行的两件事。它**不**在 preflight 中，preflight 看不到候选的文件列表——两个 preflight 传递都在制品下载之前运行——因此它在提取之后交换之前运行，那里暂存仍然是可丢弃的且没有东西被武装。且**没有目标被豁免**，不像 `Error::WouldDowngrade`，它只在 `Latest` 上触发：那个守卫是关于镜像提供陈旧清单，这个是关于一个不会启动的单元，且 `Ref` 正是它被观察到的方式。

它不在回退、reset-to-golden 或 `select` 上运行。那些是故意向后移动的，是板摆脱坏发布的方式，因此一个可以拒绝的检查不能坐在恢复路径中（`docs/design/architecture.md` §1.1）——回退到孤立单元上保持上面的有记录行为，且保持自我纠正。

## 为什么现有测试无法捕获它们

不是对测试的指责；它们覆盖它们声称的。要点是什么都没覆盖。

这是在答案是"什么都没有"时写的，说如此的行此后改变了。保留为缺失了什么的记录，以及每个检查**今天**覆盖什么：

| | 覆盖 | 不覆盖 |
|---|---|---|
| `board-test.sh` | 在真实 aarch64 Linux 上执行的二进制，**以及一个真实制品被解包并安装**，由 `install.sh` 和 `hooks/postinstall` 针对存根的 `systemctl`——放置、模式、排序、幂等性，以及每个单元的 `ExecStart` 二进制存在 | 服务实际启动，这需要真实 systemd |
| `xtask` 测试 | 工作流 YAML 对比 `install.sh`，以及单元 `ExecStart` 对比暂存的二进制 | *构建的制品*是否匹配任一——它读取源文件 |
| `updater` 测试 | 引擎、日志、验证、回退，用伪造 | 完全没有 `install.sh` |
| `shipped_config_is_safe_for_a_client_robot` | `deploy/updater.toml` 的内容 | 配置是可安装的 |

第一行过去说的是"解包制品、安装单元、启动服务"，它下面的句子是：**没有测试拿一个真实制品并安装它。** 那是本文档存在的发现，且它已修复——`xtask` 行仍然是较弱的形式，断言两个源文件一致而非观察它们产生什么，但它不再是站在打包错误和板之间的唯一东西。

## 什么会关闭它

2026-08-11 修订，在下面的重启机制落地之后，且有一个第一次没有陈述的约束：**CI 已经是迭代中最慢的部分，因此计划以它给等待增加了什么来评判，而不仅以它覆盖了什么。** 因此这里的一切都命名它在哪里运行。

### 首先是预算

CI 在每次推送和每个触及代码的拉取请求上运行，作为并行作业，因此等待绿色的时间是*最慢的*作业——不是总和。那一个事实决定了新测试属于哪里：

| 作业 | 什么使它慢 |
|---|---|
| `check` | fmt、clippy、`cargo test --workspace`、安装器 lint，以及一个真实的 `xtask package` |
| `board` | 从源码 `cargo install cargo-zigbuild`，加上 aarch64 的 QEMU 模拟 |
| `coverage` | 完整的插桩构建 |

因此添加到 `cargo test` 的毫秒级测试不花任何人注意到的成本，而任何落在 `board` 或 `coverage` 中的东西在每次推送时都被付费。三条规则随之而来，且它们是本节的要点：

- **默认的 `cargo test --workspace` 只接受进程内测试。** 没有 tarball，没有 systemd，没有网络，没有 sleep。
- **任何解包制品或驱动服务的东西按需运行**，作为脚本或 `#[ignore]`d 测试——永远不在拉取请求路径上。
- **没有新的 CI 作业。** 如果检查需要制品，它挂在 `check` 已经运行的 `xtask package` 步骤上，并复用该步骤已经构建的 tarball。

那两个数字过去更糟，修复它们的两个移除正是本节主张的形状——**从 CI 中拿走工作比下面任何测试增加的都更有价值**：

- **`coverage` 在拉取请求上运行整个插桩套件两次**，head 和 base，纯粹为了打印一个增量。已移除：`--fail-under-lines` 是捕获回归的东西，且这个作业从超过七分钟变成约两分钟。成本被陈述而非粉饰——一个降低覆盖率同时保持在下限之上的变更不再说明，且下限现在是一个棘轮。
- **仅文档变更支付了全部账单。** `on:` 没有路径过滤器，因此编辑这个文件会在 QEMU 下为 aarch64 交叉编译并在插桩下构建工作区。三个连续的文档拉取请求在写这个计划时恰好那样做了。用 `docs/**` 和 `*.md` 的 `paths-ignore` 移除。

  那个有一个附带的陷阱，被检查而非假设：被跳过的作业报告**完全没有状态**，因此过滤一个合并*必需*的检查会使文档拉取请求永久挂起。在这里是安全的，因为 `main` 没有必需的状态检查——分支保护 API 在此计划上回答 403。打开保护意味着重新审视它，那时的形状是一个过滤的作业加上一个同名的空操作作业。

### 1. 两个不需要新机器的测试

进程内，在 `cargo test` 中，且它们覆盖使更新自我愈合的两个机制的行动一半——两者都没有被任何测试观察到。两者都已写；下面是为什么它们是第一件要做的事。

- **`systemd-run` 不可观测。** `schedule_deferred_restarts` 硬编码 `Command::new("systemd-run")`，而两个函数之外的 `SYSTEMCTL` 是一个 `const`，正是为了 `restart_tests` 可以替换一个存根脚本。相同处理，然后断言从未被断言的东西：`--on-active=5s`，每个单元一次调用，`updaterd` 和 `btd` 都被命名。该标志今天可能是错的且每个测试仍然会通过。
- **`reconcile::check` 从未被测试调用**，只有它的纯 `verdict_for`。它已经将 `systemctl` 作为参数，且身份通过 `DUCK_RUNTIME_DIR` 读取——一个其自己的注释说它存在以便这是可测试的接缝。将身份文件写入临时运行时目录并断言四个结果：过时的被重启，`updaterd` 被报告且不被重启，缺失的身份文件被置之不理，失败的重启报告自己。

### 2. 制品安装——已完成，以及它留下了什么

### 3. 板上检查——已完成，在 `dev-push.sh` 内部

**已完成，且不是作为单独的场景脚本。** `dev-push.sh` 过去在"is live"结束，这意味着交换发生了且健康门通过了——不是五个 daemon 正在运行被交换进去的东西。那个缺口是一个下午去的地方：四个 wifi 修复曾经被验证为针对从未重启的 `configd` 损坏。

因此检查在每次推送时运行而非在升级之前。它读取每个 daemon 在启动时发布的身份，将那里命名的发布与板的 `current` 比较，以及——单独地，因为否则一切在*前一个*发布上一致也会通过——与这次推送构建的版本比较。`robotd`、`configd` 和 `padd` 预期立即匹配；`updaterd` 和 `btd` 被轮询最多 30 秒，因为它们在回复后五秒重启。

### 4. 真实 systemd——已完成，作为 `scripts/systemd-test.sh`

**已完成，且它在断言任何东西之前就收回了成本。** `scripts/systemd-test.sh` 将 systemd 作为 pid 1 启动，铸造三个携带真实单元和真实 `updaterd` 的签名发布，安装一个，通过运行的 daemon 应用下一个，然后应用一个交付无法启动的单元的发布。

它观察到树中其他任何东西都无法观察的四件事，因为其他一切都有存根的 `systemctl`：

- **`on_apply` 确实重启**发布交付的东西——在单元的主 PID 改变上断言，而非在命令已被发出上；
- **延迟的瞬态计时器确实触发且确实替换 `updaterd`**，在大约四秒内，且后继者正在运行新发布。子进程做不到这个：它会坐在被杀死的 cgroup 中，这是 `systemd-run` 的原因且直到现在是一个未测试的主张；
- **`hooks/postinstall` 确实安装、启用并启动**板从未有过的单元；
- **一个干净安装且无法启动的单元使更新失败并命名自己**——`restart failed: Job for broken.service failed`——而非以 `not healthy within 30s: unreachable` 回退。那是 bug 1，且它是上面各项无法到达的一类。

**Docker 而非 `systemd-nspawn`**，这与本节过去提议的不同。对 CI 中特权容器的反对成立且这不是 CI。决定它的是本节自己为将真实 systemd 排在最后的论点：一个只能在没人开发的机器上运行的检查会停止被阅读。Docker Desktop 在开发它的笔记本上运行一个带 systemd 作为 pid 1 的特权容器；nspawn 不。

它在第一次运行时发现了一个 bug，在代码中而非在它自己中。`self_test_updaterd` 运行新二进制时没有 `--config`，因此它验证 `/etc/robot/updater.toml` 无论运行的 daemon 是如何启动的——挫败了检查的全部目的，即捕获一个拒绝*板的*配置文件的新二进制。

这里命名的两个注入也在其中，且两者都落地了其他任何东西无法做出的断言：

- **`systemd-run` 无法运行。** 更新仍然成功——调度按设计是尽力而为的，因为更新到那时已经提交——日志说明了，且 `btd` 和 `updaterd` 被留在旧发布上，恰好像错过的计时器留下它们那样。然后下一次 `updaterd` 启动将过时的 `btd` 协调到活动发布上且**不**重启自己，这在那个进程中将是一个没有出路的循环。那是 `reconcile.rs` 第一次在单元测试之外关闭循环。
- **一个其 `User=` 由发布带来的单元。** `postinstall` 安装 `sysusers.d` 文件并在单元之前运行 `systemd-sysusers`，且它的注释称那个排序是承重的。账户存在且其单元运行。另一半——同一个单元没有东西创建用户——使更新失败并命名单元而非账户。

### 测试框架在路上发现的缺口——已修复

**一个失败的更新为一个它已经成功放回的机器人报告了失败的回退。** 由上面缺失用户的发布复现，且 `RollbackFailed` 是设计称为最严重的结果——因此它值得超过一个注释。

原因不是回退。`hooks/postinstall` 覆盖单元文件且按设计不把它们放回去：钩子争论一个没有生效的发布留下一个服务失败直到下一个发布生效，无论哪种方式都是相同情况。那个推理成立且不变。它没有预料到的是单元在被回退*到*的发布的重启集中——然后回退重新运行相同的重启并继承相同的失败。可以通过普通的坏发布而非仅上面的降级情况到达：两个连续的发布交付相同的单元名且较新的那个是坏的。

**修复将交换与应用动作分离，因为它们中只有一个是恢复。** 过了 `swap_to` 且试验被清除，机器人*已经*回到它来自的发布；一个然后重启失败的单元是第二个事实，而非对第一个的矛盾。因此 `Error::RollbackFailed` 保持其含义——机器人根本无法被放回——且回退期间失败的应用动作被携带进报告的结果并以 `error` 记录：

```text
not healthy within 30s: …; the release was reverted, but restarting robotd failed: …
`Restart=` may have brought it back since — `robotctl health` says whether it did.
```

两个事实，按某人需要它们的顺序：首先为什么更新失败，然后没有随回退回来的单元。

那个句子的后半部分过去读的是"so something on this robot is down"，且它错得足够频繁值得命名。这里的每个 daemon 运行 `Restart=always`，且一个立即退出的 daemon 在健康门的三十秒到来之前很久就耗尽了 systemd 的每十秒五次启动——因此回退的重启经常被以 `Start request repeated too quickly` 拒绝，且单元片刻后自己回来了。一块工作台板在它自己的 `robot healthy` 行正下方打印了那个停机声明。`restart_one` 现在用 `reset-failed` 清除计数器并再试一次，这移除了原因；结果报告它观察到的拒绝并命名回答它无法回答的东西的命令。

两个被拒绝的替代方案，因为两者都不明显错。使 `postinstall` 可逆是钩子明确拒绝的变更；它需要发布之外的状态并给恢复路径添加一个失败模式，那是必须保持无聊的一个地方。在*任何地方*容忍失败的重启会削弱 `restart_one` 故意画的区分——一个存在且不会启动的单元是坏发布被捕获的方式，且那在进入的路上仍然是致命的。

### 不做

**板作为自托管运行器。** 运维成本，且 CI 的单点故障。第 3 项按需获得大部分价值，那是房间里机器人属于的地方。

## 第二个独立问题：开发通道上的版本偏差

在同一会话中发现且容易与上面混淆，但任何数量的安装测试都不会捕获任何一个——在两种情况下制品都是完整且正确的。

形状总是相同的，且**曾经打开本节的句子不再为真。** 它读的是："`updaterd` 在更新期间从不重启自己（§4.1），因此它保持运行旧二进制直到下一次重启，而盒子上的其他一切立即移动到新发布。"那是下面两个实例的根本原因，且它已修复——`updaterd` 现在在更新回复后五秒重启自己。偏差窗口是秒，不是"直到有人重启"。

带着那个读两个案例。两者都不再是实时事件，且**两者现在都已关闭**——案例 1 通过修复它提议的东西，案例 2 通过决定反对它：

- 案例 1 的 `serde(default)` 修复**没有**被更短的窗口变得多余：版本偏差只是击中它的最常见方式，且任何更新的解析器-更旧的发送者对都会。已完成，在默认零是诚实的部分上。
- 案例 2 的握手修复**大部分**被它变得多余，从"恢复命令本身停止工作"降到"一个五秒的窗口期间它不工作"——且当设计论点最终被写出来时，它所依赖的前提没有存活。确切的 `!=` 保持；改变的是消息。见下文和 #77。

两个实例，都真实，都花了大约一小时。

### 1. 添加到 `HealthResult` 的必需字段

`main` 向 IMU 部分添加了 `consecutive_stale_blocks` 并从它发布了 0.2.0。一个在那之前合并了 `main` 的分支*没有*发送该字段。`robotd` 完美启动——服务 socket，加载两个策略，以 50 Hz 运行循环——且常驻的 0.2.0 `updaterd` 因缺失字段拒绝其回复。`RobotIo::health` 将不可解析的回复映射为 `Health::Unreachable`，因此门针对一个完全健康的机器人报告 `not healthy within 30s: unreachable`，并回退了一个好发布。

修复，都小，且**都已完成**：

- **新 `HealthResult` 字段上的 `#[serde(default)]`**，因此更新的 `updaterd` 仍然可以解析更旧的 `robotd`。否则每个 `--ref` 安装早于健康字段添加的分支都会击中这个，这是整个开发工作流。

  咬人的一半是嵌套的那个：每个*顶层*字段已经携带 `#[serde(default)]`，包括 `imu`，而嵌套的 `ImuHealth` 上的 `consecutive_stale_blocks` 没有。`ImuHealth` 和 `BusHealth` 现在在容器级别携带它，因此添加到任一的字段默认而非使整个解析失败。

  `LoopHealth`、`Battery` 和 `MotorThermal` 故意**不**，且例外是修复中有用的部分：那些部分携带*测量值*，其中默认零是一个更旧的发送者从未说过的谎言——一个默认的 `percent: 0.0` 在一个满电的机器人上渲染为平电池。规则是"默认省略诚实意味着的东西"，而非"默认一切"，且 `ImuHealth` 的文档注释逐字段争论它。
- **一个不同的 `Health::Incompatible`** 而非重用 `Unreachable`，因此原因读为"answered in a shape this updaterd does not understand"而非暗示机器人宕机。纯诊断，且它会在一分钟内发现上面的问题。

  已完成。它在被添加时也发现了自己的邻居：`safe_to_restart` 以同样的方式折叠不可读的回复，且 `permits_restart` 然后将其读为*安全*——与其自己的注释承诺的相反。那变成了 `SafeToRestart::Incompatible` 和 #68。

### 2. `robotctl` 和 `updaterd` 之间的 `API_VERSION` 偏差

`robotctl` 是一个进入 `current` 的符号链接，因此它跟随安装的发布。`updaterd` 不。因此一旦一个发布改变 `API_VERSION`，两者**保证**不一致直到 `updaterd` 重启——且停止工作的命令是 `robotctl update apply`，这恰好是你会用来摆脱它的那个。

通过普通使用而非刻意设计演示：安装分支 A，在等待 CI 时安装分支 B，且每个 `robotctl` 调用失败并报 `client speaks API v2, daemon speaks v3`。逃脱方法是调用一个来自版本与运行的 daemon 匹配的发布目录的 `robotctl`，或者重启 `updaterd`——两者都无法从错误中发现。

握手至少*捕获*了它并命名了两个版本，这比案例 1 做到的多。

第一个提议的修复是**`hello` 应该只在客户端比 daemon*更新*时拒绝**，且它被**决定反对**（#77）：它假设版本提升是累加的，而它们不是——v5 添加了 `pad.*` 且是累加的，v4 使 `system.authenticate` 变为必需且不是。基于一个常量不跟踪的模式接受更旧的客户端会承诺没有东西强制执行的向后兼容性。

**改为通过完全移除门控来修复。** 那个拒绝的前提存活——版本提升不承诺任何东西——但结论不随之而来。破坏不匹配对等方的是一个*它无法到达的路由*或一个*移动了的参数形状*，且两者都已经自己拒绝自己，按名称，在唯一无法被服务的调用上：来自 `Request::as_call` 的 `METHOD_NOT_FOUND`，来自参数解码的 `INVALID_PARAMS`。握手上的门控也在每个其他调用上触发——事实上每个调用，因为 `hello` 先于它们所有——这就是一个一位数的差异如何同时带走了 `update apply` 和 `version`。因此 `updaterd` 现在记录版本对并服务调用；差异通过 `HelloResult::api_version` 到达客户端，且 `robotctl` 每次运行打印一行警告。

在门控可以去掉之前两件事必须为真，且第二个是有用的部分：

- **拒绝必须是冗余的，不仅仅是烦人的。** 它是：`robotd`、`configd` 和 `padd` 根本不检查数字，且 `updaterd` 在 `update.status` 之前无论如何不需要握手。`duck-btctl` 已经从链路的远端得出了相同的结论（#102）。
- **静默忽略的参数必须停止成为可能。** `serde` 忽略它不知道的东西，这就是使门控感觉承重的原因：v7 添加了 `ApplyOptions::from_dir`，且一个忽略它的 v6 daemon 会从其*配置的*源安装，而操作员相信他们在侧载一个目录。每个参数类型现在拒绝未知字段，因此那是一个命名成员的 `INVALID_PARAMS`。它只向前到达——在此之前构建的 daemon 仍然忽略它不知道的东西——这就是为什么 `API_VERSION` 提升仍然值得做。

消息在此之前被重写且现在随门控一起消失了。它说 `client speaks API v2, daemon speaks v3` 且没有命名出路；它长出的补救（重试，或使用 `/usr/local/bin/robotctl` 的符号链接）现在存在于 `robotctl` 的警告中，那里没有东西被拒绝。

### 为什么这些不是安装路径 bug

上面计划中的任何东西都不会捕获任何一个。两次制品都是正确的；错的是某一时刻运行的*一对*版本，这只存在于已经被更新过的机器上。第 4 项（本地真实 systemd）如果容器也运行更旧的 `updaterd`，会捕获案例 1 的*健康门*后果，但故意构建那个偏差是一种不同的测试——更接近兼容性矩阵而非安装测试，且值得保持分开。

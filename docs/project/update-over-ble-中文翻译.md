# 从手机更新机器人

状态：已发布，尚未在板上运行 · 日期：2026-08-19 · 负责人：pierre

通过蓝牙的更新路径已经走了大半，但没人真正驱动过它。`btd` 已经路由了更新子集，`updaterd` 已经向任何询问者流式传输进度，而 `duck-btctl` 可以通过 `call` 触及所有这一切。驱动它暴露出一个缺陷，使应用自身的流程——启动更新、观看进度——变成机器人静默地从未执行的更新，`updaterd` 中还有两个较小的缺陷，以及一个值得编写的客户端界面。

本文记录了发现了什么以及决定了什么。机制与代码相邻：[`app-path-design.md`](../design/app-path-design.md) §3.5 负责连接通道，§3.1 负责路由子集，`btd/src/route.rs` 承载了使其通过的每条路由的推理。

## 1. 已经能工作、且未被重建的部分

**路由子集覆盖了读取和触发。** `hello`、`update.check`、`update.apply`、`update.status`、`update.subscribe`、`update.log` 和 `update.listInstalled` 已经能到达 `updaterd`，`robot.health` 能到达 `robotd`。这里没有向协议添加任何方法。

**一次 apply 已经流式传输它自己的进度。** `updaterd` 的 `run_mutating` 在回复之前，将 `update.progress` 通知写入 apply 到达的连接；`btd` 将上游的每一行泵入会话而不读取它；`duck-btctl` 打印无 id 的行并继续等待。因此进度在 apply 期间到达 BLE 客户端，完全不需要订阅——而 `duck-btctl.md` 声称相反，*"在其自身连接上的 apply 在完成前是静默的"*，这一点已被纠正。

**在更新中途重连的客户端不会丢失。** `updaterd` 为每个组件保留最新的 `Progress` 并将其重放给新订阅者，`update.status` 在更新期间从缓存快照中回答，并实时修补阶段。两者都是手机在链路断开后所需要的。

**而且回复在传输断开之前就出去了。** `updaterd` 和 `btd` 是更新永远不会重启的两个单元，两者都在回复后约五秒重启（[`restart-order.md`](../design/restart-order.md) §1）。

## 2. 出了什么问题

### 2.1 一个长调用使会话其余部分静默 · `btd` · **已修复**

`Pool` 为每个会话的每个服务持有一个连接，而它背后的两个守护进程一次只为一个连接服务一个请求。因此 `update.subscribe` 后跟 `update.apply` 会把 apply 写入一个 `stream_progress` 已停止读取的 socket：它永远不会运行、永远不会回复、也永远不会报错。所有者点击"更新"，机器人什么都不做，而且任何地方都找不到错误。`update.apply` 后跟 `update.status` 是同样的缺陷，症状更温和——状态轮询超时，而机器人一切正常并在更新。

调用现在按它们持有连接的时长分组，每组获得自己的连接：`app-path-design.md` §3.5 有通道说明、为什么在发生共享的地方共享一个连接是正确的，以及为什么每次调用一个连接被拒绝。两个失败都有在没有修复时会失败的测试。

这是这里唯一一个移动应用无法绕过的变更。

### 2.2 进度是对准一根 20 字节管道的消防水带 · `updaterd` · **已修复**

源报告它写入的每一个 HTTP 块——对于一个发布制品来说是数千个——每个订阅者都为所有这些付出代价。一条进度行大约一百字节，在 `btd` 帧定的 20 字节下限下是五六个通知，而当客户端落后时 `btd` 会丢弃行，因此手机看到的是百分比的任意子集，以及一个从 12 → 61 → 34 跳动的进度条。

现在每个整百分比最多一个通知，每秒最多四个，在产生数字的引擎中合并，因此 `robotctl update watch` 获得相同的流。被间隔抑制的百分比在下载结束时仍然会发布，否则快速下载会可见地停在 97%。

### 2.3 `update.check` 在引擎锁上阻塞 · `updaterd` · **已修复**

`ipc.rs` 在其自己的头文件中陈述了规则——只读请求使用 `try_lock`，以便 `status` 和 `subscribe` 在更新期间保持可应答——而 `check` 没有遵循它。在 apply 期间被询问时，它在 apply 完成后才回答，几分钟后，这在手机上与一个已经停止应答的机器人无法区分。它现在立即回答 `BUSY`，`update.pin` 也是如此。

### 2.4 已决定：回退可以从手机到达

`update.rollback` 和 `update.select` 曾被拒绝；两者现在都已路由。`update.pin` 和 `update.resetToGolden` 保持拒绝。推理在 `btd/src/route.rs` 的分支上，并在 `app-path-design.md` §3.1 中总结；决定它的因素：

`update.apply` 已经被路由，而且是三者中后果更重大的——它安装从未在这块板上运行过的代码，来自网络——而 rollback 和 select 移动到昨天在它上面运行过的发布，不下载任何东西，并且像任何其他转换一样被门控和自动回退。引擎自己的自动回退覆盖了未通过健康门的发布，这不是所有者拿起手机的场景：那是一个安装了、通过了门、然后表现*更差*的发布——一个走得不稳而不是完全不走的策略，一个停止重连的手柄。除了人没有什么能回退那个，而那个人正拿着手机且没有 ssh。

两者都被打开而不是只开 `rollback`，因为 `update.listInstalled` 已经被路由：应用可以显示板上的每个发布，而能显示它们却不能选择一个是奇怪的一半。`select` 需要从列表中挑选一个版本，这是一个更大的界面，因误触而出错的风险更大，这是被接受的代价。

`pin` 是有趣的拒绝。一个错误的 `select` 离被撤销只差一个发布，而且机器人会说明它在哪个发布上；一个被误触 pin 住的机器人拒绝之后的每一次更新并报告自己是最新的，这是这里唯一一个看起来像正确行为的失败。

### 2.5 手机触发的更新被记录为 `btd` · **已记录，未修复**

`updaterd` 在每次变更时从 `SO_PEERCRED` 记录调用者的 uid 和 pid，这是支持回答"谁触发了这次回滚"的方式。通过 BLE，答案永远是 `btd`，对每部手机都是。`btd` 逐字转发参数，添加一个"谁"字段会使它成为请求的作者而不是管道。只有在支持需要区分两部手机时才值得重开。

### 2.6 客户端截止时间是总时长，而非空闲时长 · `duck-btctl` · **已修复**

固定预算要么切断一个正在工作的更新，要么等待一个死掉的机器人，而有用的信号已经在到达：每个进度通知都是机器人正在工作的证明。截止时间现在是静默时长——更新三分钟，这是一个人可以合理拥有的最长间隔（一个安装后钩子），而不是一个人可以花费的最长时间。手机应用继承这个原则，而不是代码。

### 2.7 链路在 daemon apply 回复后约五秒断开

不是缺陷——§1 的排序，正常工作——但每个客户端都必须预期它，而且机器人宣布的断开连接不能被读为失败的更新。要据此构建的序列：

1. `update.apply` 以其结果回复。这就是答案；更新完成了。
2. 大约五秒后 `btd` 重启，连接断开。
3. 重连，读取 `update.status`。`last_attempt` 携带结果，因此在步骤 1 中错过回复的客户端仍然可以报告它。

`duck-btctl` 在它发生之前打印步骤 2。

### 2.8 故意开放：通过蓝牙的 `from_dir`

`ApplyOptions.from_dir` 命名机器人上的一个目录，这对手机毫无意义，在工作台上有用。过滤它意味着 `route.rs` 基于参数而非方法做决定，而检查参数正是 `btd` 不做的事。Preflight 已经拒绝了会咬人的情况——并且说明了——所以这保持原样，在这里命名以便下一个人找到一个决定而不是一个疏忽。

## 3. `duck-btctl` 现在提供什么

`version`，以及带有 `check`、`apply`、`status`、`versions`、`log`、`rollback`、`select` 和 `watch` 的 `update`——与 `robotctl update` 使用相同的词，因此在机器人上学到的命令可以通过无线电工作。参数从 `duck_ipc_proto` 自己的类型构建，而不是手写 JSON，这是 `call` 留给正在打字的人的：`update.apply` 的目标是一个外部标记的枚举，因此 `--ref` 和 `--version` 是不同的 JSON *形状*，错误的那个是一个解析错误，里面没有任何可操作的内容。[`duckctl.md`](../robot/duckctl.md) 有每个命令。

进度在 stderr 上每个事件打印一行，这是该页面已经承诺但工具没有做到的。

`duck-btctl` 是一个临时方案，这就是它重要的地方：§2.1、§2.2 和 §2.3 是机器人端的，因此应用继承了修复，而 §2.6 的截止时间形状是客户端的，因此工具做对了，应用自己的笔记将不得不说明原因。

## 4. 还剩什么

**没有任何一项在板上运行过。** 以上所有内容都被测试覆盖，而测试看不到手机看到的东西：进度是否在真实的 20 字节链路上平滑到达，apply 的回复是否在 `btd` 重启之前到达客户端，以及每个服务第四个 socket 在 Zero 3W 上是否有任何代价。那是下一次会话，用 `duck-btctl update apply --ref` 对着一个开发板。

**`duck-btctl.md` 中的过时声明是通过阅读代码纠正的，不是从板上。** 如果通过 BLE 的 apply 最终还是静默的，要看的机制是 `btd/src/link.rs` 中的出站队列，而不是路由。

## 5. 本文故意不做的事

**没有取消。** 引擎没有，半应用的更新比慢的更新更糟。一个走开的客户端已经被处理：更新完成。

**没有来自手机的自动应用开关。** `deploy/updater.toml` 故意不让客户端机器人加入无人值守重启，在有一个机群需要推理之前，这不是一个应该暴露为开关的决定。

**没有加密。** `app-path-design.md` §8.1 负责它，它在这里没有阻塞任何东西，以上关于无线电范围内的对等方可以做什么的每一个主张都假设它仍然关闭。
